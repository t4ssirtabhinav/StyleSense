## Post-QA design amendment — 2026-07-25 (proxy-image strategy)

User directed further investigation into whether smarter/dynamic image sizing could close `BL-058`'s latency gap, considered across the whole pipeline (R2 storage, Gemini, display), not just this ticket in isolation.

**Additional live data gathered** (same photo, properly spaced to respect Replicate's rate limit — see below): 500px→4.4s, 800px→6.5s, 1000px→6.1s, 1200px→10.8s/10.1s/4.1s (three separate runs, same input, no code change — a >2.5x spread). Conclusion: resolution has *some* effect but Replicate-side cold-start/queue variance dominates within the already-reasonably-sized range — a pure resolution fix won't reliably guarantee the original AC.

**Also discovered live**: the Replicate account is rate-limited to 6 requests/minute (burst of 1) while balance is under $5 — a real `429` was hit mid-test. Logged as `BL-059` (infra) — the existing `asyncio.Semaphore(3)` doesn't guarantee staying under this.

**User's chosen direction** (of three options presented): keep SS-010's 1200px original untouched in R2 (other tickets may need that resolution for display/tagging); generate a separate, smaller in-memory proxy (800px, chosen as a reasoned middle point, not a proven-optimal number) just for the Replicate call; composite the returned low-res alpha mask back onto the full-resolution original for the final `clean.png`. Tradeoff stated plainly in the design doc: upscaled mask edges are marginally softer than a native full-res mask.

**Design doc amended** (`docs/tickets/SS-011-design.md`): new "Image sizing strategy for the Replicate call" section with the full data table; target latency AC renegotiated from a flat "<10s/<4s avg" to "typical 4-8s, worst case ~15s to accommodate genuine cold starts" — the original ceiling isn't realistic given measured Replicate-side variance outside this pipeline's control. Two new pure functions added to `image_processing.py`'s file entry (`resize_for_bg_removal`, `apply_alpha_mask_to_original`), service flow updated, edge cases/test plan/open questions/backlog deltas all updated in place.

**New backlog**: `BL-059` (Replicate's own rate limit under low balance). Sending back to Developer for a fix pass to implement the proxy/compositing change — not yet built.

## CI fix — 2026-07-25 (two failures, both root-caused and fixed)

PR #23's CI reported two failures. Both investigated to actual root cause (not patched blind) and fixed:

**1. Backend test (`test_wardrobe_router.py::test_missing_or_invalid_auth_returns_401_via_real_dependency` — `KeyError: 'SUPABASE_URL'`):** every other test exercising `get_current_user_id`'s real path (`test_auth_dependency.py`, `test_wardrobe_repository.py`) correctly used `monkeypatch.setenv("SUPABASE_URL", ...)` before invoking it — this one test alone missed that convention and silently relied on the local dev machine's real root `.env` (loaded via `main.py`'s `load_dotenv()`). CI checks out a clean repo with no `.env` file and never sets these as workflow env vars, so it `KeyError`s there but passes locally. Fixed the one test, and added `backend/tests/conftest.py` — an autouse fixture setting baseline dummy `SUPABASE_URL`/`SUPABASE_ANON_KEY`/`CLOUDFLARE_R2_*` env vars for every test, so no future test can make the same mistake (a test wanting to exercise "env var missing" behavior can still `monkeypatch.delenv(...)` within its own body, unaffected by the fixture — confirmed `test_r2_storage.py`'s existing missing-config test already does exactly this). **Verified fix under true CI-like conditions**: temporarily moved the real root `.env` aside entirely and re-ran `ruff`/`mypy`/`pytest` — 82 passed, 1 skipped, all clean, restored `.env` after.

**2. Supabase migration drift check (`supabase-migrations.yml`):** pulled the actual failed run's log via `gh run view --log` rather than guessing. Real cause: `supabase db diff --linked` generates lowercase SQL with quoted identifiers (`drop extension if exists "pg_net";`), but the workflow's own noise-filter regex only matched an uppercase, unquoted `DROP EXTENSION` and unquoted role names in its GRANT pattern — so the exact pg_net/pg_cron case the filter's own comment says it handles slipped through uncaught. The CLI's own human-readable reminder ("Found drop statements in schema diff. Please double check if these are expected:") also isn't SQL and matched nothing. No real schema drift existed — migration 005 genuinely matches the live project. Fixed the filter: strips blank/`--`-comment lines first, case-insensitive, quote-tolerant on role names, explicitly excludes the CLI's reminder text, and checks "any non-blank line remains" rather than raw file size (a lone leftover blank line would otherwise still trip `-s`). **Verified against two synthetic reproductions** before committing: the exact failing output (now fully filtered to empty) and a synthetic real schema change (correctly still fails) — confirms the fix closes the false positive without masking genuine drift. Also removed the now-redundant `supabase/migrations/.gitkeep` (directory has had 5 real migration files since long before this session; empty placeholder no longer needed) — this also ensures the fix lands under the workflow's own `paths: supabase/migrations/**` trigger filter so it actually re-runs on this PR.

Logged as `BL-060` (ci). Both fixes are durable, repo-wide guards (conftest.py fixture, filter regex), not one-off patches scoped to this PR's specific failure.
