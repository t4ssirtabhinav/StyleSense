## Architect — 2026-07-30 (Opus, full lane)

**Verdict: design complete, `Risk: high` confirmed (not downgraded).** Spec is [`docs/tickets/SS-033-design.md`](../tickets/SS-033-design.md); it is the Developer's only input — do not re-open the proposal.

Three one-way-door surfaces justify `high`: the migration **narrows a shipped RLS policy** (`user_owns_sessions` is `FOR ALL` today, so a client can currently insert/update/delete — and post-SS-033 cascade-delete — its own session rows); a **denormalised `user_id` sits behind the RLS predicate** on both new tables, where one wrong value leaks one user's wardrobe contents to another; and it creates an **unbackfillable, purpose-limited personal-data store** (~7.3M rows/month at 10k users) whose retention enforcement depends on a scheduler this pass could not verify. All three fail quietly.

**Key decisions**

- **Extend, don't create.** `suggestion_sessions` gains 9 additive columns. `[VERIFIED 2026-07-30, ripgrep]` nothing in `mobile/`/`backend/` reads or writes it — only the two Edge Functions' service-role `count` queries — which is what makes the RLS narrowing safe.
- **Cost-proxy fix (`BL-107`):** `cost_incurred BOOLEAN NOT NULL DEFAULT **true**` (alerting must fail loud, never quietly under-report) plus a required `zero_cost_reason` enforced by a paired CHECK, a partial index matching the filter, and one shared `_shared/suggestionSessions.ts` predicate. `weekly-report`'s change is deliberately **additive** — its session count is an engagement metric, not a cost figure, so the total stays and a billable count is added beside it.
- **Superseded columns: deprecate via `COMMENT`, do not drop.** Both are `NULL` in every row and are declared in the committed `mobile/types/supabase.ts`; the drop is its own CONTRACT migration per SS-025's `007`/`008`/`009` precedent. A `test_db_schema.py` assertion makes the deprecation machine-checkable.
- **Retention: batched cascade delete, not partitioning.** Partitioning was rejected for a structural reason, not effort — the outcomes→impressions FK forces the partition key into the FK, and an outcome legitimately lands in a later partition than its impression, which breaks the ticket's own "purge as a unit" case with the very mechanism chosen to satisfy it. Deleting *sessions* and cascading makes orphaning impossible. The window reads from `app_config` (SQL-side, clamped `[30,730]`, degrades to 180), so 180 stays the user's number without a migration.
- **`user_id` is derived by a `BEFORE INSERT` trigger, never trusted from the writer** — that is the leak guard, and the test that a deliberately wrong `user_id` gets corrected is the most important assertion in the schema module.
- `item_ids` is a `UUID[]` with **no FK**, which is what makes "impressions survive item deletion" structural rather than procedural. `ISuggestionLogRepository.log_session` takes the session *and* its impressions in one never-raising call, so a caller cannot half-log a request.

**Blockers the user/Developer must resolve before or during Developer**

1. **`pg_cron` availability is unverified** and AC #6 ("retention enforced") depends on it. The migration degrades to a loud `WARNING`, not a failure; the fallback is a scheduled Edge Function, which `BL-113` shows is itself on unverified ground. Verify first.
2. **DPDP Act applicability is `[trained-knowledge — must be verified against the current statutory text]`** before the first production row. No consent surface exists for this collection.
3. **Serialize the `db push`** relative to the sibling Wave 1.5 tickets (`BL-110`); regenerate `mobile/types/supabase.ts` only if the diff is confined to this ticket's objects.
4. Nothing writes these tables at merge (by design — `outfit_suggestion_service.py` is off-limits per `BL-096`/`BL-102`). **The unbackfillable data does not start accumulating until SS-020 ships.**
