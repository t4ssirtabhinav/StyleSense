### Architect — 2026-08-15 — DONE

**Verdict: `Risk: high` confirmed** (unchanged from the raw ticket). Design note (sketch tier): `docs/tickets/SS-070-design.md`.

Ground-check corrected the ticket: **`public.users` has no FK to `auth.users`** (`001_initial.sql:25`, no migration adds one), so `auth.admin.delete_user` alone orphans the profile row and all its children — the ticket's "cascades via the FK from `001_initial.sql`" Technical Note is wrong. Worse, four tables reference `users(id)` with no `ON DELETE` action (`suggestion_sessions`, `user_avatars`, `social_posts`, `shopping_wishlist`) and will **block** the profile delete for any account that actually used the app. Design specifies an explicit ordered delete: four no-action tables → `public.users` (cascades the rest) → `auth.users`.

Other decisions: `supabase-py` 2.31.0 Admin API surface verified against installed source (`create_user`/`list_users`/`delete_user`/`generate_link` names and params all as assumed); `list_users` has **no** server-side filter, so `list`/`delete` page and filter client-side on prefix **and** `app_metadata` marker. `session` uses `sign_in_with_password` rather than magic-link redemption (simpler; `BL-174` confirms email confirmation off); localStorage key `sb-<project-ref>-auth-token`. `wardrobe_items` seed columns confirmed against migrations (`category` nullable since 005, `occasion_tags` is `TEXT[]` since 008, `cost_per_wear` generated — never insert).

No blockers for Developer. AC #4 and #5 are manual-verification by construction — QA must record them as manually verified, not as test-covered.

**Backlog:** added `BL-175` (Active, `schema`) — the missing `auth.users` FK is app-wide, matters to any future delete-account feature; not fixed here. `BL-167` noted as *related, not resolved* — the `session` subcommand works around the missing sign-out, it doesn't fix it. `BL-001`/`BL-037`/`BL-047`/`BL-171` unaffected.

**All six mandatory guard rails implemented exactly as specified:** (1) `_require_opt_in()` gates every subcommand incl. `list`, checked in `main()` before the client is even constructed; (2) `delete` requires prefix **and** `app_metadata` marker, re-verified against the record the Admin API actually returned, not inferred from the label; (3) every subcommand's arg is `--label` only, id resolved internally via `_find_by_label`; (4) `create`/`seed`/`delete` print the project ref (parsed from `SUPABASE_URL`) and require an injectable interactive confirmation; (5) `create` pre-checks `public.users` by email and refuses a duplicate label before ever calling `create_user` (BL-169); (6) `service_role` is scrubbed from every exception via `_run_scrubbed`/`_scrub` (`from None` also suppresses the unscrubbed original from traceback display) — asserted by an autouse leak-guard fixture that checks captured stdout/stderr after every single test in the suite, not just the ones targeting failure paths.

**Delete order matches the design note's correction exactly:** `NO_ACTION_FK_TABLES` (`suggestion_sessions`, `user_avatars`, `social_posts`, `shopping_wishlist`) cleared first, then `public.users` (cascades `wardrobe_items`/`outfits`/`ai_cost_ledger`/`suggestion_impressions`), then `auth.admin.delete_user(..., should_soft_delete=False)` — asserted by explicit call-order test. Post-delete verification queries all three surfaces (`get_user_by_id` → 404, `public.users` select, `wardrobe_items` select) rather than trusting a clean exit (AC #6).

**`wardrobe_items` seed payload** uses only real registry values per the design note: `category='western_top'`, `pattern='solid'`, `fabric='cotton'` (both real `patterns`/`fabrics` keys per `016`), `occasion_tags=['office']` (real `occasions` key per `007`), `season_tags=['summer']`, `processing_status='bg_removed'`, placeholder `image_url` (never R2), `cost_per_wear` never inserted (GENERATED column).

**Boundary sweep (Risk: high, §C6 — full sweep run, not skipped):** empty (`--items 0` refused, empty/malformed `--label` rejected by `LABEL_RE` before any admin call), max (added `MAX_SEED_ITEMS=200` typo guard, not in the design note but cheap and directly protects the shared live DB from an accidental extra-zero), duplicate (label collision refused pre-flight on both the auth side and the `public.users`/BL-169 side), concurrent (any race is caught by `_run_scrubbed` and surfaces as one clean `ERROR:` line — never a raw driver traceback, structurally, since `main()`'s outer catch-all is unconditional), stale (session-expiry reminder printed by `session`), mid-operation crash (`delete` re-run after a simulated kill between clearing the FK tables and deleting `public.users` finishes cleanly — every step is idempotent).
