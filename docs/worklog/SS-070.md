**Verdict: `Risk: high` confirmed** (unchanged from the raw ticket). Design note (sketch tier): `docs/tickets/SS-070-design.md`.

Ground-check corrected the ticket: **`public.users` has no FK to `auth.users`** (`001_initial.sql:25`, no migration adds one), so `auth.admin.delete_user` alone orphans the profile row and all its children — the ticket's "cascades via the FK from `001_initial.sql`" Technical Note is wrong. Worse, four tables reference `users(id)` with no `ON DELETE` action (`suggestion_sessions`, `user_avatars`, `social_posts`, `shopping_wishlist`) and will **block** the profile delete for any account that actually used the app. Design specifies an explicit ordered delete: four no-action tables → `public.users` (cascades the rest) → `auth.users`.

Other decisions: `supabase-py` 2.31.0 Admin API surface verified against installed source (`create_user`/`list_users`/`delete_user`/`generate_link` names and params all as assumed); `list_users` has **no** server-side filter, so `list`/`delete` page and filter client-side on prefix **and** `app_metadata` marker. `session` uses `sign_in_with_password` rather than magic-link redemption (simpler; `BL-174` confirms email confirmation off); localStorage key `sb-<project-ref>-auth-token`. `wardrobe_items` seed columns confirmed against migrations (`category` nullable since 005, `occasion_tags` is `TEXT[]` since 008, `cost_per_wear` generated — never insert).

No blockers for Developer. AC #4 and #5 are manual-verification by construction — QA must record them as manually verified, not as test-covered.
