### 3. Tests written

**`backend/tests/test_db_schema.py`** (new) — implements all 6 tests from the design doc's test plan:
- `test_all_seven_tables_exist`
- `test_enums_have_full_value_set` (asserts exact 21/3/12 value lists and order via `pg_enum`/`pg_type`)
- `test_rls_enabled_on_all_tables` (via `pg_class.relrowsecurity`)
- `test_wardrobe_occasion_tags_gin_index_exists` (via `pg_indexes`)
- `test_cost_per_wear_computed_correctly` (inserts `purchase_price=1000, wear_count=4` and asserts `cost_per_wear == 250`; inserts `wear_count=0` and asserts `cost_per_wear == purchase_price`)
- `test_rls_denies_cross_user_read` (simulates two users via `SET ROLE authenticated` + `request.jwt.claims` GUC, the same mechanism PostgREST uses internally, since no live JWTs were available)

**Checked existing conventions first:** `backend/tests/` only had `test_health.py` (plain `TestClient` against `main.py`, no DB fixtures, no conftest.py) — there was no existing DB connection pattern to follow, so I introduced one. `backend/requirements.txt` only has the `supabase`/`postgrest` Python packages (PostgREST-based REST client), no `psycopg2`/`asyncpg` — PostgREST cannot query `pg_catalog`/`information_schema` or issue `SET ROLE`, so schema-level introspection requires a direct Postgres driver. I did **not** add `psycopg2-binary` to `requirements.txt` or install it, since there's no live `SUPABASE_DB_URL` to test against yet and installing an unused dependency didn't seem justified for a verification-only ticket — instead the whole module is guarded with `pytest.importorskip("psycopg2", ...)` plus `pytestmark = pytest.mark.skipif(not SUPABASE_DB_URL, ...)`, so it **skips cleanly** (not an error, not a false pass) when neither is present, which is the current state. Confirmed via `pytest tests/ -v`: `1 passed, 1 skipped` (health check passes, schema suite skips with a clear reason string).

**Explicitly not executed against a live database** — these tests are written to be correct and runnable per the design doc's spec, but have NOT been run against the actual `mefpfykuinasgkpfhmzk` project or a local Supabase stack. Whoever picks this up next needs `pip install psycopg2-binary` in `backend/venv` plus a `SUPABASE_DB_URL` env var (direct Postgres connection string, `postgres` role, from Supabase Dashboard → Project Settings → Database) to actually run them.

**`mobile/__tests__/types/supabase-types.test.ts`** (new) — runtime shape assertions (not just compile-time types) against `Constants.public.Enums` in the generated types file: `wardrobe_category` has exactly 21 members matching the exact value list/order, `plan_tier` has exactly 3, `occasion_type` has exactly 12. These guard against silent drift if someone edits an ENUM in SQL/dashboard without regenerating types.

**`mobile/__tests__/lib/supabase.test.ts`** (new) — added per the design doc's conditional instruction ("only add it here if the Developer finds `lib/supabase.ts` itself lacks any coverage yet") — confirmed no existing test covered it (only `__tests__/sanity.test.ts` existed beforehand). Mocks `@supabase/supabase-js`'s `createClient` and asserts the client is constructed with `persistSession: true`, `autoRefreshToken: true`, `detectSessionInUrl: false`, and an `auth.storage` object shaped like the SecureStore adapter (`getItem`/`setItem`/`removeItem` functions) — protects the foundation SS-003 depends on. Also asserts the key passed to `createClient` is sourced from `EXPO_PUBLIC_SUPABASE_ANON_KEY`, not a service-role key.
