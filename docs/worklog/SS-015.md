# SS-015 — Wardrobe Item Edit, Delete & Mark Worn

Branch: `feature/SS-015-wardrobe-item-edit-delete-mark-worn`

## Architect — 2026-07-27

**Verdict:** Design complete — `docs/tickets/SS-015-design.md`. **Risk: high (full lane — every human gate preserved).** Justification: new table + migration + RLS policy + trigger + a `UNIQUE` constraint on an existing table + a lossy, irreversible backfill; plus item delete moving onto a backend endpoint that permanently destroys R2 objects. All squarely inside CLAUDE.md's / §C2's `high` bar. The raw ticket's own "no new schema, no new routes" Status note is superseded by `BL-071`.

**Key decisions:**
- **`wear_count`/`last_worn_at` become trigger-maintained caches, not a view.** `cost_per_wear` is `GENERATED ALWAYS ... STORED` off `wear_count`, and a generated column can only reference its own row — so `wear_count` must stay a real column. A `STORED` column recomputes on every row `UPDATE`, so the trigger's write keeps `cost_per_wear` correct with zero changes to it. A view would have forced dropping/recreating the generated column for no gain.
- **Cross-user integrity is the non-obvious risk here**: without guards, a user could insert a wear row pointing at *another* user's `item_id` and corrupt that user's `wear_count` through the trigger. Closed two ways — explicit `WITH CHECK` on the new RLS policy, and a composite FK to `wardrobe_items (id, user_id)` (needs a new `UNIQUE (id, user_id)` on `wardrobe_items`). A dedicated manual DB check for this is in the test plan; it must not be skipped.
- **`UNIQUE (item_id, worn_on)`** — one wear per item per day, making the Mark Worn tap idempotent. Directly fixes `BL-071`'s "unbounded taps inflate the count" complaint; costs the ability to log two wears in one day. Architect's call, flagged for confirmation.
- **Delete routed through a new `DELETE /wardrobe/items/{item_id}`** (DB row first, R2 cleanup second, async) rather than the raw ticket's suggested Edge Function/DB webhook — the backend already holds real, verified R2 credentials, whereas the Edge Function runtime is precisely where `BL-069` found `CLOUDFLARE_R2_*` was never provisioned.
- The client's `markWardrobeItemWorn` write is **deleted**, not adapted — leaving it would let a client write a column the trigger now owns.
- No new date-picker dependency (quick-picks + validated `DD/MM/YYYY` input); no new `components/ui/` primitive for the toast (in-sheet banner) — both follow SS-014's precedents on a web-first app.
