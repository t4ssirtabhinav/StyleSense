**Verdict:** Design complete, full lane. See `docs/tickets/SS-012-design.md`. (Ran on `model: opus` per triage.)

**Risk: high** — a deliberate "classify up on the fence" call, stated as such. On the strict §C2 criteria this is *lighter* than SS-011: **no migration** (every output column already exists in `001_initial.sql`; tagging state lives in an `ai_tags.tagging` JSON sub-key, not the `processing_status` enum), no new auth (reuses `get_current_user_id`), no RLS change, no payments, reversible writes. **Key decisions:**
- **No migration.** Bg-removal and tagging are independent pipelines; tagging populates existing first-class columns (`category`/`subcategory`/colours/`pattern`/`fabric`/`occasion_tags`/`season_tags`) + `ai_tags.tagging` (carrying its own `status`). SS-011's enum-extension directive is satisfied by *not* touching `processing_status` at all. Client-ready = `processing_status='bg_removed'` AND `ai_tags.tagging.status='tagged'`.
- New `IVisionProvider` port + `GeminiVisionAdapter` (Gemini 1.5 Flash, `response_mime_type='application/json'`, India 21-value taxonomy), mirroring SS-006/SS-011's port shape; adapter never raises. Category/occasion validated strictly (real DB enums); pattern/fabric kept free `str` (DB is `TEXT`) so one odd value can't nuke a result.
- `POST /wardrobe/tag` added to SS-011's existing `wardrobe.py` router; only ever `UPDATE`s (`404` if row absent — honours `BL-041`, guards the `BL-029` silent-0-row class). Tags `original.jpg` (decoupled from bg-removal). 202 + Realtime, heavy work in `BackgroundTasks`.
- Caching in Upstash (`tag:{md5}`, 30-day TTL, fails **open**) + `ai_tags.tagging`; in-process `GeminiRateLimiter` (15 RPM, queues not drops). Both flagged single-instance-only (compounds `BL-037`).
- **BL-044 resolved**: prompt-based `content_flag` on the same Gemini pass (cheapest place); enforcement/takedown deferred (`BL-061`).
- **BL-053 resolved**: `update_tagging_result` read-merge-writes under `ai_tags.tagging`, preserving `bg_removal`, with a dedicated non-clobber test.
- Extending `IWardrobeRepository` with `update_tagging_result` (abstractmethod) requires adding a no-op stub to SS-011's two `_FakeRepository` fakes — a green-locally/red-in-CI trap called out for Developer.

**Blockers/notes for Developer:**

## Architect — Amendment 1 — 2026-07-25 (post-live-research, orchestrator + user-approved)

Orchestrator did the deep live web-research the user asked for; two first-pass core assumptions turned out **dead, not just unverified**. Design doc amended in place (sections tagged **(amended A1)**); all four changes user-confirmed. Pointer-style — full detail in `docs/tickets/SS-012-design.md`'s Amendment-1 banner + tagged sections.

1. **Model + SDK are shut down.** `gemini-1.5-flash` retired 2025-09-29; `google-generativeai==0.8.6` (the old SDK) support ended 2025-11-30 (Google's own repo says "deprecated"). → switched to model **`gemini-3.5-flash-lite`** via the **`google-genai`** SDK. `requirements.txt` now changes (add `google-genai`, remove `google-generativeai` + `google-ai-generativelanguage` — grep-confirmed both appear *only* in `requirements.txt`, nothing imports them). **Still no DB migration.** First-pass "<3s"/model notes and the "no new dependencies" claim are superseded.
2. **Explicit `asyncio.wait_for` timeout + bounded retry (503/transient only, not 400/safety) with backoff** added to the adapter — the SDK's own `HttpOptions.timeout` is confirmed unreliable, and a partial call bills input tokens. Added a short-TTL Upstash **in-flight marker** (`tag_inflight:{hash}`) so a duplicate/retried `/wardrobe/tag` for the same image doesn't re-charge Gemini. Residual (a post-TTL retry still re-calls) documented, accepted for MVP.

Added a `contains_person: bool` moderation field distinct from `content_flag`, wired through model/prompt/`ai_tags.tagging.moderation`/tests.
4. **Concurrent `ai_tags` read-merge-write race** (tag-vs-tag, or tag-vs-`bg_removal`) now an explicit Edge case — accept-and-reduce (in-flight marker), durable `jsonb_set`/RPC fix deferred to keep migration-free → new Active **`BL-066`** (sibling of `BL-036`).

**Risk: high — reaffirmed and strengthened** (dead-model correction + free-tier privacy/DPDP precondition are exactly the pre-build one-way-door class the full lane exists to catch).

**Deviation from the design doc's own file list (flagged, not silently improvised):** the design's "Files to create/modify" section names only one new `IWardrobeRepository` abstractmethod (`update_tagging_result`), but its own Endpoint-contract section requires a *synchronous pre-dispatch existence check* ("SELECT id on the RLS-scoped client... before dispatching") that can't be done through `update_tagging_result` (which only runs inside the background task, after the `202`/`404` decision must already be made) without an inline Supabase call in the router — which the hexagonal pattern forbids. Minimal, hexagonal-consistent, and directly implements the doc's own literal text — not a divergence from anything the doc says explicitly, just a gap between two of its own sections.

**Key implementation notes:**
- `GeminiRateLimiter` is built as a **module-level singleton** in `routers/wardrobe.py` (`_gemini_rate_limiter`), not a fresh `Depends()`-per-request instance — its in-process sliding-window state must persist across requests to mean anything (unlike `TagCache`/`CircuitBreaker`/`DailyRateLimiter`, whose state lives in Upstash, so a fresh wrapper per request is harmless for those). Still overridable via `dependency_overrides` for tests.
- `update_tagging_result(tag_columns: dict | None, tagging_tags: dict)` — `tag_columns=None` on a failed/timed-out tag means **zero** first-class columns are included in the `UPDATE` payload (verified by a dedicated repository test), literally matching "no columns written" on failure, while `ai_tags.tagging` is always written via the same read-merge-write `update_bg_removal_result` already established (non-clobber verified for both the repository layer and, via a merge-simulating fake, the service layer).
- `contains_person` and `content_flag` are both **required** (no default) on `GarmentTags` — an incomplete/malformed Gemini response fails Pydantic validation (→ `success=False` → `status='failed'`) rather than silently defaulting a moderation signal to a safe-looking value.
- `season_tags` uses a lenient `field_validator(mode="before")` that drops unknown values instead of failing (free `TEXT[]`); `occasion_tags`/`category` have no such leniency (real DB enums) — mirrors the design's risk-weighting exactly.
