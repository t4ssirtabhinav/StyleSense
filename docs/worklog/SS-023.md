### Architect — done (2026-08-07)

**Verdict:** `Risk: high` — confirmed, reinforced. Full lane, every gate stays. Developer must not start until Open Questions #1–#3 are explicitly answered by the user.

**Design doc:** [`docs/tickets/SS-023-design.md`](../tickets/SS-023-design.md).

**Key decisions:**
- **Corrected the ticket's central premise:** `outfits` is *not* a new table. It has existed since `001_initial.sql:80-94` with RLS, a `user_owns_outfits` FOR ALL policy, `occasion` already TEXT + normalisation trigger (`008`), and three dependent FKs. SS-023 is its **first writer**, not its creator. Migration `020` is therefore additive hardening (provenance columns, `items_snapshot`, `NOT NULL` on `user_id`, CHECKs, a partial unique index for idempotent saves), safe only under an empirically-verified `count(*) = 0` precondition.
- **Accept/reject cannot be a client-only Supabase write.** `suggestion_outcomes` (SS-033) has no INSERT policy for any client role by deliberate design, so the swipe requires a new backend endpoint `POST /outfit-suggestions/outcome`. Designed with `(session_id, rank)` as the join key onto `suggestion_impressions`.
- **Found the highest-risk line in the ticket:** `SupabaseSuggestionLogRepository` is `service_role` and bypasses RLS, so `find_impression` will return *any* user's row. The caller-vs-impression `user_id` comparison is the only thing preventing a cross-tenant write primitive into the personalisation corpus. Specified as a 404 (not 403 — no enumeration oracle) and made the single most important test.
- **Rejected** mirroring SS-033's `DROP POLICY` move on `outfits`: it's user-authored content, not accounting data; keeping FOR ALL avoids a one-way RLS change for no security gain. Backend writes `outfits` JWT-scoped, per CLAUDE.md.
- **Regenerate:** SS-020 has no reachable cache-bypass/pool knob (effort tier is server-resolved, the narration cache is shape-keyed, novelty is item-level and 30-day-windowed). Mechanism is a new additive `exclude_fingerprints` request field → additive `EngineV2.generate_portfolio` kwarg → filter before MMR.
- **SS-020's response shape is insufficient for this UI** — no `session_id`, `rank`, or `outfit_fingerprint`. Additive-only widening specified.
- **No new `components/ui/` primitive** (SS-008's kit covers every visual element; the swipe is domain behaviour). Occasion grid is registry-driven, not `OCCASION_PILLS`.
- **BL-120 closed on a clear semantic line:** swipe right = `saved` (no wear row); a separate explicit "Wore this today" writes `wardrobe_item_wears` with `outfit_id` + `occasion_key`. Cleanly separable if scope is cut.

**Deviations from the design, flagged explicitly:**
- **No real drag/swipe gesture was implemented.** `OutfitCardDeck`/`OutfitCard` ship ONLY the accessible accept/reject `IconButton` pair — the design's own web-first mitigation ("every swipe action must also be reachable from a plain accessible Button... doubles as the guarantee AC #2 is satisfiable even if the gesture layer degrades") is what actually ships, not an additional `react-native-gesture-handler` drag layer on top of it. AC #2 ("swipe right saves outfit; swipe left dismisses") is satisfied functionally, not literally via a drag gesture. Cut for time; `BL-142` (already logged by the Architect pass, "web swipe-gesture unverifiable by RNTL") should be read as "not built" as much as "not verified" until a follow-up adds the actual gesture on top of this working button-based interaction.
- **`ImpressionRef` gained a doc-internal `occasion: str | None` field** not in the design's own dataclass sketch (§3) — required because `outfits.occasion` must come from "the impression's own session row" (§7) but nothing else on the documented dataclass carries that value. Same "doc-internal gap-fill" posture as `IWardrobeRepository.item_exists`'s established precedent; populated via a `suggestion_impressions → suggestion_sessions` embedded PostgREST select.
- **`already_saved` doubles as the wear-idempotency signal** for `outcome_type='worn'` (true when either the outfit row already existed OR today's wear was already logged) — the design's `RecordOutcomeResponse` has no dedicated field for "already logged for today" and adding one would diverge from the fixed §1 contract; documented in `outfit_outcome_service.py`.
- Found and left alone (out of scope): `mobile/types/supabase.ts` was already missing `suggestion_narration_cache`/`purge_suggestion_narration_cache` (SS-020's migration `019`, never regenerated) — only `outfits` was touched here since that's what `020` changed.
