## Developer — 2026-07-24

**Verdict: done**, with one design-doc deviation the design itself anticipated and instructed to flag back (see below) — implementation matches the design's own fallback plan, not an improvisation.

**Live R2 verification (real credentials now in root `.env`, previously blocked per Open Questions §1):** wrote a throwaway Node script (scratchpad, not committed) using `@aws-sdk/client-s3`/`@aws-sdk/s3-presigned-post`/`@aws-sdk/s3-request-presigner` against the real `stylesense-media` bucket, referencing env vars by name only (never printed secret values), cleaning up every test object it wrote.
- `HeadBucketCommand` — succeeds: credentials authenticate, bucket exists.
- `createPresignedPost` (S3-compatible POST policy, the design's amended plan) — **R2 rejects it entirely**: `501 NotImplemented: "Presigned post requests are not yet implemented"`. Overturns the design's `[trained-knowledge, not verified]` assumption that R2 supports presigned POST the way it supports presigned PUT.
- Per the design's own documented fallback, reverted to a presigned **PUT**. Second live finding while implementing that fallback: a plain pinned `ContentType` on `PutObjectCommand` is **not enforced** by R2 against the actual request (a mismatched `Content-Type` header still returned `200`) unless `content-type` is forced into the *signed* headers via `getSignedUrl`'s `signableHeaders` option — with that, a mismatched header correctly fails R2's own signature check (`403 SignatureDoesNotMatch`, verified live). Implemented with `signableHeaders`.
- No PUT-based equivalent exists for `content-length-range` — server-side max-upload-size enforcement stays an open gap (client-side compression is the only guard). Logged as `BL-051` (new row) rather than silently dropped.
- `npm:@aws-sdk/client-s3` / `npm:@aws-sdk/s3-request-presigner` resolution inside the actual Supabase Edge Runtime remains **unverified this session** — no `deno` binary available in this sandbox (checked: not on PATH, no `.deno/bin`). Written with `npm:` first per the design's instruction, esm.sh fallback noted in a code comment if it doesn't resolve at deploy time.

**Key implementation decisions:**
- `supabase/functions/get-upload-url/index.ts` exports a `handleRequest(req, deps)` seam (dependency-injected supabase/S3 clients) purely so `index.test.ts` can substitute fakes — Deno has no `jest.mock()`-style import interception. Production path (`Deno.serve`) always uses the real defaults.
- Free-tier count query now runs unconditionally (not skipped for premium) so `existingItemCount` can feed the mobile FIRST_ITEM_ADDED funnel step for every tier; only the *blocking* (403) is skipped for premium — reconciles an apparent tension between the design's Concrete Values prose ("as part of every request") and Test Plan item 5's "skips entirely" wording in favour of the more specific/executable behavior test 5 actually needs (premium never blocked at 50+), without contradicting it.
- `wardrobe.queries.ts`'s retry loop keeps independent counters for expired-URL (403, max 2 extra retries, same itemId re-signed) vs. generic network/server failures (max 3 total attempts, exponential backoff 1s/2s capped 8s) per the design's Edge Cases; `Sentry.captureException(error, { tags: { feature: 'wardrobe_upload' } })` fires only on retries-exhausted or the non-retryable `invalid_file`/`wardrobe_limit_reached` paths, never on a 403-then-succeeded retry.

**Critical implementation details verified:**

- **R2 presigned POST → PUT fallback (design amendment, live-verified):** `createPresignedPost` live-tested against real R2 credentials (2026-07-24) returned `501 NotImplemented`. Fallback to presigned `PUT` with `signableHeaders: new Set(['content-type'])` (index.ts:183) confirmed live — a mismatched `Content-Type` header now correctly fails with `403 SignatureDoesNotMatch` (previously R2 ignored a plain pinned `ContentType` and accepted any header). Size-enforcement gap (design's POST policy would have had `content-length-range`) has no PUT equivalent; logged as `BL-051`, not silently dropped.

- **Analytics wiring (post-review amendment #2, SS-009 merged same day):**
  - `track(ANALYTICS_EVENTS.ITEM_UPLOADED, { source })` fires exactly once on every successful upload (queries.ts:149; queries test 187–215 verifies).
  - `track(ANALYTICS_EVENTS.FIRST_ITEM_ADDED)` fires additionally when pre-upload count was 0 (queries.ts:150–152; queries test 217–240 verifies; queries test 242–265 verifies it does NOT fire when count ≥1).
  - `Sentry.captureException(error, { tags: { feature: 'wardrobe_upload' } })` fires only on terminal failures (retry exhausted or non-retryable 400/limit); never on 403-then-success path (queries.ts:116/129/136; queries test 83–116 verifies no capture on 403 retry success; test 118–156 verifies once on network retries exhausted; test 267–295 verifies once on 400 invalid_file).

- **Retry logic breakdown:**
  - 403 (expired URL mid-upload): up to 2 additional attempts with same itemId re-signed (queries.ts:114–126; test 83–116).
  - Generic network error: up to 3 total attempts with exponential backoff 1s→2s capped 8s (queries.ts:134–145; test 118–156).
  - 400 (policy violation, Content-Type/size mismatch): non-retryable, immediate failure (service.ts:168–178; test 235–249).
  - 403 vs 400 distinction: checked in `onload`, not just `onerror` (service.ts:157–183).
  - Hard-cap (wardrobe_limit_reached): no retry, immediate failure (queries.ts:88–94; test 158–185).

- **Compression quality ladder:** start 0.8, step down 0.1 each re-invoke to floor 0.5, checked against already-fetched blob size (service.ts:46–68; test 57–91 verifies).
