# SS-017 — Migrate Off Deprecated `expo-router` `Tabs`/`tabBar` API

Branch: `feature/SS-017-tabs-migration`

## Architect

**Verdict**: design complete, `docs/tickets/SS-017-design.md` written. `Risk: low` confirmed (unchanged from the ticket) — isolated to the tab-bar shell, no auth/payments/schema/RLS/secrets/external-facing surface, fully reversible client-side navigation-API swap.

**Key decisions**:
- **Corrected the ticket's own premise**: verified directly against the installed `expo-router@56.2.11`'s `.d.ts`/`.js` (this worktree has no `node_modules` yet, so verification was read from the sibling main-checkout's identically-versioned install, read-only) that `expo-router/js-tabs` is **not** where `TabList`/`TabTrigger`/`TabSlot` live — it's byte-identical to `expo-router/tabs` (both just alias the same deprecated render-prop `Tabs`). The real primitives live at **`expo-router/ui`**, a differently-named module. Migrating to `expo-router/ui` instead.
- Ruled out `expo-router/unstable-native-tabs` (`NativeTabs`) as an alternative — it renders genuinely-native tab bar chrome via `Icon`/`Label`/`Badge` sub-components, not arbitrary custom JSX, so it can't reproduce the dot indicator; also `unstable_`-prefixed (real adoption risk for shipped UI).
- Confirmed `expo-router/ui`'s `TabTrigger` (`asChild` + `TabTriggerSlotProps`) is exactly the customization hook needed: traced `TabTrigger.js`'s internal `handleOnPress` to confirm an `onPress` prop passed to `<TabTrigger>` fires first, and calling `event.preventDefault()` inside it blocks the subsequent tab-switch — this is how the 400ms debounce + haptics now compose (previously an imperative `if (debounced) return;` before calling `navigation.navigate`).
- Traced `GestureResponderEvent`'s type chain (`react-native/Libraries/Types/CoreEventTypes.d.ts` → `@types/react`'s `BaseSyntheticEvent`) to confirm `preventDefault()`/`isDefaultPrevented()` are real, fully-typed methods — no `any`/casting needed under `strict: true`.
- `useSafeAreaInsets()` must move into `CustomTabBar` itself (no `insets` render-prop exists under the new API) — `SafeAreaProvider` is already mounted (SS-005), so this is a like-for-like swap, no new provider needed.
- New file: `features/navigation/components/TabBarItem.tsx` (must be `forwardRef`, since Radix's `Slot` clones the child and needs a ref target) carries the per-tab icon/dot/label JSX lifted out of `CustomTabBar`'s old inline `.map()`.
- Test strategy changes materially: `CustomTabBar` can no longer be unit-tested standalone with hand-built fake props — it now needs a real navigator ancestor, so tests move to `expo-router/testing-library`'s `renderRouter()` (confirmed present/exported in this installed version).

**Blockers for Developer**: none hard-blocking. Two things to carry forward: (1) deep-link verification stays manual-only per the standing `BL-013` constraint (no device reachable from this dev machine); (2) `expo-router/ui`'s stability is inferred from its `.d.ts` lacking any `@deprecated`/`unstable_` marker, not from a changelog (no web-fetch tool available) — re-verify if `expo-router` is upgraded again.

**Backlog deltas**: **BL-032** moved Active → Resolved (this ticket) — the correct migration target is `expo-router/ui`, not `expo-router/js-tabs` as originally logged; customization surface confirmed sufficient, no visual-gap workaround needed.

## Developer

**Verdict**: implemented and tested; all checks green. One material, verified deviation from the design doc's literal composition (below) — required to make the migration actually work, not a style choice.

**Files changed**:
- `mobile/app/(tabs)/_layout.tsx` — `Tabs`/`TabSlot` from `expo-router/ui`; calls `useCustomTabBar()` (see deviation) unconditionally at the top of the component, before either early return.
- `mobile/features/navigation/components/CustomTabBar.tsx` — rewritten per design (prop-less, own `useSafeAreaInsets()`, `TabList`/`TabTrigger` + `handleTriggerPress` calling `event.preventDefault()` on the debounced path) but exported as a **hook** (`useCustomTabBar`), not a component.
- `mobile/features/navigation/components/TabBarItem.tsx` (new) — `forwardRef` sub-component per design, straight lift of the old per-tab JSX.
- `mobile/features/navigation/navigation.constants.ts` — added `href` per tab (`/`, `/wardrobe`, `/style`, `/discover`, `/profile`).
- `mobile/features/navigation/navigation.types.ts` — `TabConfig.href: Href`; `CustomTabBarProps` replaced with `TabBarItemProps = TabTriggerSlotProps & { tab: TabConfig }`.
- `mobile/__tests__/features/navigation/components/CustomTabBar.test.tsx` — full rewrite, `expo-router/testing-library`'s `renderRouter()`.
- `mobile/__tests__/app/(tabs)/_layout.test.tsx` — extended mocks (`expo-router/ui`, `react-native-safe-area-context`) for the new unconditional hook call.

**Deviation from design doc (verified, not a guess)**: the design doc's literal `<Tabs><TabSlot /><CustomTabBar /></Tabs>` composition does not work against the installed `expo-router@56.2.11`. Read `build/ui/Tabs.js`'s `parseTriggersFromChildren`: `Tabs` discovers its triggers by structurally walking its own direct JSX children (recursing only into `React.Fragment`), looking for literal `TabList`/`TabTrigger` element types — it never renders/inspects what a nested custom component will return. Confirmed via isolated repro (minimal `TabTrigger`, `TabList` wrapped in any custom component): `Tabs` throws "Couldn't find any screens for the navigator" every time, regardless of what's inside the wrapper. Fix: export `CustomTabBar.tsx`'s contents as a hook (`useCustomTabBar`), called directly in `_layout.tsx`'s own render body (unconditionally, before any early return — Rules of Hooks) so its returned `<TabList>` element is a literal, un-wrapped child of `<Tabs>`. Same file, same visuals/logic/customization surface as designed — only the export shape (hook vs. component) changed. Both `CustomTabBar.tsx` and `_layout.tsx` carry inline comments explaining this.

**Test-infra findings (all confirmed via isolated repro, documented inline in the test files)**, not covered by the design doc's Test plan:
- `@testing-library/react-native@14.x`'s `render()` is `async` (React 19), but the installed `expo-router@56.2.11`'s `renderRouter()` doesn't `await` its internal `render()` call — leaves RNTL's `screen` singleton unbound unless every `renderRouter()`/`fireEvent` call is itself wrapped in `await act(async () => { ... })`.
- RNTL's default `fireEvent.press()` event stubs `preventDefault`/`isDefaultPrevented` as two independent, stateless no-ops (not linked) — the debounce test needed a custom stateful event object (`buildPreventableEvent()`) passed as `fireEvent.press`'s second arg to actually exercise `TabTrigger`'s real `event.isDefaultPrevented()` gate.
- `react-native-screens` needs a manual jest mock (`ScreenContainer`/`Screen`/`featureFlags.experiment`) — this repo's jest config doesn't wire one up, and `expo-router/ui`'s `TabSlot` renders it directly.
- `@gorhom/bottom-sheet`'s module-load-time `Easing.out(...)` call breaks specifically when `expo-router/testing-library` is also imported in the same file (its internal `react-native-reanimated` jest-mock re-registration leaves `Easing` undefined) — worked around with a minimal, non-`requireActual`-spreading `@gorhom/bottom-sheet` mock (this file doesn't exercise bottom-sheet behavior).
- Any jest mock of `react-native-safe-area-context` (in both test files) must spread `jest.requireActual(...)` rather than fully replace the module — NativeWind's `react-native-css-interop` and React Navigation's own internals depend on other exports from it; a bare `{ useSafeAreaInsets }` replacement surfaces as an unrelated "Element type is invalid" / "Cannot read properties of undefined (reading 'displayName')" crash.

**Backlog**: no new rows — the RNTL/expo-router async-render mismatch and the `preventDefault`/`isDefaultPrevented` stub gap are `expo-router/testing-library`-specific test-authoring knowledge, fully resolved and documented inline in this ticket's test files (not a deferred blocker for a future ticket); nothing here needs separate tracking.
