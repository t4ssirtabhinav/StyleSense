**Key decisions:**

- **`scope` column does double duty** (visibility switch, not just a label) — `'server'` (default) is `service_role`-only; `'client_visible'` on a specific row opts that row into `authenticated` read access. Explicit per-row enumeration, never a wildcard/negation predicate — directly answers the ticket's own "an internal budget accidentally exposed" edge case. Six columns only, exactly the AC's literal list.
- **`updated_by` is nullable with no default**, not defaulted to a filler string — a fake default a writer never overrides would be worse than an honest gap (indistinguishable from a real identity). `updated_at` IS enforced via a `BEFORE UPDATE` trigger regardless of what the writer sets.
- **Single typed accessor (`AppConfigService`), snapshot-based.** `snapshot()` (async, TTL-cached, never raises, falls back to last-good-or-empty on repository failure) + `read(snapshot, spec)` (pure, no I/O, per-key Pydantic validation, malformed→default+ERROR log, missing→default+INFO log). A caller takes exactly one snapshot per request/task and reads every value from it — this is what satisfies "one request, one consistent config view." Cache TTL is itself a config key (`config_cache_ttl_seconds`), self-referentially adopted after each successful fetch, with a two-layer defense against a bad value (shape failure → coded default; shape-valid-but-extreme number → numeric clamp `[5, 3600]`s).
- **Config truly never touches boot** — the module-scope singleton (`app_config_service`) is constructed with zero I/O, and nothing in `main.py` or any router imports `services/app_config.py` yet (no consumer wired). Stronger than graceful degradation: there's no coupling to break.
- **`AppConfigRepository` is the first `adapters/` class in this repo to deliberately use `service_role`** — every other repository here is documented "never service_role, scope to caller JWT" for per-user data; `app_config` isn't user data, so that rule doesn't apply, but the deviation is called out explicitly (design §3.4) rather than silently introduced.
- **Two demo-only seed keys, no real consumer wired**: `config_cache_ttl_seconds` (mechanism-intrinsic) and `gemini_quota_ceiling_rpm` (`rpm=15`, matching `GeminiRateLimiter`'s current hardcoded value exactly, so a future consumer reading it changes nothing until deliberately updated). Per the ticket's own Status note, `backend/services/gemini_rate_limiter.py` is untouched — the mechanism exists, the constant doesn't move. No model-routing/cost-budget/pre-filter-threshold keys invented (explicitly SS-027/028/029's job).
- **Two mechanisms, kept separate as specified.** PostHog feature flags wired on mobile (`lib/featureFlags.ts`, sharing `lib/analytics.ts`'s existing singleton client via one new `getAnalyticsClient()` export — never a second `PostHog` instance) and backend (`services/feature_flags.py`, first-ever backend PostHog usage in this repo — `[trained-knowledge, unverified against the actually-installed package]`, flagged loudly for the Developer to confirm before shipping). One typed placeholder flag key (`paywall_copy_variant`) on both sides; the flag itself doesn't exist in the PostHog dashboard yet (same class of gap as `BL-047`/`BL-048`).
- **`backend/tests/conftest.py` needs one new line** (`SUPABASE_SERVICE_ROLE_KEY` in the baseline env fixture) — caught by re-reading that file's own documented "local-passes-CI-fails" gap before it could repeat for this ticket's new adapter.

**One test-authoring correction, not a design deviation:** `AppConfigService`'s self-referential-TTL mechanism (design §3.5) adopts `config_cache_ttl_seconds`'s *own* freshly-read value after every successful fetch, including the first — so a test/script that sets `initial_ttl_seconds=N` but leaves the seeded `config_cache_ttl_seconds` row at its default (60s) silently gets a 60s effective TTL after the first snapshot, not `N`. Caught this via the manual live-verification script (`ss026_verify_config_live_reload.py`) failing check 2c on the first run; fixed by having the script also pin the DB's `config_cache_ttl_seconds` row to `MIN_CACHE_TTL_SECONDS` (5s, the `_clamp_ttl` floor — a smaller value would silently clamp back up to this same number) for the duration of the demo, restoring it in a `finally`. One unit test (`test_supabase_unreachable_subsequent_call_falls_back_to_last_good_marked_stale`) had the same gap and was fixed the same way (seed `config_cache_ttl_seconds` in the fake repo's values). Mechanism behaves exactly as designed; only the test/script setup needed to account for it.

**Migration state:** `010_app_config.sql` applied to the live `mefpfykuinasgkpfhmzk` project via `supabase db push`; `supabase migration list` confirms Local/Remote/Time all show `010`. Purely additive, zero existing data touched, matching design §9's risk assessment.
