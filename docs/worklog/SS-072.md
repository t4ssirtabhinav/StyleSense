### Architect — 2026-08-16 (Opus, full lane)

**Verdict: `Risk: high` (confirmed, not lowered).** Design doc: `docs/tickets/SS-072-design.md`. Tier `standard`.

**Key decisions.** Three deviations from the raw ticket's Description (all ACs still satisfied; the Description predates SS-071 shipping):
1. **No `app/(auth)/email-auth.tsx` route.** `EmailAuthForm` registers as `AUTH_METHODS[1].Component` and renders under `/login`, which is already in `_layout.tsx`'s `GUARDED_ROUTES` — so AC #2/#6 routing holds by construction. A new route would sit *outside* that set and re-create `BL-168` in the ticket right after the one that fixed it.
2. **`AuthMethodChooser` reshaped**: primary method (`AUTH_METHODS[0]`) renders inline by default with secondary methods as buttons below, instead of a two-button menu. Two reasons: a menu has no "default", failing AC #1's "phone remains visually primary/default"; and it would break `login.test.tsx` (SS-003's 6-case suite, which resolves the *real* registry and asserts the phone form on a bare mount — the file SS-071 worked hard to keep unmodified). Cost: rewriting SS-071's own `login.registry.test.tsx`, equivalent coverage.
3. **`components/ui/Input.tsx` gains additive `email` + `password` variants.** Ground-check: `TextVariantInput` forwards no `secureTextEntry`/`keyboardType`/`autoCapitalize` and hardcodes `accessibilityLabel="Text input"` — a password field is literally unrenderable today, and the missing `autoCapitalize="none"` would manufacture the `User@x.com` duplicates this ticket exists to reject.

**Migration `021` confirmed as the next number** (`020` is the highest, no gaps). Defence is three layers, only one new: client error mapping (UX) → `021`'s `lower(email)` pre-check + `RAISE EXCEPTION 'stylesense_email_conflict'` (clean message, **not** atomic) → the pre-existing `email UNIQUE` from `001` (atomic correctness backstop). Stated plainly that `021` does not close the race — layer 3 already made it safe. Phone path untouched via `NEW.email IS NOT NULL` short-circuit; AC #5 still requires a live before/after check. Rollback = re-run `002`'s function body verbatim.

**Verified against the installed SDK** (`@supabase/auth-js`, not memory) — this closed the ticket's largest unknown: the duplicate-signup **obfuscation only happens when both Confirm-email and Confirm-phone are enabled**; with Confirm-email off, `signUp` returns a real `User already registered` error, so **AC #3's specific copy is achievable and needs no downward reconciliation**. Also confirmed `session: null` iff Confirm-email on, and the stable `error.code` union (`user_already_exists`, `invalid_credentials`, `weak_password`, …) to branch on instead of message strings.

**Blockers before Developer: none** — no vendor, no provisioning, work can start immediately. Three live-verification tasks that can't be done from the repo (no Bash/MCP this pass): read+record the Confirm-email setting before flipping it off; read+record the password minimum and HIBP availability (`BL-183`); observe whether GoTrue propagates the trigger's exception token to the client (design is correct under either answer). One task to run **first**: `login.test.tsx` now transitively imports `hooks/useAnalytics` — if it throws at load, the only sanctioned repair is adding a mock line, never an assertion change.
