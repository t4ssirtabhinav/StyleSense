Key implementation decision not spelled out verbatim in the design doc: `StylingRulesOverride`'s per-field leniency is implemented as a `parse_lenient(raw: dict) -> StylingRulesOverride` classmethod (uses `pydantic.TypeAdapter` per field, catching `ValidationError` and dropping to `None`) rather than a `field_validator`-per-field approach — a bare `mode="before"` validator that just returns the value unchanged does not actually achieve "wrong-typed value dropped to `None`" (Pydantic still raises during normal field coercion), so `parse_lenient` is the mechanism that makes `test_malformed_styling_rules_degrades_without_raising` true. `_resolve_styling_rules` calls `parse_lenient` then layers successfully-parsed fields over the kind default exactly as specified.

**AC Coverage (7/7 met):**
1. **Zero network calls & deterministic:** Code inspection confirms no network imports (`requests`/`httpx`/`supabase`), only stdlib `colorsys` for colour conversion. `as_of` and `season` are required caller-supplied parameters (never `date.today()`). Tests `test_deterministic_same_input_same_output` (deep-copy identical inputs → identical `model_dump()`) and `test_as_of_is_never_read_from_system_clock` (different `as_of` → different results) confirm determinism is real, not theoretical. ✓

2. **Item IDs never hallucinated:** `generate_candidates` builds candidates from `eligible` wardrobe list via `_group_by_slot`, `_rank_within_slot`, and `_build_base_combinations` — all operations preserve only real input IDs structurally. Test `test_all_candidate_item_ids_are_subset_of_input_ids` verifies across 20–80-item wardrobes. Property test `test_property_never_hallucinates_ids_across_random_wardrobes` with hypothesis (30 examples). ✓

3. **Occasion rules from `styling_rules`, not hardcoded:** `_resolve_styling_rules` parses `occasion.styling_rules` via `StylingRulesOverride.parse_lenient`, falls back to `DEFAULT_STYLING_RULES_BY_KIND[occasion.kind]` on empty/malformed. Test `test_occasion_with_empty_styling_rules_uses_kind_defaults` confirms all 9 kinds produce valid candidates with empty rules. Test `test_malformed_styling_rules_degrades_without_raising` confirms `{"required_base": 12345}` degradation. ✓

4. **`wedding_guest` white exclusion (code-level, unconditional):** `HARD_EXCLUDED_COLOR_FAMILIES = {"wedding_guest": frozenset({"white"})}` is applied at line 93-99 of engine.py regardless of `styling_rules` content. `_is_near_white` uses HSV thresholds (`value >= 0.92 and saturation <= 0.12`). Test `test_wedding_guest_excludes_all_white_hero_candidates` creates all-white wardrobe → 0 candidates (strongest proof). Test `test_other_ceremony_occasion_key_still_allows_white` confirms guard is keyed by exact `occasion.key`, not by `kind`. Property test `test_property_wedding_guest_white_rule_holds_across_random_colors` with hypothesis (30 examples of near-white colours). ✓

5. **Combinatorics bounded (1–500+ items):** `MAX_ITEMS_PER_SLOT=8` caps ranking before combination. Worst case: 8 one_piece + 64 (8×8) top/bottom pairs = 72 bases, each with ≤2 additional items (footwear + accessory) = ~150 assembled candidates regardless of input size. Test `test_large_wardrobe_bounded_time_and_output_size` creates 500-item wardrobe, runs to completion in **0.05s** (well under 2s assertion). ✓

6. **`limited_options` flag & gap handling:** `limited_options = len(scored) < 3` (line 184). Candidates never padded/invented — returned as-is with gap flags (e.g., `["missing_footwear"]`).
