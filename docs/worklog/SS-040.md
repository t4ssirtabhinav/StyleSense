# SS-040 — Item Lifecycle & Cost-Per-Wear Schema (trimmed)

Branch: `feature/SS-040-item-lifecycle-schema`

Promoted 2026-08-20 from `docs/competitive/07-EPICS-AND-TICKETS.md`'s portfolio-scope rewrite — second ticket of the trimmed post-Google-Wardrobe plan (after `SS-044`, merged). Adds the small set of `wardrobe_items` columns genuinely missing (`do_not_style`, `is_archived`, `condition`, `custom_tags`, `render_transform`) and wires `do_not_style`/`is_archived` into `engine_v2_eligibility`'s exclusion path — an unwired flag is worthless.

### Architect — 2026-08-20 (Opus, tier `standard`)

**Verdict: designed, ready for Developer. `Risk: high` confirmed (not inherited).** Design doc: `docs/tickets/SS-040-design.md`.

Ground-check (all verified against the repo, not the raw ticket's note):
- The raw ticket's schema claim **holds** — `brand`/`purchase_price`/`purchase_date`/`is_favourite`/generated `cost_per_wear` all exist (`001_initial.sql:58-71`), and **no** migration 002→022 added any of the five target columns. Only column-shape changes since 001 are `005` (`processing_status`, `category` NOT NULL dropped), `006` (composite UNIQUE), `008` (`occasion_tags`→`TEXT[]`). Next free migration is **`023`**.
- RLS needs no change: `user_owns_wardrobe ... FOR ALL USING (auth.uid() = user_id)` (`001_initial.sql:164-165`) is row-level, so new columns are covered by the existing policy.
- **The raw ticket under-specified the wiring by two files.** `WardrobeRepository.get_items_for_styling` (`wardrobe_repository.py:185-188`) uses an **explicit select list**, and the port docstring (`adapters/interfaces.py:602-613`) enumerates it verbatim. Adding fields to `WardrobeItemInput` alone leaves every item at `do_not_style=False` forever — a silent no-op that all unit tests would still pass. Hence a mandatory repository select-list test.

Key design decisions (detail in the doc): lifecycle filter runs **first**, before the missing-category/colour count, so an archived untagged item isn't double-counted; single `not (do_not_style or is_archived)` predicate so both-flags counts once; lifecycle exclusions are **never** relaxed by SS-022's relax-if-empty weather guardrail (user instruction beats engine inference); new `excluded_lifecycle` counter stops at `EligibilityResult` and does **not** widen `GapReport`/the API. Booleans ship `NOT NULL DEFAULT false` (not bare nullable) because a NULL would fail pydantic validation and `_fetch_wardrobe` silently *drops* such rows. `render_transform` ships as bare nullable JSONB with no CHECK — SS-055 owns its shape.

Blockers for the user (none stop the Developer starting): **nothing writes these columns** — SS-040 ships a correct, tested, 100% live-inert read path (`BL-194`); `supabase db diff --linked` (AC #7) can only be an operator-run manual check while `BL-028`/`BL-110` are open; `condition`/`custom_tags` have no consumer at all and could be dropped from the migration at zero cost if the user prefers not to ship unconsumed columns.

Backlog: **added `BL-194`** (no writer for the lifecycle flags), **`BL-195`** (`condition` free-TEXT, no vocabulary — third `BL-064`-pattern instance), **`BL-196`** (lifecycle exclusions invisible to the user). Left Active with stated reasons: `BL-124` (this ticket adds a new UPDATE path that amplifies it — `trg_wardrobe_items_normalize_occasions` has no `WHEN` clause), `BL-075` (money-unit ambiguity, must be settled before SS-052, not by this ticket), `BL-143` (confirmed still stale; **closable by this ticket's `supabase.ts` regeneration** — Developer should regenerate the whole file and resolve it).
