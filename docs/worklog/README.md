Note the ticket's `Risk:` lane (from the design doc) in the Architect entry so a reader knows whether it ran full-lane or fast-lane.

**Wave 1.5 created — Styling Engine v2 foundation (2026-07-30):** SS-033 through SS-037 above came out of [`docs/proposals/STYLING-ENGINE-V2.md`](../proposals/STYLING-ENGINE-V2.md) (commit `a95059f`) via `/new-feature` intake, after a review of SS-027's shipped v0 engine concluded it is a correct *skeleton* and the wrong *ceiling*. Three findings drove it, each verified against the repo rather than recalled:

1. **`wardrobe_category` is still a 21-value Postgres ENUM** (`001_initial.sql:7-14`) containing **zero ethnic bottoms** — no churidar, salwar, patiala, palazzo, dhoti, pyjama or sharara. That, not the scoring formula, is why the engine can only offer *kurta with jeans*: no scoring change fixes a vocabulary that cannot express the outfit. SS-025 already retired the sibling `occasion_type` enum; garments never got the same treatment. Sourced replacement taxonomy (web-researched, cited) is in the proposal's Appendix B, which also surfaced five modeling problems — notably that a "kurta set" is a *set* rather than a garment (`BL-109`), and that mekhela sador / mundum neriyathum are genuinely two-piece.
2. **Search breadth was capped as though it were the cost driver.** It is not — stages ①–④ are pure Python (microseconds); only LLM tokens cost money. SS-027 explores ~2% of a 200-item wardrobe's top/bottom pairs (64 of 3,000). Widening to ~5,000 fully-scored candidates and then selecting a *diverse portfolio* of 5 costs **₹0 extra**, because the LLM still sees only 5. Exhaustiveness and cost are independent; v0 conflated them.
