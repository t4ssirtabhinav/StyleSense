## Manual verification — bug found & fixed, 2026-07-26

While attempting manual verification (tapping the "Add your first item" CTA to get a real item into the grid), the user hit a pre-existing bug in SS-013's `CaptureStep.tsx` — not part of SS-014's own scope, but blocking this ticket's manual-verification gate, so fixed here rather than deferred.

**Root cause (confirmed by reading `expo-camera`'s own web source, `node_modules/expo-camera/src/ExpoCameraManager.web.ts`, plus MDN):** `getUserMedia` (camera access) requires a browser "secure context" — HTTPS, or the `localhost` exception. This is a browser platform restriction, not fixable in app code; the correct workarounds are `localhost` (not the LAN IP) on desktop, and either `npx expo start --tunnel` (HTTPS) or the native Expo Go app (not browser) on the phone.

**Real bug found and fixed:** independent of the above, `CaptureStep.tsx` gated the *entire* screen — camera preview **and** the Gallery button — behind camera permission being granted. A user who can't get camera permission (denied, or stuck on an insecure origin) had no way to reach Gallery either, even though Gallery needs no permission at all on web (`expo-image-picker`'s web adapter always auto-grants media-library permission — confirmed via its source, `ExponentImagePicker.web.ts`). Fixed: only the camera preview area is now gated on camera-permission status; the Gallery button, tip banner, and clamp-message UI always render regardless. User confirmed this fix via `AskUserQuestion` before it was made.

## Manual verification — second bug found & fixed, 2026-07-26 (CORS on get-upload-url)

After the CaptureStep fix above, gallery selection worked but the upload flow itself failed: browser console showed `Access to fetch at '.../functions/v1/get-upload-url' ... blocked by CORS policy: Response to preflight request doesn't pass access control check: It does not have HTTP ok status.` Reproduced identically on laptop (LAN IP), iPhone Safari (LAN IP), and after switching to `npx expo start --tunnel` (HTTPS) — ruling out the HTTPS/secure-context issue as the cause here, since it persisted even over HTTPS.

**Root cause, confirmed against Supabase's own docs and a matching community report** ([supabase.com/docs/guides/functions/cors](https://supabase.com/docs/guides/functions/cors), [github.com/orgs/supabase/discussions/38832](https://github.com/orgs/supabase/discussions/38832)): `supabase/config.toml`'s `[functions.get-upload-url]` had `verify_jwt = true` (set by SS-010). This is a platform-level gate that intercepts *every* request — including the browser's automatic CORS preflight `OPTIONS` request — and rejects anything without a valid `Authorization` header. Preflight `OPTIONS` requests never carry the app's headers by spec, so the platform rejected it with 401 before `index.ts`'s own code ever ran; the browser then blocked the real request as a CORS failure. This bug has existed since SS-010 shipped (2026-07-24) — never caught because SS-010's own live verification called R2 directly from a Node script (server-side, no browser/CORS involved) and its Deno tests were never executed locally (`BL-042`, no Deno binary in this sandbox) — this is the first real browser-based exercise of this endpoint.

**Fix (user confirmed via explicit sign-off before applying, given the auth-adjacent + live-external-service nature):**
1. `supabase/config.toml` — `verify_jwt` flipped `true` → `false` for `get-upload-url`. Safe: the function already independently re-verifies the caller's JWT itself via `supabase.auth.getUser()` (`index.ts`, pre-existing) — this was always the real security boundary; the platform gate was redundant defense-in-depth that happened to be incompatible with CORS. This is Supabase's own documented recommended pattern for a CORS-enabled authenticated function.
2. `supabase/functions/get-upload-url/index.ts` — added an `OPTIONS` short-circuit (returns 204 + CORS headers before any auth check) and `Access-Control-Allow-Origin: *`/`-Headers`/`-Methods` on every response (success and error paths). Wildcard origin is safe here since this is a Bearer-token API with no cookies — nothing ambient to leak.
3. `supabase/functions/get-upload-url/index.test.ts` — added 2 Deno test cases (OPTIONS short-circuits before touching auth/deps; both success and 401 responses carry CORS headers). Not locally executable (same `BL-042` gap), written to spec.
4. Redeployed via `supabase functions deploy get-upload-url --project-ref mefpfykuinasgkpfhmzk` (CLI already linked to the live project).

**Live-verified post-deploy (not just "should work"):**
- `curl -X OPTIONS ...` → `204`, `access-control-allow-origin: *`, `access-control-allow-headers: authorization, content-type`, `access-control-allow-methods: POST, OPTIONS`.
- `curl -X POST ...` with no Authorization header → still `401 {"code":"unauthorized","message":"Missing Authorization header."}` — confirms the auth boundary is unweakened, only the CORS-breaking platform gate was removed.

**Backlog:** no new row (fixed same-session, not deferred). Full corresponding entry also appended to `docs/worklog/SS-010.md` ("Post-ship fix — 2026-07-26") since the changed code is SS-010's, not SS-014's, for anyone auditing that ticket's history later.

**Round 2 (same incident, same fix session):** after the above fix, a *different* CORS error appeared: `Request header field x-client-info is not allowed by Access-Control-Allow-Headers in preflight response` — reproduced on both `localhost` and the LAN IP, and (separately reported) persisted even over `npx expo start --tunnel`'s HTTPS URL, confirming it's unrelated to the earlier secure-context issue. Cause: the mobile client actually calls this function via `supabase.functions.invoke()` (`wardrobe.service.ts`'s `requestUploadUrl`), not a raw `fetch` — the installed supabase-js SDK automatically attaches `apikey`/`x-client-info`/`x-retry-count` headers the first CORS fix's hand-picked allowlist (`authorization, content-type`) didn't cover. Fixed by copying the exact header list verbatim from the installed SDK's own canonical `corsHeaders` export (`mobile/node_modules/@supabase/supabase-js/src/cors.ts`) instead of hand-picking headers a second time — `authorization, x-client-info, apikey, content-type, x-retry-count` — and widening `Access-Control-Allow-Methods` to the SDK's full set. Redeployed; live-verified via `curl` OPTIONS preflight — response now echoes all 5 required headers.

## Manual verification — fourth bug found & fixed, 2026-07-27 (R2 secrets never provisioned on the deployed Edge Function)

With CORS resolved, the real `POST /functions/v1/get-upload-url` finally reached the function body and returned **500** `{"code":"internal_error","message":"Resolved credential object is not valid"}` (`sb-error-code: EDGE_FUNCTION_ERROR`).

**Root cause (confirmed, not inferred):** ran `supabase secrets list --project-ref mefpfykuinasgkpfhmzk` — the project had **no `CLOUDFLARE_R2_*` secrets at all** (only `ANTHROPIC_API_KEY`, `RESEND_API_KEY`, `SLACK_WEBHOOK_URL`, and the auto-managed `SUPABASE_*` set). `index.ts`'s `buildR2Client()` reads `CLOUDFLARE_R2_ACCOUNT_ID`/`ACCESS_KEY`/`SECRET_KEY` via `Deno.env.get(...)!` — all `undefined` in the deployed environment, so the AWS SDK's credential resolver rejected the object with exactly that message. All four values *were* present in the local root `.env`, which is a separate environment the deployed function cannot see.

**Why SS-010's QA never caught this:** its "live R2 verification" (see `docs/worklog/SS-010.md`'s Developer entry) ran a throwaway **Node script on the dev machine**, reading the local `.env` directly. That correctly proved the credentials themselves are valid and that R2 rejects presigned POST — but it never exercised the deployed Edge Function's own environment, where the credentials simply didn't exist. Same blind spot class as the CORS bug above: both live only in the deployed-function/browser path that no test in this repo covers (`BL-042`).

**Fix:** pushed the four `CLOUDFLARE_R2_*` values from local `.env` to the project's secret store via `supabase secrets set --env-file <temp>` — scoped to only those four keys (not the whole `.env`, which holds unrelated provider credentials), staged through a scratchpad file that was deleted immediately after, with no secret values printed to the console at any point. Verified post-set: all four now appear in `supabase secrets list`. Function redeployed to force a cold start onto the new environment.

**Verification status — partial, stated honestly:** the four secrets are confirmed *present* in the deployed environment, and the function redeployed cleanly. The actual end-to-end presigned-PUT path could **not** be verified from here — the function 401s before reaching the R2 code without a real user JWT, and minting one wasn't appropriate. Final confirmation requires the user's own retry from the app. Not claiming this as passing until that happens.

**Backlog:** no new row for the fix itself, but this is the second production-only defect in two days that this repo's test suite structurally cannot catch — see the new `BL-069` row (Active, tag `ci`) covering the missing deployed-Edge-Function smoke check, which compounds `BL-042`.

## Manual verification — fifth and sixth bugs, 2026-07-27 (R2 bucket CORS + AWS SDK flexible-checksum)

With the Edge Function finally minting URLs, the browser's `PUT` **to R2 itself** failed: preflight `OPTIONS` → `403`, `No 'Access-Control-Allow-Origin' header is present`. Two separate defects were identified from that one signed URL.

**Bug 5 — R2 bucket has no CORS policy.** Browser uploads go straight from the browser to R2 (`wardrobe.service.ts`'s `uploadToR2WithProgress`), so R2 must answer the preflight itself; the Edge Function's CORS headers are irrelevant to this hop. R2 buckets have no CORS policy by default. Native builds are unaffected (CORS is browser-only), which is precisely why this survived from SS-010 — SS-010's verification was a Node script, and SS-013's QA never ran a real browser upload either.
- Added `infra/r2-cors.json` (version-controlled policy), `infra/apply-r2-cors.mjs` (applies it via the S3-compatible `PutBucketCors` API — [VERIFIED 2026-07-27, developers.cloudflare.com/r2/api/s3/api/ lists `PutBucketCors`/`GetBucketCors` as implemented], so no Cloudflare account token is needed, only R2 keys), and `infra/README.md` explaining why this exists and the wildcard-origin tradeoff.
- **Not yet applied — blocked on credentials.** Running the script returned `AccessDenied`: the `CLOUDFLARE_R2_ACCESS_KEY` in `.env` is object-scoped, and `PutBucketCors` needs an **Admin Read & Write** R2 token. Handed to the user to apply via the Cloudflare dashboard (R2 → bucket → Settings → CORS Policy) or with an admin-scoped token. This is the one remaining blocker on the upload flow.
- Wildcard origin logged as `BL-070` to tighten before launch.

**Bug 6 — AWS SDK flexible checksums corrupt the presigned PUT (latent; would have blocked the very next attempt).** The signed URL contained `x-amz-checksum-crc32=AAAAAA%3D%3D&x-amz-sdk-checksum-algorithm=CRC32`. `AAAAAA==` is the CRC32 of **zero bytes** — the SDK computes a checksum at signing time, when `PutObjectCommand` has no `Body`, and bakes it into the signature. The browser then PUTs real bytes that cannot possibly match. Known AWS SDK v3 behaviour for presigned PUTs since ~v3.729 ([VERIFIED 2026-07-27, github.com/aws/aws-sdk-js-v3 issues #4849/#6810 — "integrity protections can be disabled by setting the config flag to `WHEN_REQUIRED`"]); the Edge Function imports `npm:@aws-sdk/client-s3` unpinned, so it silently picked this up. Fixed by adding `requestChecksumCalculation: "WHEN_REQUIRED"` to `buildR2Client()`'s `S3Client` config; redeployed. Found by reading the actual signed URL rather than waiting for it to fail, so it never cost a debug cycle of its own.

**Verification status:** the checksum fix is deployed but, like the secrets fix, cannot be end-to-end verified from here (needs a real user JWT, and the R2 CORS policy is still missing anyway). Both remain unconfirmed until the user applies the CORS policy and retries. Stated as deployed, not as working.
