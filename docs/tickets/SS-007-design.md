# SS-007 — Granular Preferences Editor (Profile → Edit Preferences) — Design

## Scope restatement

Today, Profile → "Edit Preferences" (`mobile/app/(tabs)/profile.tsx`) routes to `/onboarding`, forcing a full 4-step wizard replay just to change one field. This ticket replaces that stopgap with a dedicated, non-wizard screen (`mobile/app/edit-preferences.tsx`) that shows the 5 `style_preferences` sections — style keywords, wardrobe type, occasion priorities (cap 3), budget range, favourite colours (cap 5) — each pre-filled from the DB, each independently editable and independently saveable via its own partial-update DB write, using the exact same taxonomy sources (`onboarding.constants.ts` static lists + `useOnboardingTaxonomiesQuery`'s DB-backed reference tables) and the exact same `Badge`/colour-swatch presentation SS-004 already built. No new design-system components, no schema change, no new tables.

## Route placement — deliberate deviation from the ticket's literal suggested path

The ticket's Technical Notes suggest `app/(tabs)/profile/edit-preferences.tsx`, caveated "(exact route depends on SS-005's Profile tab structure)". Now that SS-005 has shipped, `app/(tabs)/profile.tsx` is a **flat leaf file**, not a directory — `TAB_CONFIG`'s `name: 'profile'` (`mobile/features/navigation/navigation.constants.ts`) maps directly to it. Turning that into `profile/index.tsx` + `profile/edit-preferences.tsx` would require restructuring the existing tab file and reasoning through whether the nested route inherits the `(tabs)` Tabs-navigator chrome or needs its own nested Stack/layout to hide the tab bar on the sub-screen — non-trivial surface for a ticket whose own scope note says "only a new screen composing [existing components] differently."

CLAUDE.md's own documented folder structure already has precedent for exactly this situation — a full-screen destination reached *from* a tab but not itself a tab (`outfit/[id].tsx`, `tryon/[outfitId].tsx` live top-level under `app/`, not nested inside `(tabs)`). This design follows that precedent: **`mobile/app/edit-preferences.tsx`**, route `/edit-preferences`, guarded the same way `(auth)/onboarding.tsx` guards itself (see above) since it sits outside the `(tabs)` Auth Guard's reach.

## Files to create/modify

1. **`mobile/app/edit-preferences.tsx`** (new) — the screen. Session guard (loading Card / `<Redirect href="/login">`, copied pattern from `(auth)/onboarding.tsx`), fetches `useOnboardingProgressQuery(userId)` (already exists, already returns `stylePreferences: StylePreferences | null` — no new read hook needed), fetches `useOnboardingTaxonomiesQuery()` once and passes `data`/`isLoading`/`isError`/`refetch` down to the 3 sections that need DB-backed options (style keywords, occasion priorities, colours) rather than each section re-calling the hook independently (deliberate deviation from Step2/Step3/Step4's per-step-owns-its-own-call pattern — those are pager pages that mount/unmount independently; this screen mounts all 5 sections simultaneously, so one shared call avoids 3 redundant network requests. - Static option lists: `WARDROBE_TYPES`, `BUDGET_RANGES` from `onboarding.constants.ts` — import directly, do not re-declare.
- DB-backed option lists: `useOnboardingTaxonomiesQuery()`'s `styleKeywords`/`occasionTypes`/`colourPalette` — same hook, same shapes (`TaxonomyOption`/`ColourPaletteOption`).

- Query key for invalidation: `['onboarding', 'progress', userId]` (existing literal, already used by `useSaveStep1Mutation`/`useCompleteOnboardingMutation` — new hooks must use the identical array, not a new key).

## Why plain component state, not `onboarding.store.ts`, and not a new Zustand store

Each of the 5 sections is independently editable and independently saved (per AC) — there is no cross-section shared client state to justify a store, and each section is a single, self-contained component (parent screen → one section = 1 level of prop drilling, within CLAUDE.md's "no more than 2 levels" rule). Reusing the wizard's `onboarding.store.ts` was considered and rejected: that store is explicitly reset on wizard completion (`reset()` in `handleGetStarted`) and is the *in-progress, not-yet-saved* wizard state — an open Edit Preferences draft living in the same store as an in-progress wizard run risks one clobbering the other if a user has both open across app backgrounding/foregrounding. Each section instead: (a) initializes local `useState` from its slice of `progressQuery.data?.stylePreferences` (or the static default the wizard itself uses, e.g. `undefined`/`[]`, when that field was never set), (b) enforces its own cap via the same transcribed toggle logic, (c) has its own "Save" `Button` calling its own mutation, showing that mutation's own `isPending`/`isError` — not a shared save-all action, matching the AC's "each section saves independently."

## Edge cases

Carried forward from the ticket:
- **User has never completed onboarding, reaches this screen some other way.** Decision (this design, not silently picked): **allow entry and partial editing**, do not redirect to the wizard. Rationale: the screen already handles a `stylePreferences: null` or partially-populated case gracefully (each section just renders its empty/unset state, which is a legitimate state, not a bug) — blocking entry would contradict the AC's "no stale/empty state even if the user has never touched a given section," which already anticipates partially-empty data. A `Card`/banner (`variant="flat"`, `"Finish setting up your profile for the best recommendations."` or similar) is shown above the sections when `progressQuery.data?.onboardingCompleted === false`, but every section remains editable underneath it — no gate.
- **Network failure mid-save on one section must not roll back or affect other already-saved sections.** Satisfied structurally: each section's save is its own independent `useMutation` / DB round-trip (read-current → merge → write). A failed save simply never commits that one section's patch; every other section's already-committed write is a separate, already-completed transaction and is untouched. Each section shows its own inline error + "Try again" (mirroring `Step2`/`Step3`/`Step4`'s existing `isError` → retry `Button` pattern) rather than a screen-wide error state.

New, found while designing:
- **Read-modify-write race on `style_preferences`.** `patchStylePreferences` does a read-then-write, not an atomic DB-level merge (Supabase JS's `.update()` can't express a Postgres `jsonb || jsonb` merge without an RPC/stored procedure, which would be new schema-adjacent surface out of scope here). Two of this screen's own sections saved in rapid succession (e.g. double-tapping two different "Save" buttons within the same round-trip window) could have the second write's read miss the first write's not-yet-committed patch, silently reverting it. Low real-world likelihood (each section has its own explicit Save button; a single user is unlikely to fire two saves within the ~100–300ms round-trip window) but not impossible. **Logged as BL-036 (Active, `schema` tag)** rather than silently fixed with a heavier RPC-based change — see Backlog Logging below.
- **`onboarding_completed` not previously exposed by `fetchOnboardingProgress`.** Needed for the banner decision above; adding it is a 1-column `.select()` change, not a schema change (column already exists since SS-004/BL-018).
- **`ColourSwatch` is currently a private, unexported function inside `Step4BudgetColours.tsx`.** This ticket needs the identical presentation. See Open Questions #1 for the two options (export it vs. duplicate it) — Developer should pick based on which is less invasive to `Step4BudgetColours.tsx`'s existing file.
- **Style keywords / wardrobe type / budget range have no server-side cap enforcement either** (same as onboarding — cap is client-only for occasions/colours, and style keywords/wardrobe type/budget range were never capped anywhere). Nothing in this ticket needs to change that; noting only so it isn't mistaken for a gap introduced by this design.

## Risk: low

This ticket only adds a new screen + 5 new components + new partial-update methods on an already-write-permitted column (`users.style_preferences`, JSONB, already updated by existing SS-004 code via the same authenticated Supabase client and the same RLS posture) and repoints one existing button. No migration, no RLS change, no new secrets, no payment surface, and nothing here is irreversible — a bad save is corrected by another save. The one non-trivial risk found (BL-036's read-then-write race) is a data-freshness edge case affecting only the acting user's own preference data, not a security or schema boundary, and is logged rather than silently accepted.
