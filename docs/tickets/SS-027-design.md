# SS-027 — Styling Rules Engine & Deterministic Pre-Filter — Design

## Scope restatement

SS-027 ships a pure, offline, side-effect-free Python module that turns a caller-supplied wardrobe (a list of item descriptors) plus a caller-supplied occasion context (kind, formality, and an optional `styling_rules` JSONB override from SS-025's `occasions` table) into a small, deterministic, score-ranked list of candidate outfits — each candidate referencing only real input `wardrobe_item.id` values, each carrying per-rule explanations compact enough to become the LLM's entire input for SS-028's later ranking/prose pass. The module does no DB I/O, no network I/O, and is called with all data already fetched by whoever wires it in later (explicitly out of this ticket's scope — see Open Questions). Its central design constraint, per the raw ticket's Technical Notes, is that colour/formality/completeness rules must live in exactly one place so a future prompt-builder cannot drift from the scorer by construction, not by convention.

## Files to create/modify

All new files. **Zero existing files are modified** — this ticket has no file overlap with SS-028, SS-029, or any already-shipped ticket, and ships no migration, no router, no new endpoint.

- `backend/services/styling_rules_types.py` — pure typed data contracts (Pydantic `BaseModel`s, no I/O), mirroring the existing convention (`OutfitSuggestionResult`, `GarmentTags`) rather than dataclasses, since these shapes are meant to be JSON-serialized into a future API response / LLM prompt:
  - `WardrobeItemInput` — `id: str`, `category: WardrobeCategory | None` (import the existing `Literal` from `ai.ports.interfaces`, do not redefine it), `color_primary: str | None` (hex), `color_secondary: str | None`, `pattern: str | None`, `fabric: str | None`, `occasion_tags: list[str]`, `season_tags: list[SeasonTag]` (import from `ai.ports.interfaces`, do not redefine), `wear_count: int = 0`, `last_worn_at: date | None = None`.
  - `OccasionStylingInput` — `key: str`, `kind: str` (one of the 9 `occasions.kind` CHECK values — transcribe the literal list from `supabase/migrations/007_occasions_registry.sql` line 42-44, do not re-derive it: `"everyday" | "ceremony" | "festival" | "travel" | "sport" | "professional" | "social" | "milestone" | "religious"`), `formality: int` (0-10, matches the `occasions.formality SMALLINT CHECK (formality BETWEEN 0 AND 10)` constraint), `styling_rules: dict[str, Any]` (raw JSONB as fetched — may be `{}`, may be partial, may be hand-edited garbage; never trust its shape).
  - `StylingRulesOverride` — the **documented schema** for what a non-empty `occasions.styling_rules` JSONB value means, all fields `Optional[...] = None` and validated leniently (unknown keys ignored, wrong-typed values dropped to `None` rather than raising — mirror `GarmentTags`' lenient-validator posture): `required_base: Literal["top_bottom", "one_piece", "either"] | None`, `footwear_required: bool | None`, `preferred_footwear_categories: list[str] | None`, `preferred_accessory_categories: list[str] | None`, `excluded_color_families: list[str] | None` (currently only `"white"` is a recognized family — see `styling_rules_defaults.py`), `formality_tolerance: int | None`. **This is the schema any future migration or dashboard edit to `occasions.styling_rules` must write against** — it is intentionally the only place this shape is defined.
  - `RuleScore` — `rule: str`, `score: float` (0.0-1.0), `explanation: str` (short, human-readable — this is the string a future prompt template embeds verbatim, per the "consumed twice" contract).
  - `ScoredCandidate` — `item_ids: list[str]`, `category_labels: dict[str, str]` (item id -> category, for prompt rendering without a second wardrobe lookup), `total_score: float`, `rule_scores: list[RuleScore]`, `gap_flags: list[str]` (e.g. `"missing_footwear"`, `"missing_outerwear"` — never `"missing_top_or_bottom_or_one_piece"`, since that case excludes the candidate entirely rather than flagging it).
  - `GapReport` — `excluded_missing_color_or_category: int`, `missing_slots: list[str]` (aggregate, occasion-level: which slots had zero eligible items at all, distinct from a per-candidate `gap_flags` entry).
  - `PreFilterResult` — `candidates: list[ScoredCandidate]`, `limited_options: bool`, `gap_report: GapReport`.

- `backend/services/styling_rules_defaults.py` — the single source of truth for every numeric/tunable constant this module uses. **All of the following are Architect-assigned starting values, not verified product/stylist input** — flagged once here, not per-line:
  - `CATEGORY_SLOT: dict[WardrobeCategory, str]` — maps all 21 `WardrobeCategory` values (transcribed verbatim from `ai/ports/interfaces.py`'s `WardrobeCategory` Literal, which itself transcribes `001_initial.sql`'s `wardrobe_category` enum) to one of six slots: `"top"` (`western_top`, `ethnic_kurta`), `"bottom"` (`western_bottom`), `"one_piece"` (`western_dress`, `ethnic_saree`, `ethnic_lehenga`, `ethnic_anarkali`, `ethnic_salwar_kameez`, `ethnic_sherwani`, `indo_western`), `"outerwear"` (`western_outerwear`), `"footwear"` (`footwear_formal`, `footwear_casual`, `footwear_ethnic`, `footwear_sports`), `"accessory"` (`accessory_bag`, `accessory_jewellery`, `accessory_watch`, `accessory_belt`, `accessory_scarf`, `ethnic_dupatta`). A `dict` covering all 21 keys, not a function with a fallback — a missing key must be a loud `KeyError` a test catches, never a silent default (see test plan).
  - `CATEGORY_FORMALITY: dict[WardrobeCategory, int]` (0-10 scale, matching `occasions.formality`'s own scale, an Architect inference, not sourced from anywhere): `western_top=3, western_bottom=3, western_dress=5, western_outerwear=4, ethnic_kurta=5, ethnic_saree=8, ethnic_lehenga=9, ethnic_anarkali=8, ethnic_salwar_kameez=6, ethnic_dupatta=5, ethnic_sherwani=9, indo_western=6, footwear_formal=7, footwear_casual=3, footwear_ethnic=6, footwear_sports=1, accessory_bag=4, accessory_jewellery=5, accessory_watch=4, accessory_belt=3, accessory_scarf=3`.
  - `DEFAULT_STYLING_RULES_BY_KIND: dict[str, StylingRulesOverride]` (a literal, exhaustive dict over the 9 `kind` values — not a function, so a missing kind is a `KeyError` at import time / a test failure, not a silent runtime default):
    - `everyday`, `travel`, `social`, `milestone` → `required_base="either"`, `footwear_required=True`, `formality_tolerance=3`.
    - `professional` → `required_base="either"`, `footwear_required=True`, `preferred_footwear_categories=["footwear_formal"]`, `formality_tolerance=1`.
    - `sport` → `required_base="either"`, `footwear_required=True`, `preferred_footwear_categories=["footwear_sports"]`, `formality_tolerance=2`.
    - `ceremony`, `festival`, `religious` → `required_base="either"`, `footwear_required=True`, `preferred_footwear_categories=["footwear_ethnic", "footwear_formal"]`, `preferred_accessory_categories=["accessory_jewellery"]`, `formality_tolerance=1`.
    - This is `default_styling_rules_for(kind: str) -> StylingRulesOverride` (a thin lookup into the dict above, not a re-derivation) — used whenever `OccasionStylingInput.styling_rules` is `{}` or fails to parse into `StylingRulesOverride`.
  - `HARD_EXCLUDED_COLOR_FAMILIES: dict[str, frozenset[str]] = {"wedding_guest": frozenset({"white"})}` — **code-level, unconditional, applied regardless of what `styling_rules` contains or omits.** This is the literal mechanism for the AC's "enforced in code, not in a prompt" — it is checked in `styling_rules_engine.py` in addition to (never instead of) whatever `excluded_color_families` a fetched `StylingRulesOverride` supplies. See Edge Cases for why this is keyed by exact occasion key, not by `kind`.
  - `NEAR_WHITE_VALUE_THRESHOLD = 0.92`, `NEAR_WHITE_SATURATION_THRESHOLD = 0.12` (HSV, 0-1 scale) — the "white-dominant" test: a hex colour is near-white if `value >= 0.92 and saturation <= 0.12`. **Both numbers are an inference, not a verified colour-science standard** — tunable without touching call sites.
  - `MAX_ITEMS_PER_SLOT = 8` — the per-slot cap that bounds combinatorics (see Technical design below).
  - `RULE_WEIGHTS: dict[str, float]` summing to `1.0`: `formality_fit=0.30, category_completeness=0.20, colour_harmony=0.20, wear_recency=0.15, occasion_tag_bonus=0.10, season_fit=0.05`. (`style_preferences` is folded into `wear_recency`'s sibling — see below, not a 7th weight, to keep the sum simple and auditable.)

- `backend/services/styling_rules_engine.py` — the module CLAUDE.md's "one rules module, consumed twice" instruction is about. Public API (both a future scorer call-site and a future prompt-builder call-site import **these same functions** — there is no second implementation to drift):
  - `generate_candidates(wardrobe: list[WardrobeItemInput], occasion: OccasionStylingInput, *, as_of: date, season: SeasonTag | None = None, style_preferences: StylePreferencesInput | None = None, max_candidates: int = 5) -> PreFilterResult` — the entry point. **`as_of` is a required keyword-only parameter, never `date.today()` called internally** — this is what makes "same input, same output, every time" actually true; see Edge Cases.
  - `score_candidate(items: list[WardrobeItemInput], occasion: OccasionStylingInput, rules: StylingRulesOverride, *, as_of: date, season: SeasonTag | None, style_preferences: StylePreferencesInput | None) -> tuple[float, list[RuleScore]]` — scores one already-assembled combination; exposed publicly so a future ticket can score a single user-assembled outfit outside the generation path (e.g. "why did the AI suggest this" on an existing `outfits` row) without re-deriving the formula.
  - `render_candidate_for_prompt(candidate: ScoredCandidate) -> dict[str, Any]` — the exact, only, LLM-input-shaping function. Returns a plain JSON-serializable dict: `{"items": [{"id": ..., "category": ...}], "score": ..., "explanation": <top-2 RuleScore.explanation strings joined>, "gap_flags": [...]}`. A future prompt template calls this per candidate and concatenates — it must never re-derive colour/formality text itself.
  - Internal (not exported): `_resolve_styling_rules(occasion) -> StylingRulesOverride` (parses `occasion.styling_rules`, degrades to `default_styling_rules_for(occasion.kind)` on empty/`ValidationError`, then applies `default_styling_rules_for` as the base with any successfully-parsed override fields layered on top — partial overrides work, e.g. a hand-edited `{"formality_tolerance": 0}` only changes that one field); `_group_by_slot`; `_rank_within_slot` (caps to `MAX_ITEMS_PER_SLOT`, deterministic tie-break by `id` ascending); `_build_base_combinations`; `_is_near_white(hex_color: str) -> bool`; `_hue_distance_score(hex_a: str, hex_b: str) -> float`.

## Bounding the combinatorics (Technical design)

1. Group `wardrobe` items into the six `CATEGORY_SLOT` buckets, dropping any item with `category is None or color_primary is None` first (counted into `GapReport.excluded_missing_color_or_category`, per the ticket's own edge case).
2. Precompute each remaining item's per-item scores once (`O(n)`): formality distance to `occasion.formality`, recency (`wear_count`/`last_worn_at` vs `as_of`), season fit, occasion-tag match, style-preference bonus.
3. Within each slot, sort deterministically (score desc, then `id` asc as the tiebreak — never rely on insertion order or Python's stable-sort-on-equal-keys alone without an explicit secondary key) and cap to `MAX_ITEMS_PER_SLOT` (default 8) before any combination happens.
4. Build base combinations: every capped `one_piece` item is its own base (≤8); every capped `(top, bottom)` pair is a base (≤8×8=64) if `required_base` permits `"top_bottom"`/`"either"`. Base pool ≤ 72, independent of wardrobe size once capped.
5. For each base, attach the single best-fit footwear item (by `preferred_footwear_categories` bonus + per-item score) if any footwear exists; if none exists and `footwear_required`, keep the base as a candidate with `gap_flags += ["missing_footwear"]` rather than dropping it (ticket edge case). Same pattern, optionally, for one bonus outerwear/accessory item if `occasion.kind`'s defaults name a preferred category and one exists — additive to score, never required.
6. Score every assembled candidate via `score_candidate`, sort deterministically (score desc, `item_ids` tuple asc tiebreak), return the top `max_candidates`. `limited_options = len(candidates) < 3`.

This bounds worst-case combine work at roughly `72 × 2 (footwear alternatives considered) ≈ 150` scored candidates regardless of whether the input wardrobe has 1 or 5,000 items — the `O(n)` part is only the single precompute-and-rank pass per item.

## Colour harmony (deterministic, hex-only — sidesteps BL-064's still-open pattern/fabric vocabulary gap entirely, since it never needs a colour-name taxonomy)

Convert `color_primary` hex to HSV. A colour is "neutral" (harmonizes with anything, score `1.0`) if `saturation <= 0.12` (near-grey/black/white) — this reuses `NEAR_WHITE_*_THRESHOLD`'s saturation cut but not its value cut, since near-black is also neutral and near-white-but-not-white-enough-to-trigger-the-wedding-guard is still visually neutral. Otherwise compute hue distance (mod 360, folded to ≤180°) between the base garment's colour and its footwear/second-hero colour: `≤30°` (analogous) → `0.9`; `30-60°` → `0.6`; `60-150°` (clashing midrange) → `0.5`; `150-180°` (complementary/contrast, fashion-conventional) → `0.85`. **Explicitly labeled `[inference — a deliberately simple, tunable v1 heuristic, not a verified colour-theory standard]`** — real quality validation is in `BL-077`'s scope (the whole Epic 3 foundation's unrun eval), not this ticket's.

## Edge cases

Carried forward from the ticket, each concretized above:
- Wardrobe smaller than the occasion's required slots → partial candidate + `gap_flags`, never dropped (feeds SS-024's alert).
- All items tagged for a different occasion → `occasion_tag_bonus` (weight `0.10`) is additive-only, never gating; `formality_fit` alone still produces a valid, lower score.
- `style_preferences: null` → `RULE_WEIGHTS` unchanged, the style-preference bonus component simply contributes `0` rather than raising or being omitted from the weighted sum (so the total still sums correctly over the same fixed weights).
- Occasion with empty `styling_rules` → `_resolve_styling_rules` falls back to `default_styling_rules_for(occasion.kind)`, exercised by **every one of the 12 currently-seeded occasions today**, not just hypothetical future ones — this is the strongest possible test of "a new occasion must work the moment it is inserted."
- `NULL` colour or category items → excluded pre-grouping, counted in `GapReport.excluded_missing_color_or_category`.

Newly found during this design pass:
- **Determinism requires `as_of`/`season` to be explicit caller-supplied parameters — the module must never call `date.today()` or read a system clock internally.** This is the single most likely way "Deterministic: same input, same output" silently fails (identical wardrobe + identical occasion, run a day apart, would otherwise score recency differently). Flagged as a structural rule (parameter is required, not optional-defaulting-to-now) in the API signature above, and directly tested (see Test plan).
- `styling_rules` JSONB is hand-editable (no write policy in `007_occasions_registry.sql`, but `service_role` — i.e. a human via the Dashboard — bypasses RLS) and therefore untrusted-shaped: `_resolve_styling_rules` must degrade leniently (partial/garbage → ignored fields, never a 500-equivalent exception) — mirrors `GarmentTags`'s established lenient-validator posture in this codebase.
- Duplicate `id`s in the input `wardrobe` list (shouldn't happen given the DB's real PK, but a caller bug or test fixture could construct one) — `generate_candidates` must dedupe by `id` (keep first occurrence) before grouping, rather than let a duplicate silently double-count in a candidate or make two "different" candidates that are actually the same outfit.
- **The `wedding_guest` white-exclusion guard is keyed by the literal occasion key, not by `kind='ceremony'`.** This exactly satisfies the AC (which names `wedding_guest` specifically) but is fragile if a future near-identical occasion (e.g. a hypothetical `sangeet`/`reception` split) is added later and expected to inherit the same protection — it would not, automatically. The general, extensible mechanism for that case is `styling_rules.excluded_color_families` (a per-occasion DB-configurable list, already part of `StylingRulesOverride`'s schema) — the hardcoded guard is deliberate belt-and-suspenders specifically for the one occasion CLAUDE.md itself names verbatim, not a template for how every future colour exclusion should be expressed. Recorded here rather than silently generalized (which would be scope creep) or silently left unstated.

## Open questions / blockers

1. **No wiring exists yet, and this ticket deliberately does not add any.** `backend/adapters/occasion_repository.py`'s `SupabaseOccasionRepository.fetch_registry` currently selects only `key, label, badge_color, kind, parent_key, sort_order` — **not** `formality` or `styling_rules`. Nothing in this repo yet constructs `WardrobeItemInput`/`OccasionStylingInput` from real DB rows, and nothing calls `generate_candidates`. A future ticket (most likely folded into SS-028's AI-router work, since that's the ticket that will actually build the LLM-facing call path) must: (a) extend `fetch_registry` (or add a narrower new method) to also select `formality`/`styling_rules`; (b) fetch wardrobe items via the existing `IWardrobeRepository`; (c) call `generate_candidates`; (d) build the real LLM prompt from `render_candidate_for_prompt`'s output. Flagging explicitly rather than silently assuming SS-028 already covers it, since SS-028's own worktree is being designed independently in parallel.
2. **`occasions.styling_rules` ships `{}` for all 12 seeded rows, and this design does not populate it.** SS-025's migration comment says "populating it is SS-027's job," which I've read as "define the schema and make the fallback correct" (satisfied above) rather than "author real per-occasion override content today" — the latter is genuine product/stylist judgment (e.g., should `festival` prefer `footwear_ethnic` over `footwear_casual`? by how much?) that a code-only Architect pass shouldn't invent wholesale, and the ticket's own edge case explicitly requires the empty-styling_rules path to work correctly regardless. Logged as `BL-097` below rather than silently deciding either "ship a migration" or "ignore it forever."
3. **Colour-harmony and formality-distance scoring are v1 heuristics, not validated against any real stylist or user data** — same open gap `BL-077` already tracks for the whole Epic 3 foundation (Gemini styling quality). This ticket's scoring weights (`RULE_WEIGHTS`) and thresholds are additional unvalidated inputs to that same future eval, not a new separate gap — no new backlog row needed, cross-referencing `BL-077` is sufficient.
4. **Backlog scan (Active, tags `ai`/`infra`/`schema`/`test`):** `BL-064` (pattern/fabric free-text vocabulary) is acknowledged, not resolved — this design's posture (pattern/fabric treated as advisory-only, never a hard filter) already matches `BL-064`'s own recommended stance, so no change to that row is needed. `BL-079` (registry-pattern extension to pattern/fabric) is unrelated to this ticket's read-only, no-DB-write scope. `BL-077` (post-launch AI eval) is referenced above, not resolved (that eval hasn't run and isn't this ticket's to run).
