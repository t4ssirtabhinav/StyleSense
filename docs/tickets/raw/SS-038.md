## Description

Replace SS-027/SS-037's stage-②/③ scoring (wide-but-flat pruning, star-topology colour, no novelty signal) with the four-stage pipeline described in the proposal's §5:

1. **Eligibility** — hard constraints only (occasion norms, modesty, weather floor/ceiling, hard colour bans). Mostly a refactor of what SS-027/037 already built (`HARD_EXCLUDED_COLOR_FAMILIES`, the `IStylingProvider` hard-filter fields), pulled into its own explicit stage rather than mixed into scoring.
2. **Candidate search** — score the full base-pair space (not an 8×8 cap), keep the top ~200, expand each of the top ~50 with the top 3–5 options per remaining slot. Nothing is pruned before it has been scored on colour/formality/register.
3. **Attribute scoring** — pairwise colour harmony (not star-topology against `items[0]`), volume balance, register coherence, fabric×weather (where `fabrics` attributes exist, per SS-036), coverage×modesty, and **occasion-aware novelty** via `public.wear_recency()` (SS-035) and `suggestion_impressions`/`suggestion_outcomes` history (SS-033).
4. **Portfolio select** — Maximal Marginal Relevance (`λ·score − (1−λ)·max_similarity_to_already_selected`) with a hard score floor, returning 5–8 outfits plus 0–2 labelled "exploration" candidates (never below the floor).

Garment identity (slot, layer, register, base formality, `pairs_with`/`requires_with`) is read through a new adapter over the `garment_types` registry (SS-034), with an explicit, tested fallback to the legacy `CATEGORY_FORMALITY`/`CATEGORY_SLOT` dicts (`styling_rules_defaults.py`) for any category not yet present as a `garment_types` row — which today is every category, since SS-034 seeded 63 rows under new keys and the live `wardrobe_items.category` column still writes the 21-value enum. This is what lets Engine v2 ship before the taxonomy migration.

**Cream/ivory at `wedding_guest` (resolves `BL-111`'s decision, per user 2026-08-06):** keep the current aggressive near-white HSV exclusion (`value >= 0.92, saturation <= 0.12`) as the default behavior — do not narrow it. Move the two threshold constants from Python literals in `styling_rules_defaults.py` into a `ConfigSpec`-backed `app_config` row, with the coded default identical to today's values (SS-026's "missing/malformed row behaves exactly like today" pattern, same as `GEMINI_QUOTA_CEILING_SPEC`). Additionally, make the threshold overridable per-occasion via `occasions.styling_rules` (the `StylingRulesOverride` JSON schema SS-027 already defined and `occasions.styling_rules` already stores, currently empty for all 12 seeded rows per `BL-097`) — so a future ticket, informed by the impression/outcome data this same engine starts writing, can narrow the threshold for a specific occasion without a code change or a global behavior shift.

## Acceptance Criteria

- Given a wardrobe of N items, candidate search scores the full base-pair space and keeps the top ~200 (not the flat ~72-candidate cap SS-027/037 ships today) — proven by a property test showing candidate count scales with wardrobe size rather than staying constant
- Attribute scoring is pairwise for colour harmony (every relevant pair scored, not everything-vs-`items[0]`), includes volume-balance and register-coherence terms driven by `garment_types.register`/`pairs_with` when available, and includes occasion-aware novelty derived from `public.wear_recency()` + impression/outcome history — each term independently unit-tested
- Portfolio selection returns 5–8 outfits via MMR with a hard score floor (diversity only reorders *above* the floor, never surfaces a below-floor candidate) and 0–2 candidates explicitly flagged `is_exploration=true`, drawn only from eligible, above-floor candidates
- The garment-registry adapter returns `garment_types` attributes when a row exists for the item's category, and falls back to `CATEGORY_FORMALITY`/`CATEGORY_SLOT` otherwise — proven by a test running the same wardrobe fixture through both paths and asserting identical output for categories the legacy enum already covers (zero regression vs. today's SS-027/037 behavior for enum-only wardrobes)
- `suggestion_impressions` rows are actually written per candidate shown (item set, score, rule breakdown, rank, `is_exploration` flag) — this ticket is the first real caller of SS-033's schema, not just a test fixture
- `suggestion_sessions.engine_version` is bumped to a new value describing this engine (e.g. `"engine-v2"`) — resolves `BL-114`'s "no owner for bumping it"
- The near-white HSV threshold is read from `app_config` (coded default identical to `NEAR_WHITE_VALUE_THRESHOLD=0.92`/`NEAR_WHITE_SATURATION_THRESHOLD=0.12`) with an `occasions.styling_rules`-level override path proven by a test that narrows the threshold for one occasion and confirms the global default is unaffected for every other occasion
- `wedding_guest` still excludes 100% of near-white-by-default items with the coded default in place — no behavior change vs. SS-037's shipped guard unless a future ticket writes an override row
- The module docstring (successor to `styling_rules_engine.py`'s current one) states explicitly which SS-027/037-era gaps this ticket fixes and which remain open, naming the relevant `BL-XXX` rows, matching the discipline SS-037 itself set
- No new HTTP route, no change to `backend/routers/outfit_suggestions.py` — this ticket's output is a Python-callable pipeline (e.g. `EngineV2.generate_portfolio(...)`), consumed later by SS-020
- `supabase db diff --linked` is empty after push (this ticket's only DB surface is a data-seed migration into the already-live `app_config` table — no DDL)

Cover this explicitly in a mixed-wardrobe test (some items resolve via `garment_types`, some via fallback).

## Edge Cases & Failure Modes

- Wardrobe with fewer than 3 relevant-slot items — return the honest partial/`limited_options` result the current engine already returns; wide search does not fabricate candidates
- Every item in the wardrobe resolves via the legacy-enum fallback (a wardrobe tagged before `garment_types` had any real consumer) — register/volume-balance terms degrade to neutral, colour/formality/novelty terms are unaffected; the portfolio must still be non-empty
- An item's `category` matches a `garment_types` alias, not the canonical key — the adapter must resolve via `garment_type_aliases` before falling back, not treat an aliasable-but-unmatched slug as a fallback case
- `public.wear_recency()`/`suggestion_impressions` unreachable (DB error, not just empty) — novelty scoring degrades to a neutral (non-blocking) term, logged, never a hard failure of the whole pipeline; mirrors `BL-056`'s "never fail the user's request because a secondary read failed" posture
- A user with zero suggestion history (new user, or history purged by SS-033's 180-day retention) — novelty term degrades to "everything equally novel," not an error
- The near-white threshold `app_config` row is missing or malformed — coded default (today's exact 0.92/0.12 values) is used; `wedding_guest` behavior must be provably unchanged in this state, exercised by a test with the config row deliberately absent
- An `occasions.styling_rules` override narrows the threshold for one occasion, but the wardrobe has zero non-white candidates at that occasion even after narrowing — return the honest gap/partial result, never force a white item through
- Two occasions sharing the same `kind` (e.g. a hypothetical `sangeet` split from `ceremony`) do not automatically share a threshold override — each occasion's override is independent, matching `BL-111`'s note that the hard-coded-by-key guard "would not automatically extend to a future near-identical occasion"
- MMR's exploration slot must never select a below-score-floor candidate even when the eligible pool is small — floor check happens before diversity selection, not after
- Concurrent requests reading the same `app_config` threshold row mid-TTL-refresh — reuses SS-026's existing snapshot/cache mechanism; no new consistency requirement introduced here
