## Source note (this repo)

Created by `/new-feature` intake 2026-07-30, **Wave 1.5**. Not one of the four candidates the [Styling Engine v2 proposal](../../proposals/STYLING-ENGINE-V2.md) named — **added by Stage 1 analysis**, because the proposal's §1 claim that monsoon/fabric logic "needs no migration" is only half true: the *columns* exist, but there is no **vocabulary**, and Engine v2's fabric×weather scoring depends on one.

`BL-079` already specifies this build in full and states it *"no longer needs a design pass, only a build"* — written by SS-025's Architect once the registry precedent was concrete. This ticket executes that spec.

**One correction to `BL-079`, which this ticket also lands:** its claim that `color_primary`/`color_secondary` "transfer unchanged" to the same registry shape is **wrong**. Those are hex strings in practice (`gemini_vision_adapter.py:101`) parsed *numerically* by SS-027 (`_hex_to_hsv`, `_hue_distance_score`), and `style_preferences.favourite_colours` are hexes too. A slug registry over a continuous hex value is a different problem needing a hex→colour-family **binning** decision first. Colour is therefore **explicitly out of scope here**; `BL-064`'s colour half stays open.

## Description

Give `wardrobe_items.pattern` and `.fabric` a canonical controlled vocabulary using SS-025's proven registry shape, so the styling engine can reason about them instead of ignoring them — and so wardrobe filters/facets have a stable vocabulary rather than whatever distinct strings happen to exist in one user's wardrobe (the workaround SS-014's colour filter had to adopt).

## Acceptance Criteria

- `patterns` and `fabrics` registry tables exist, each with slug `TEXT` PK (`^[a-z][a-z0-9_]*$` CHECK), `label`, `sort_order`, `is_active`
- Sibling `pattern_aliases` / `fabric_aliases` tables, with canonical-key-first resolution order (collision inert, proven by test not constraint)
- A shared `*_unknown_tags` capture table: an unrecognised pattern/fabric from the vision model is **normalised, stored, and logged** — never dropped, never a failed item write
- `SECURITY DEFINER` normalisation function with `SET search_path = public, pg_temp`, invoked by a `BEFORE INSERT OR UPDATE` row trigger on the consuming column
- Seed transcribes SS-012's existing prompt vocabulary verbatim (see Technical Notes) — no new vocabulary invented in this ticket
- RLS: `SELECT` for `authenticated`, **no write policy** on any table
- **SS-012's tagging path keeps working unchanged**: an out-of-vocabulary fabric string still cannot fail an otherwise-good tagging result (the risk-weighted posture `BL-064` records)
- Existing `pattern`/`fabric` values on all current `wardrobe_items` rows are normalised or captured — none silently dropped; asserted against a before/after fixture
- `supabase db diff --linked` is empty after push

## Technical Notes

**Migration `016_pattern_fabric_registries.sql`** — assigned up front. **Renumbered 2026-07-31**: SS-029 shipped as live migration `012` (`011` went to SS-028 instead), shifting every Wave 1.5 slot up by one. `012` SS-029, `013` SS-033, `014` SS-034, `015` SS-035.

**Why this is `Risk: high` while SS-034's registry is `med`:** SS-034's tables are inert — nothing reads them. This ticket puts a `BEFORE INSERT OR UPDATE` trigger on **`wardrobe_items`**, which is the live write path for every SS-012 vision-tagging call. Same DDL shape, materially different blast radius. That asymmetry is also why Stage 1 recommended **not** merging this with SS-034 into one "registry" ticket.

**The seed already exists — transcribe, don't invent.** `BL-064` records SS-012's Gemini prompt vocabulary verbatim:
- **Patterns:** `solid`, `stripes`, `checks`, `floral`, `block_print`, `bandhani`, `ikat`, `paisley`, `polka_dots`, `embroidered`, `printed`
- **Fabrics:** `cotton`, `silk`, `linen`, `denim`, `wool`, `rayon`, `polyester`, `georgette`, `chiffon`, `khadi`, `chikankari`

These are already India-aware (bandhani, ikat, block_print, khadi, chikankari) and already what the model is instructed to emit, so normalisation should be near-lossless on existing data. Verify that claim against the live table rather than assuming it.

**Lift `007_occasions_registry.sql`** structurally, exactly as SS-034 does. `BL-079`'s row text is effectively the spec; follow it.

**Fabric attributes for Engine v2:** consider carrying `weight` / `breathability` / `season_affinity` columns on `fabrics` from day one — Engine v2's fabric×weather rule (velvet in Chennai in May, synthetics in Mumbai monsoon) needs them, and adding them later means re-authoring rows. Flag as a design question rather than assuming.

**Parallel `db push` hazard:** serialize the push across Wave 1.5's migration tickets; expect siblings' objects as `db diff --linked` drift; report the exact diff, never loosen the CI filter (`BL-060`).

## Edge Cases & Failure Modes

- The vision model emits an out-of-vocabulary fabric (e.g. `"tussar silk"`) → normalised if aliasable, else stored + captured; the item write must succeed either way
- An existing row's `pattern` differs only by case/whitespace/plural → alias resolution must handle it, and the migration must report how many rows normalised vs. captured
- `NULL` pattern/fabric (tagging failed or in progress, per SS-005's processing status) → remains `NULL`, not coerced to a default
- A pattern slug colliding with an alias → inert by resolution order
- Deactivating a registry row (`is_active = false`) must not orphan or rewrite existing item values
- Two Wave 1.5 migrations both adding an `*_unknown_tags`-shaped table → ensure names don't collide with SS-034's `garment_unknown_types`
