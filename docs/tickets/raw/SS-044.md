**Also closes a second, independent bug found by SS-024's Architect (`BL-156`, 2026-08-14):** the registry reserves a `feet` slot but seeds zero footwear rows — footwear can never resolve through the registry even after this migration, unless this ticket also seeds it. Folded into this ticket's scope rather than left as a second migration on the same table, per `BL-156`'s own recommendation ("natural pairing... whoever owns Wave 2's taxonomy migration must either seed `feet`-slot rows or knowingly accept footwear as permanently registry-invisible").

## Description

Make `wardrobe_items.category` resolve through the `garment_types` registry for every live row, so the scoring terms SS-038 already built and tested actually run against real data. This is a MIGRATE-phase ticket in the EXPAND→MIGRATE→CONTRACT playbook SS-025 established for `occasion_type` and SS-034 started for garments — SS-034 was the EXPAND phase (additive, inert); this is MIGRATE.

Two ways to close the gap, and the design doc must pick one explicitly rather than leaving it implicit (same instruction SS-034's own ticket carried for set-modeling, which that ticket honoured):
- **(a) Add alias rows** mapping each of the 21 live enum values onto an existing (or new) `garment_types.key`, and change `garment_registry_adapter.py`'s lookup to resolve through `garment_type_aliases` first.
- **(b) Migrate the column itself** from the ENUM to `TEXT REFERENCES garment_types(key)`, backfilling every row, following the exact CONTRACT-phase precedent `009_drop_occasion_type_and_merge_taxonomy.sql` already set for occasions.

Prefer (b) if the AC's "verify against live data" bar can be met with acceptable migration risk — it's the one SS-025 already proved out on this exact table shape, and (a) leaves a permanent two-hop lookup (`category` → alias → registry key) that (b) collapses to one. Record the choice and the reasoning in the design doc; don't default silently.

## Acceptance Criteria

- Every live `wardrobe_items` row's `category` resolves to a `garment_types` row (directly or via alias) — asserted against the real project's current data, not a fixture, per `BL-132`'s own "verify against live data, not fixtures — this is the whole point of the ticket."
- `garment_registry_adapter.get_garment_attributes` returns non-`None` for every live category value that has a plausible registry match, including all 8 footwear categories in the live enum (closing `BL-156`) — seed `feet`-slot rows in `garment_types` as part of this ticket if SS-034 didn't (it didn't; verified above).
- `engine_v2_attribute_scoring`'s `volume_balance` and `register_coherence` produce **non-neutral** scores when run against a real seeded wardrobe (a live-data verification script, following the `ss0NN_verify_*.py` pattern established by SS-015/033/035/036, not just a unit test against fixtures — unit tests already pass today per `BL-132`'s own text, so a passing unit test proves nothing new here).
- Migration is reversible (a documented rollback path — either alias rows are additive-only and safely droppable, or the ENUM→TEXT migration follows `009`'s three-step reversibility precedent).
- `supabase db diff --linked` is empty after push.
- `mobile/types/supabase.ts` regenerated if the column type changes (approach (b)).
- Existing readers of `wardrobe_items.category` (SS-012's tagging writer, any wardrobe filter/facet code, `styling_rules_engine.py`'s pre-Engine-v2 fallback path if still live) keep working against whichever shape this ticket lands — enumerate the actual call sites before choosing, don't assume.

## Edge Cases & Failure Modes

- A live `wardrobe_items.category` value with no plausible registry match at all (shouldn't exist in a 21-value enum against a registry meant to be a superset, but verify rather than assume) → must degrade gracefully, not fail the row or the migration
- A user's item was tagged before SS-034 existed and holds a category value that's since been reconsidered → same resolution path, no special-casing by tag date
- Alias/key collision (if approach (a)) → canonical-key-first resolution order, proven by test per SS-034's own established precedent, not by a DB constraint
- Rollback after partial rollout (approach (b)) → the reverse migration must not silently drop data; test it before pushing forward
- Two engine scoring terms (`volume_balance`, `register_coherence`) both depend on this migration — verify both independently rather than assuming one working implies the other does
