# SS-025 — Occasion Taxonomy & Extensibility Migration

`[Refactor]` `[P0]` `[Sprint 5]` `[5 pts]` Est: 28h
Depends on: SS-002, SS-004, SS-012, SS-013, SS-014, SS-015
Risk: high

## Description

Replace the fixed `occasion_type` Postgres ENUM (12 values) with a data-driven `occasions` registry table, so new occasions — regional festivals, travel, sports, fitness, milestones, year-round regional weddings — become an `INSERT`, not a migration + type regeneration + TS constant edit + app-store release.

This is the foundation ticket for Epic 3. It is a **precursor to SS-020** and unblocks SS-030/SS-031 (occasion calendar, multi-day event series). Full rationale, blast radius and cost analysis: [`docs/proposals/EXECUTION-PLAN.md`](../../proposals/EXECUTION-PLAN.md).

### Why the enum cannot stay

`[VERIFIED 2026-07-28]` — the occasion vocabulary is hardcoded in four places:

| Location | Form |
|---|---|
| `supabase/migrations/001_initial.sql:18` | `CREATE TYPE occasion_type AS ENUM (…)` — 12 values |
| `mobile/features/wardrobe/wardrobe.constants.ts:104` | `OCCASION_TYPES` array, "transcribed verbatim" from the migration |
| `mobile/types/supabase.ts` | generated TS union |
| `occasion_types` **table** (`003_onboarding_taxonomies.sql`) | a *separate* object — 9 rows, onboarding only |

Postgres enums cannot have values removed or reordered, cannot carry metadata (region, date rule, formality, styling rules, tier gate), and have no hierarchy. `003_onboarding_taxonomies.sql`'s own comments already establish the correct pattern — *"taxonomies must not be hardcoded TS unions"* — which SS-004 implemented for onboarding only. **This ticket finishes that pattern and merges the split brain.**

## Acceptance Criteria

- `occasions` registry table exists, seeded with all 12 existing enum keys, values byte-identical
- `wardrobe_items.occasion_tags`, `outfits.occasion`, `suggestion_sessions.occasion`, `social_posts.occasion` migrated from `occasion_type` to `TEXT`/`TEXT[]`; `occasion_type` type dropped
- **All 3 existing remote wardrobe items retain their exact occasion tags post-migration** (see Status note for the verified fixture)
- Adding a new occasion requires **only** a row insert — no migration, no type regeneration, no mobile release. Demonstrated in QA by inserting a genuinely new occasion (e.g. `ganesh_chaturthi`) and seeing it appear in the app without a rebuild
- Mobile occasion vocabulary is fetched at runtime; `OCCASION_TYPES` and `OCCASION_BADGE_COLOR_MAP` constants are removed
- Every occasion has a `badge_color` — the 4-of-12 colour gap (`BL-008`) cannot recur by construction
- Unrecognised occasion strings from AI tagging normalise via `occasion_aliases` rather than failing the write
- RLS: `occasions`/`occasion_aliases` readable by `authenticated`, writable by `service_role` only
- All 7 shipped tickets in the regression scope below re-verified

## Technical Notes

**Slugs, not UUID FKs.** `TEXT[]` of stable keys with a GIN index, with `occasions` as the metadata registry. Three reasons: (1) the AI writes these tags and returns `"wedding_guest"`, not a UUID; (2) a hard FK would *reject* novel AI output where a soft slug + alias table *captures* it — unrecognised tags are a signal about occasions we haven't modelled, not an error; (3) preserves the existing GIN index and needs no join on the hot "filter my wardrobe by occasion" path.

**Schema shape** (full column list in the execution plan §3.1):
```
occasions(key PK, parent_key, label, labels_i18n, kind, formality,
          region_scope[], culture_scope[], styling_rules JSONB,
          date_rule JSONB, tier_gate, badge_color, is_active, sort_order)
occasion_aliases(alias PK, occasion_key)
```
`kind` ∈ everyday | ceremony | festival | travel | sport | professional | social | milestone | religious.

`parent_key` gives hierarchy (`festival > navratri > garba_night`). Combined with SS-030's `occasion_calendar` (`starts_on`/`ends_on`), it yields multi-day series as one primitive — Navratri's nine nights and a wedding's sangeet/mehendi/reception are the same shape. **Do not model weddings as a special case.**

**Migration is a lossless cast:**
```sql
ALTER TABLE wardrobe_items
  ALTER COLUMN occasion_tags TYPE TEXT[] USING occasion_tags::text[];
```
**Forward migration only (`007_…`).** Never edit `001_initial.sql` — it breaks the CI drift check and every local dev DB (`BL-060` documents that check's false-positive history; do not feed it).

**Expand → migrate → contract**, even at low data volume: seed `occasions` and make it readable *before* any consumer switches to it, so every step is independently revertible.

**Mobile:** extend `onboarding.taxonomies.service.ts` to serve wardrobe occasions rather than adding a second taxonomy fetcher. The two vocabularies become one.

## Edge Cases & Failure Modes

- **Loss of compile-time exhaustiveness.** `OccasionType` stops being a closed TS union. This is the correct trade for a taxonomy that must grow without a release, **but it must be paid for with runtime validation at every write boundary plus tests** — otherwise it becomes a silent-bug generator. Non-negotiable QA scope
- Gemini (SS-012) emits an occasion string not in the registry → normalise via `occasion_aliases`; if still unknown, store it and log it for review rather than dropping the tag or failing the item write
- An occasion is deactivated (`is_active=false`) while items still reference it → items keep the tag; filters hide it; the item detail view still renders the label. Never orphan a user's data because of a taxonomy edit
- `region_scope`/`culture_scope` NULL means universal, not "no regions" — get the null semantics right in the resolver or every regional occasion silently disappears
- Taxonomy fetch fails on a cold mobile start → cache last-known-good; never render an empty occasion picker
- Two occasions with the same `label` in different regions (e.g. regional new-year names) — `key` is the identity, `label` is display-only
