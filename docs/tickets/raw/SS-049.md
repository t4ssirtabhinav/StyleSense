# SS-049 — Home Screen Rewrite

`[Feature]` `[P0]` `[4 pts]` Est: 14h
Depends on: SS-048
Risk: low

## Source note (this repo)

Promoted from `docs/competitive/07-EPICS-AND-TICKETS.md`'s portfolio-scope rewrite (2026-08-20), trimmed from `docs/competitive/06-UIUX-SPEC.md` §2.5 to what `SS-048` actually serves: a day-suggestion card plus the four rails. **No paywall teasing, no monetisation-shaped UI** — that whole layer (blur-tease headers, credit costs) is cut from the current plan along with `SS-069`.

## Description

Replace `mobile/app/(tabs)/index.tsx`'s current placeholder Home with a real screen: a "today" suggestion card at the top (reads `todays_picks` from `SS-048`), followed by the three remaining rails (`never_tried_pairs`, `not_yet_worn`, `newest_pieces`) as horizontal scroll sections, each with a header and a "see all" affordance.

## Acceptance Criteria

- Home reads exclusively from `suggestion_rails` (via a new `mobile/features/home/home.queries.ts` React Query hook) — **no direct engine call from the client**, matching this repo's "no direct Supabase calls in components" and "queries.ts is the only place Supabase is called from" rules (`.claude/CLAUDE.md`)
- Loading, error, and empty states handled for every rail independently — a failed `never_tried_pairs` fetch must not blank the whole screen if `todays_picks` succeeded
- A rail with zero items (per `SS-048`'s empty-payload contract) is hidden entirely, not rendered as an empty section
- Uses `FlashList` for each horizontal rail per `.claude/CLAUDE.md`'s "never `FlatList` for large lists" rule
- All items/cards imported from `components/ui/` (existing design system) — no raw `View`/`Text`
- "See all" on a rail navigates to a full-page view of that rail (a new route, or reuse of the existing wardrobe-filtered view if the rail maps cleanly onto an existing filter — e.g. `not_yet_worn` may just be `wardrobe.tsx` with `wear_count = 0` applied)
- Pull-to-refresh triggers the on-demand recompute path from `SS-048`

## Technical Notes

**This is a rewrite of a specific existing file** — read `mobile/app/(tabs)/index.tsx` as it currently exists before designing, don't assume its current shape from this ticket's description alone.

**Reuse `OutfitCard` from `mobile/features/outfit-ai/components/`** for the today-suggestion card if its shape fits — `SS-023` already built a real accepted-outfit card component; check before building a second one.

**No monetisation UI.** The original `06-UIUX-SPEC.md` §2.5 spec this was trimmed from included blur-tease paywalls on every rail header — explicitly cut. If any of that spec's language survives into implementation, it's a scope leak, not a feature.

## Edge Cases & Failure Modes

- A user who dismissed/skipped onboarding and has zero wardrobe items — Home must show a real empty state directing them to add items, not four empty/loading rails forever
- Rail data that's stale (computed hours ago) vs. a wardrobe change made seconds ago on the same session (e.g. just marked an item worn) — decide whether to show a "may be slightly stale, pull to refresh" affordance or silently accept staleness; state the choice
- Web-first rendering (`react-native-web`) of horizontal `FlashList` rails — verify this repo's existing horizontal-scroll patterns (if any) work on web before assuming they do, per this repo's history of web-specific surprises (`BL-146`, `BL-150`)
