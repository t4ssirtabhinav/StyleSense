## Source note (this repo)

Created by `/new-feature` intake 2026-07-30 from [`docs/proposals/STYLING-ENGINE-V2.md`](../../proposals/STYLING-ENGINE-V2.md) §3–§4 and Appendix B (commit `a95059f`), **Wave 1.5**.

The problem this exists to fix, stated plainly: **`wardrobe_category` is still a 21-value Postgres ENUM** (`001_initial.sql:7-14`) containing **zero ethnic bottoms** — no churidar, salwar, patiala, palazzo, dhoti, pyjama, sharara. That is why the styling engine can only ever offer *kurta with jeans*, and **no scoring change can fix a vocabulary that cannot express the outfit.** SS-025 already retired the `occasion_type` enum with an expand→migrate→contract playbook; garments never got the same treatment. This ticket is step 1 of the same playbook.

Appendix B's taxonomy is `[VERIFIED 2026-07-30 — web research, sources listed there]`, not recalled — it replaced an earlier trained-knowledge list and in doing so exposed five modeling problems that would have been expensive to discover after migration.

## Description

Create the data-driven garment registry: `garment_types` (with `parent_key` hierarchy), `garment_type_aliases`, `garment_unknown_types`. Seed it. **Nothing reads it yet** — this phase is purely additive and inert, exactly as SS-025's `007` was.

The design principle: **closed CHECK sets for physics, rows for culture.** `slot` and `layer` are physically closed (you can only wear one thing on your legs) and code may switch on them. Garment names, cultural register, and styling rules are unbounded and live in rows. SS-025 discovered this split already — `kind` is a closed 9-value CHECK, `key` is unbounded rows.

## Acceptance Criteria

- `garment_types`, `garment_type_aliases`, `garment_unknown_types` exist with: closed `slot` and `layer` CHECKs, open `register TEXT[]`, and `parent_key` self-reference with `parent_key IS DISTINCT FROM key`
- `region_scope`/`culture_scope` null semantics match `occasions` **exactly** — `NULL` means universal/pan-India, the empty array is forbidden by CHECK so nobody can write "applies nowhere", and the canonical applicability predicate is documented in-file (`007_occasions_registry.sql:19-27` transfers verbatim; this is the #1 silent-failure mode)
- Alias resolution order is canonical-key-first, so a key/alias collision is inert — proven by a test, **not** by a constraint (`007:64-67`'s deliberate precedent; do not add a trigger)
- An unrecognised garment slug is normalised, kept, and captured in `garment_unknown_types` — never dropped, never a failed write
- Seed covers every parent slot plus the 10 ethnic bottoms (Appendix B.2), the drapes, and the `torso_mid` layering types, with **parent-level** `styling_rules` authored and children overriding only where they differ
- RLS: `SELECT` for `authenticated`; **no write policy on any of the three tables**
- **Nothing in `backend/` or `mobile/` reads these tables** — asserted by a grep-based test, so "purely additive" is checked rather than claimed
- `supabase db diff --linked` is empty after push

## Technical Notes

**Migration `013_garment_types_registry.sql`** — assigned up front to prevent worktree collision. `011` is SS-029's; `012` SS-033; `014` SS-035; `015` SS-036.

**Lift `007_occasions_registry.sql` structurally.** Same slug PK with `^[a-z][a-z0-9_]*$` CHECK, same `labels_i18n JSONB`, same `is_active`/`sort_order`, same `SECURITY DEFINER` normalisation function with `SET search_path = public, pg_temp`, same aliases + unknown-capture sibling tables, same default-deny RLS. `badge_color` is occasion-specific and drops out. Proposal §4 carries a DDL sketch — treat it as a starting point, and prefer `007`'s actual shipped shape wherever the two differ.

**⚠️ The set-modeling decision must be made explicitly in the design, not left implicit.** Appendix B.1 finding #1 — *"kurta set / suit set is a SET, not a garment"* — is called the highest-value research finding and **is not expressible in §4's DDL**. Retailers sell kurta + bottom + dupatta as one SKU, and a user will photograph either the set or the individual pieces; we cannot control which. Either land a set-membership concept in this EXPAND phase, or state in the design that `requires_with` is the interim mechanism and set semantics are Wave 2 — but decide and record it. Retrofitting set semantics after rows exist is the expensive path.

**Cap the seed; the registry exists so the tail is cheap.** The tables are trivially safe but the *seed* is a two-week authoring project if allowed to be. Appendix B gives names, regions and some `pairs_with` edges — it does **not** give `layer`, `coverage`, `base_formality` or `excludes_with` for 75–95 types. Ship: ~15 parent rows + the 10 ethnic bottoms (B.2) + the four drapes + the five layering types (`nehru_jacket`, `waistcoat`, `blazer`, `shrug`, `koti`) + the genuinely-missing modern types (`cargo_pants`, `joggers`, `co_ord_set`, `kaftan`, `jumpsuit`, `dungarees`). Treat the regional tail (B.4) as follow-on `INSERT`s — using the registry that way *is* the value proposition, not a compromise.

**Silhouette/fit are item attributes, NOT types** (Appendix B.6). `oversized_tee` must not become a row; it is `tee` + `silhouette=oversized`. This is what keeps the type count at ~75–95 instead of 200+. Item-level attributes are Wave 2's `garment_attribute_specs`, out of scope here.

**Attribute-vs-identity, for whoever authors rules:** `base_formality` on a *type* is a starting point; a scuffed sneaker and a patent loafer differ per *item*. Do not over-invest in type-level formality precision — item-level attributes carry that in Wave 2.

**Register must be multi-valued** (`TEXT[]`, Appendix B.1 finding #5): leggings and jeans are legitimate modern ethnic bottoms; dhoti pants, culottes and cigarette pants are indo-western hybrids. A single-value register forces wrong choices.

**Parallel `db push` hazard:** serialize the push across Wave 1.5's migration-bearing tickets; expect other tickets' objects as `db diff --linked` drift and report the exact diff rather than loosening the CI filter (`BL-060`).

## Edge Cases & Failure Modes

- A type whose `parent_key` points at a deactivated parent → child must still resolve; `is_active` on a parent is not inherited silently
- `region_scope = NULL` (universal) vs `region_scope = '{}'` (forbidden) — the CHECK must make the second impossible, per `007`
- An alias that collides with a canonical key → inert by resolution order; test it
- A type with `requires_with` naming a type that isn't seeded yet → must not break; treat as an unsatisfiable requirement surfaced as a gap, not an error
- Two-piece regional garments (mekhela sador, mundum neriyathum) are **not** `full_body` — modeling them as one piece makes their components unmatchable (Appendix B.1 finding #4)
- 9-yard vs 6-yard sarees are physically different garments — a 6-yard saree cannot be draped nauvari/madisar style (B.1 finding #3); `length_yards` has real consequences, not cosmetic ones
- `kurta` vs `kurti` is a length difference, not two sibling types (B.1 finding #2) — forcing the AI to pick between siblings creates disagreement users will notice
