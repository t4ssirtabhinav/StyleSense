## Description

Add the small set of columns that are genuinely missing, and — this is the part that actually matters — **wire `do_not_style` into the engine's eligibility stage**, not just add the column. An unwired flag is worthless; `docs/competitive/04-INDYX-TEARDOWN.md` §7.7 calls this the single cheapest suggestion-quality feature in the whole competitive set.

## Acceptance Criteria

- `wardrobe_items` gains: `do_not_style BOOLEAN DEFAULT false`, `is_archived BOOLEAN DEFAULT false`, `condition TEXT`, `custom_tags TEXT[] DEFAULT '{}'`, `render_transform JSONB` — additive migration, all nullable/defaulted, no existing row rewritten
- `do_not_style = true` items are excluded from `engine_v2_eligibility.filter_eligible`'s eligible pool — **wired in code, asserted by a test**, not just present on the row
- `is_archived = true` items are excluded from the eligible pool the same way (an archived item shouldn't get suggested any more than a do-not-style one)
- `WardrobeItemInput` (`backend/services/styling_rules_types.py`) gains the fields the eligibility stage needs to read (`do_not_style`, `is_archived` at minimum) — additive, existing fields untouched
- RLS: no policy change needed (`wardrobe_items` is already `FOR ALL USING (auth.uid() = user_id)` — confirm this covers the new columns, since Postgres RLS is row-level not column-level, but state it explicitly rather than assuming)
- `mobile/types/supabase.ts` regenerated
- `supabase db diff --linked` empty after push (verify in CI per the `BL-028` Docker gap this repo's prior migration tickets have all hit)
- GIN index on `custom_tags` (mirrors `wardrobe_items.occasion_tags`' existing GIN index, `001_initial.sql:77`)

## Technical Notes

**Migration number:** confirm the next free number in `supabase/migrations/` before writing — `022` is taken by `SS-044`.

**`render_transform`'s shape is not this ticket's job to design.** `SS-055` (Dressing Room) is the real consumer and owns the `{x, y, scale, rotation, z}` shape decision — this ticket should ship it as a bare nullable `JSONB` column with no shape assumption baked into a CHECK, so `SS-055`'s Architect isn't constrained by a guess made here.

**`is_favourite` already exists (`001_initial.sql:71`) — do not re-add it.** The original epic draft listed it as new; it isn't.

**Read `engine_v2_eligibility.py` and `styling_rules_types.py::WardrobeItemInput` before designing the wiring** — `filter_eligible` is pure and already has a clear single point (`missing_filtered`/`pre_weather` list comprehensions) where an additional exclusion predicate composes cleanly.

## Edge Cases & Failure Modes

- An item with `do_not_style = true` that is already part of a previously-saved outfit (`outfits.item_ids`) — the flag should stop it from being suggested *again*, not retroactively invalidate outfits that already include it (no cascade, no re-validation of existing saves)
- `is_archived = true` and `do_not_style = true` both set — excluded once, not double-counted in any "N items excluded" reporting
- `custom_tags` containing near-duplicate strings (`"office"` vs `"Office"`) — no normalisation is in scope here (that's `BL-064`'s open vocabulary problem); store verbatim
- A NULL `render_transform` must not break any existing reader — nothing reads it yet, but assert that via a grep-based test the way `SS-034`'s "purely additive" guard did, so `SS-055` inherits a known-clean starting point
