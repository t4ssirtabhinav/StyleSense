## Description

`POST /ai/outfit-suggest` on FastAPI. Assembles the Epic 3 foundation into a working endpoint:

1. **Resolve the occasion** against the `occasions` registry (SS-025) — not a fixed enum
2. **Generate and score candidates deterministically** via the pre-filter (SS-027) — no LLM involved, no network
3. **Send ~5 pre-scored candidates to be ranked and narrated** via the provider router (SS-028), which picks provider+model from config by complexity, quota and tier
4. **Record cost** in the ledger and enforce the budget-based gate (SS-029)
5. **Cache on a cross-user combination signature** — see below

Parse structured JSON: 3 outfits with `item_ids`, reasoning, scores.

**Cache key change (do not skip).** The original `(user_id + occasion + wardrobe_hash)` key is a *per-user* cache with a near-zero cross-user hit rate. Cache instead on a **combination signature** — `(item category+colour+formality set, occasion)` — so two users with a navy kurta and beige churidar for `office` share the answer. Cache keys are near-impossible to change once a populated cache is live; this must be right the first time.

Two constraints on that shared cache:
- **Personalisation must not leak.** Cache the outfit + rationale *skeleton*; render anything referencing the user's name, city or `style_preferences` outside the shared entry.
- **It is a privacy surface.** A key derived from item attributes must not be reversible into another user's wardrobe. Salted hash; no `user_id` in the shared entry. Explicit QA boundary-sweep item.

This is still the first ticket to implement `IStylingProvider` for real (SS-006 shipped the port + `MockStylingAdapter` + stub router only), but the adapters themselves now land in SS-028 — per CLAUDE.md's Open/Closed rule the port is not modified by either ticket.

## Acceptance Criteria

- Returns 3 valid outfit combinations using actual wardrobe item IDs (not hallucinated) — **now structural, not prompt-dependent**: candidates come from SS-027's pre-filter, which can only reference real IDs from the input set
- Each outfit includes AI reasoning in English or Hindi
- Occasion-appropriate — white not suggested for `wedding_guest`. **Enforced in code** (SS-027 reads `occasions.styling_rules`), not left to the prompt
- Cache hit returns under 200ms; cold call under 4s — verify against the **slowest** model in the routing table, not the fastest
- Graceful fallback if a provider is down — fail over to the alternate provider (SS-028), then degrade to deterministic candidates with rule-based reasoning (SS-027). Never a hard error to the user
- Free tier gated server-side by **budget (paise), fail-closed** (SS-029); paying tiers fail open with logging
- Works for an occasion inserted into the registry *after* this endpoint shipped, with no code change — the extensibility promise is only real if this holds

## Technical Notes

- Adapters and routing land in **SS-028**; the pre-filter in **SS-027**; cost/limits in **SS-029**. This ticket wires them and owns the HTTP contract, the cache, and the response shape. Do not re-implement any of the four.
- Background task pattern (no synchronous AI calls), per CLAUDE.md
- Log all AI calls: `user_id`, `tokens_used`, `latency_ms`, per CLAUDE.md — SS-028/SS-029 provide the mechanism, this ticket must not bypass it
- Rate limiting is **budget-based (paise), not call-count** (SS-029). The "3 calls/day" AC below is now expressed as a free-tier budget ceiling that a typical call count maps onto — a 200-item wardrobe costs ~4× a 50-item one for the same three suggestions, and call-counting under-charges exactly the users who cost most
- The combination-signature cache key needs a stable serialisation of the item attribute set — define it **once**, in one module, and don't let it drift per caller. Same discipline the original `wardrobe_hash` note called for, applied to the new key
- **The pre-filter is the last line of defence.** If both providers are down or over quota, SS-027's deterministic candidates plus rule-based reasoning still produce a real answer with no network and no quota. That is how this ticket's "never a hard error" AC is actually satisfied

## Edge Cases & Failure Modes

- `style_preferences: null` (user skipped onboarding) — degrade to generic/popular suggestions, per SS-006's spec, not an error
- Wardrobe has fewer than 3 items in the relevant occasion category — return what's available with an honest "limited options" flag, not padded/invented items
- `pattern`/`fabric` tags are free-text with no canonical vocabulary (`BL-064`, still open) — prompt should treat these as advisory hints, not hard filters, since an unexpected string shouldn't silently exclude an item
- Claude API latency/availability — same class of risk SS-011/SS-012 hit with Replicate/Gemini (`BL-058`/`BL-067`): verify the "<4s cold call" AC against a real call with a real (non-trivial) wardrobe, not a synthetic 1-item case, before claiming it passes
