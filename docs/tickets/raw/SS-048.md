# SS-048 — Rail Presets & Precompute Job

`[Infra]` `[P0]` `[4 pts]` Est: 16h
Depends on: SS-044 (merged)
Risk: med

## Source note (this repo)

Promoted from `docs/competitive/07-EPICS-AND-TICKETS.md`'s portfolio-scope rewrite (2026-08-20). Per `docs/competitive/08-CHEAP-SUGGESTION-ENGINE.md` §4.2: the engine already exists (`backend/services/engine_v2.py`, `EngineV2.generate_portfolio`) and today has exactly one real caller path (the synchronous suggestion endpoint). This ticket turns it into four always-fresh home-screen surfaces at effectively zero marginal AI cost, by precomputing rather than generating on every view.

## Description

A new `suggestion_rails` table caching precomputed rail payloads per user, plus a job that (re)populates it. Four rail presets, each a thin parameterisation over `EngineV2.generate_portfolio` or a direct query — not four separate algorithms:

- **`todays_picks`** — a fresh portfolio for "today" (occasion inferred or defaulted, matches what the suggestion flow already does)
- **`never_tried_pairs`** — item pairs that have never co-occurred in a saved outfit or an accepted suggestion (a query over `outfits.item_ids` / `suggestion_impressions`, not an engine call — see Technical Notes)
- **`not_yet_worn`** — items with `wear_count = 0` (already a real column, `wardrobe_items.wear_count`)
- **`newest_pieces`** — most recently added items, ordered by `created_at`, with a suggested pairing from the engine

## Acceptance Criteria

- `suggestion_rails` table: `(id, user_id, rail_key, computed_at, payload JSONB)`, one row per `(user_id, rail_key)` (upsert semantics, not append-only), RLS `FOR ALL USING (auth.uid() = user_id)` matching the existing `wardrobe_items` pattern
- Serving a rail to the client is **one indexed read** — no engine call, no AI provider call, on the hot path a user actually hits opening the app
- Precompute triggers: on wardrobe write (debounced — don't recompute on every single item upload in a batch), and on demand (explicit refresh action) — a nightly cron is **out of scope for this environment** (no deployed backend exists yet, per `BL-037`; state this plainly rather than building a scheduler with nothing to run it)
- `todays_picks` and `newest_pieces`' pairing calls go through `EngineV2.generate_portfolio` exactly as the existing suggestion endpoint does — **no second scoring implementation**
- `never_tried_pairs` and `not_yet_worn` are pure SQL/query-layer, asserted by a test that they make **zero calls into `engine_v2*`** — this is the ticket's proof of `08-CHEAP-SUGGESTION-ENGINE.md`'s central claim, not just an assumption
- Every rail write logs `cost_incurred=False, zero_cost_reason="rules_only"` for the query-layer rails, matching `engine_v2.py`'s existing accounting posture for `todays_picks`/`newest_pieces` (which do call the engine and inherit its real accounting)
- Empty-state handling: a rail with zero eligible items (e.g. `not_yet_worn` on a wardrobe where everything's been worn) returns an empty payload, not an error — and the mobile consumer (`SS-049`) must be told to hide the rail entirely rather than render an empty section

## Technical Notes

**`never_tried_pairs` is a `NOT EXISTS` query, not a new algorithm — see `08-CHEAP-SUGGESTION-ENGINE.md`'s own reverse-engineering of the identical Fits feature.** Read that doc's §3 table before designing this from scratch; it already specifies the query shape.

**Read `EngineV2.generate_portfolio`'s full signature (`backend/services/engine_v2.py`) before designing the precompute job** — it already takes `occasion`, `as_of`, `season`, `style_preferences`, `exclude_fingerprints` as of `SS-023`. The precompute job is a caller with sensible defaults (today's date, no occasion override, no exclusions), not a new code path.

**Debounce mechanism:** this repo's established pattern for "don't do expensive work on every write" is `app_config`-driven TTL caching (`SS-026`) — consider whether the precompute trigger should be a lightweight "stale flag + lazy recompute on next read" rather than a real background job, given no deployed backend exists (`BL-037`) to run a scheduled job against. Record the choice explicitly.

**`is_archived`/`do_not_style` from `SS-040`** must be excluded from every rail — depends on that ticket landing first, or on the eligibility stage already excluding them if `SS-040` ships before this ticket starts.

## Edge Cases & Failure Modes

- A brand-new user with < 5 wardrobe items — every rail should degrade gracefully (fewer results, not an error), and `todays_picks` specifically should not fail just because the engine's `portfolio_size_range` can't be met
- A user's wardrobe changes between precompute and read (item deleted after the rail was cached) — the rail payload should reference items by id and the client (or a serving-time check) must handle a since-deleted item without crashing; consider whether `outfits.items_snapshot`'s denormalisation pattern (`020_outfits_first_writer.sql`) applies here too
- Two rapid wardrobe writes race the debounced recompute — last-write-wins is acceptable, no lock needed (rails are advisory, not a ledger)
- A rail computed under an old `engine_version`/`effort_tier` and never refreshed — decide whether `computed_at` staleness alone is enough, or whether `engine_version` should invalidate too (compounds with `BL-134`'s outfit-fingerprint inconsistency if fingerprints are stored in the payload)
