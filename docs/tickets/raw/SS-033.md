This is an **extend**, not a create.

## Description

Record what the styling engine suggested, and what the user did about it. Three surfaces: the request context (extend the existing `suggestion_sessions`), the individual candidates shown (`suggestion_impressions`), and the user's reaction (`suggestion_outcomes`).

This is substrate, not a user-facing feature. It unlocks four things nothing else can: anti-repetition across sessions (SS-023's own "regenerate should not return the same 3 outfits" AC), occasion-aware novelty scoring, a measurable tuning dial, and — later — genuine per-user personalization.

## Acceptance Criteria

- A suggestion request records exactly one `suggestion_sessions` row carrying occasion, weather, tier, effort tier, engine version, and a config-snapshot hash
- Each candidate shown records one `suggestion_impressions` row with the item-id set, total score, per-rule score breakdown, rank, and an `is_exploration` flag
- `saved` / `worn` / `dismissed` / `shuffled_away` / `shared` each record a `suggestion_outcomes` row referencing its impression; multiple outcomes per impression are permitted and ordered
- RLS: a user can read only their own sessions/impressions/outcomes; **writes have no policy at all** (`service_role` writes by bypass) — the SS-025/SS-026 default-deny shape, `007_occasions_registry.sql:91-105`
- **`cost-monitor`'s daily AI-cost figure counts only sessions that actually incurred provider cost** — verified by asserting the query against a fixture containing a cache-hit session. In scope for this ticket, not a follow-on
- A retention window is defined, documented, and enforced (see Technical Notes) — not left open
- Logging failure never fails the user's suggestion request (log-and-continue), proven by a test that makes the repository raise
- An explicit decision is recorded for the two superseded pre-existing columns (see Technical Notes)

## Technical Notes

**Migration `012_suggestion_impressions.sql`** — assigned up front so parallel worktrees cannot collide. `011` is reserved by SS-029 (`SS-029-design.md` §3.5). Ticket→migration map for Wave 1.5: `012` this ticket, `013` SS-034, `014` SS-035, `015` SS-036.

**⚠️ The `cost-monitor` break is the one non-obvious hazard.** `supabase/functions/cost-monitor/index.ts:18-21` counts today's `suggestion_sessions` rows and treats that count as the AI cost proxy against a hardcoded threshold. The moment sessions are written for cache hits, E0/degraded paths, or any ₹0 request, that number stops meaning "paid AI calls today" — silently. Fix is a filter on a new column, but it must land in this ticket. `weekly-report/index.ts:27` reads the same table; check it too.

**Additive columns on `suggestion_sessions`:** `engine_version TEXT`, `effort_tier TEXT`, `config_snapshot_hash TEXT`, `tier TEXT`, `candidate_count SMALLINT`, plus whatever the cost-proxy fix needs. `weather_data JSONB` and `cache_key TEXT` already exist — reuse, don't duplicate.

**Two superseded columns need a decision, not drift:** `suggestion_sessions.suggestions JSONB` ("array of outfit combos from AI") becomes redundant once impressions are rows — nothing writes it today. `accepted_outfit_id UUID REFERENCES outfits(id)` is a single-accepted-outfit precursor to `suggestion_outcomes`. Deprecate via `COMMENT ON COLUMN` or keep as a denormalised blob — pick one and say why.

**Retention: 180 days rolling**, `[product-adjustable — user owns this number]`. Purpose limitation, stated for the record: suggestion-quality measurement and personalization. Enforcement mechanism (scheduled purge vs. partition drop) is the Architect's call given volume. India's DPDP Act consent/purpose-limitation obligations plausibly apply `[trained-knowledge — MUST be verified against the current statutory text before this ships, per BL-001's lesson]`.

**Volume is the highest in the schema by an order of magnitude:** 5–8 impressions × ~3 requests/day/user ≈ 730 rows/user/month; at 10k users ≈ 7.3M rows/month. Index plan and retention/partition strategy belong in the design, not a later optimisation pass.

**Ports:** new `ISuggestionLogRepository` in `backend/adapters/interfaces.py` alongside `IAppConfigRepository`/`IOccasionRepository`, with a Supabase adapter — per CLAUDE.md's Open/Closed rule and matching the shape SS-029 established for `ICostLedger`.

**Do not touch `backend/services/outfit_suggestion_service.py`.** It is `BL-096`'s landmine (raises `HTTPException` inside a `BackgroundTasks` callback, which always crashes on a real rate-limit rejection). `BL-102` records that SS-029 stayed out of it for exactly this reason. **This ticket ships the substrate + tests; SS-020 does the wiring** — and SS-020 must be scoped to write impressions from day one, because that is the unbackfillable part.

**Parallel `db push` hazard:** three Wave 1.5 tickets carry migrations against the one shared live project (`mefpfykuinasgkpfhmzk`). Parallelize the code, **serialize the push**. Expect the other tickets' objects to appear as drift in `supabase db diff --linked` — report the exact diff, never loosen the CI filter (`BL-060`'s standing directive).

## Edge Cases & Failure Modes

- Ledger/impression write fails but the suggestion succeeded → never fail the user's request; log and continue
- A cache hit still records a session + impressions (with a zero-cost marker) — otherwise cache effectiveness is invisible, but the cost proxy must exclude it
- E0/degraded (both providers down, rules-only narration) still records impressions — this is exactly the data that proves the offline path works
- The same candidate is shown twice across two sessions → two impression rows, not a dedupe; repetition is the signal we are trying to measure
- An impression whose items are later deleted → outcome/impression rows survive (historical truth); do not cascade from `wardrobe_items`
- A user dismisses then later saves the same outfit → both outcomes recorded, ordered
- Retention purge must not orphan outcomes whose impression has aged out — purge as a unit
