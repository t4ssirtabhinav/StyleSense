## Description

Wire the E0/E1/E2 effort tiers from the proposal's §6 table into one `app_config`-backed `ConfigSpec` (same shape as `GEMINI_QUOTA_CEILING_SPEC`/`GEMINI_QUOTA_CEILING_SPEC`-style specs in `app_config_specs.py`), and a tier-resolution function that picks E0/E1/E2 per request based on provider health, budget status, and user tier — reusing SS-028's existing provider-down/failover signal and SS-029's existing budget-gate signal rather than inventing new ones.

| Tier | Search pool | Colour | Diversity | LLM | Use |
|---|---|---|---|---|---|
| **E0** degraded | 500 | star | λ=0.9 | none — rules narrate | both providers down; offline; free-tier over budget |
| **E1** economy | 1,500 | pairwise | λ=0.85 | cheap model, 5 cands | free tier steady state |
| **E2** standard | 5,000 | pairwise + volume | λ=0.75 + 1 explore | mid model, 6 cands | **launch default** (paying tier, and free tier when budget allows) |

These are the exact values from the proposal's §6 table for E0–E2; do not alter them without a product sign-off (the proposal itself calls out that "a dial you cannot measure is a dial you turn blind" — tuning them meaningfully requires the impression/outcome data SS-033 collects and SS-038 writes to, not a code-only guess).

## Acceptance Criteria

- One `ConfigSpec`-backed `app_config` row defines all three tiers' parameters (search pool size, colour mode, MMR `λ`/exploration-slot count, LLM candidate count) — a tier change is an `UPDATE`, no redeploy, matching every prior `app_config` consumer's no-redeploy AC (SS-026, SS-028, SS-029)
- Coded defaults, used when the config row is missing/malformed, exactly match this ticket's E0–E2 table above — a missing row must not silently degrade behavior below E0's documented floor
- A tier-resolution function returns **E0** when SS-028's provider-health signal shows both providers down (or offline), **E1** when SS-029's budget gate reports the caller at/near their ceiling, and **E2** otherwise (paying-tier default / free-tier-with-budget-headroom) — each branch independently tested, without duplicating SS-028/SS-029's own health/budget logic
- Search pool size, colour mode, and `λ` values resolved per-tier are the exact parameters SS-038's stage ②/③/④ functions accept — proven by an integration test that runs the same wardrobe fixture at each of the three tiers and asserts the candidate count / diversity behavior differs as the table predicts (E0 fewer/less-diverse candidates than E2)
- **E3/E4 are explicitly out of scope**: any attempt to resolve to E3/E4 either raises a clear "not yet implemented, pending a spend-ceiling decision" error or is structurally unreachable (no code path selects them) — not silently mapped onto E2's numbers
- The config schema is additive-only for a future E3/E4 addition — adding those tiers later must not require changing this ticket's E0–E2 row shape, proven by a design note (not necessarily a test) showing the planned shape
- `supabase db diff --linked` is empty after push (data-only seed migration, no DDL)

## Edge Cases & Failure Modes

- Config row present but only partially valid (e.g. E1 malformed, E0/E2 fine) — falls back to the coded default for the whole spec, not a per-tier partial merge (matches SS-026's existing all-or-nothing malformed-row posture; do not invent partial-merge semantics here)
- Provider-health and budget signals disagree in the same request (e.g. providers healthy but budget exhausted) — budget takes precedence (E1, not E2), since a healthy provider the caller cannot afford to call is equivalent to E1's "free tier steady state" framing, not E0's "nothing works" framing
- A request resolves to E2 but the wardrobe is too small to fill a 5,000-item search pool — the tier's pool size is a ceiling, not a requirement; SS-038's stage ② already handles small wardrobes honestly (fewer real candidates, not padded)
- Rapid tier flapping (provider health oscillating near the failover boundary within one user session) — out of scope for this ticket to smooth; note it as a candidate for hysteresis if it proves disruptive in practice, don't build unrequested debouncing logic speculatively
- A future E3/E4 ticket reads this ticket's config row shape and needs to add fields — the design must make that additive (new optional keys), not a breaking change to the E0–E2 shape already live in `app_config`
