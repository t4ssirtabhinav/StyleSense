# SS-006 — Outfit Styling AI: Preference Consumption Spec

`[Task]` `[P1]` `[Sprint 2]` `[2 pts]` Est: 6h
Depends on: SS-004

## Source note (this repo)

Surfaced during SS-004's Architect design review (2026-07-13): SS-004 designs the *producer* of onboarding preference data (`users` table fields + `style_preferences` JSONB), but no ticket anywhere in this backlog defines the *consumer* — the styling AI that's actually supposed to use `styles[]`, `occasions_priority[]`, `budget_range`, `favourite_colours[]`, `wardrobe_type`, and `gender` to generate outfit suggestions. Without this spec, SS-004 risks collecting fields the AI never uses, or shipping without a field the AI turns out to need (e.g. skin tone/undertone, body type/fit) — which would require re-onboarding users later. This ticket exists to close that gap before real AI adapter work starts.

## Description

Define (not necessarily fully implement) the hexagonal port(s) and consumption contract for turning a user's onboarding `style_preferences` into outfit suggestions, per CLAUDE.md's Backend architecture (`ai/ports/interfaces.py` — `IStylingProvider` — implemented by adapters, never modified per new provider). Specifically:

- Exact mapping from each `style_preferences` field to a concrete effect on suggestion output (e.g., "`occasions_priority` biases which occasion categories are ranked first in Discover/Home feed"; "`budget_range` is a hard filter, not a soft signal"; "`favourite_colours` biases coordination scoring, does not exclude other colours").
- Whether any onboarding-collected field turns out to be unused by the AI (candidate for removal from SS-004/future tickets) or whether a field the AI needs is *missing* from what SS-004 collects (e.g. skin tone/undertone for colour recommendations that suit the user rather than ones they already picked; height/fit preference for virtual try-on).
- The "first outfit suggestion" onboarding hook deferred from SS-004 (show a personalized result immediately after "Get Started" instead of a bare redirect home) — decide whether this ships as part of whichever ticket implements `IStylingProvider` for real, or stays a static/canned placeholder until then.
- Rate limiting (Upstash Redis, per CLAUDE.md) and background-task execution pattern for the first real AI call path, even if the adapter itself is stubbed in this ticket.

## Acceptance Criteria

- `ai/ports/interfaces.py` defines `IStylingProvider` with a method signature consuming a typed `StylePreferences`-shaped input and returning a typed suggestion result (adapter implementation may be a stub/mock for this ticket)
- A written mapping doc/table: onboarding field → suggestion-engine effect, covering every field in SS-004's `style_preferences` JSONB
- Explicit decision recorded on any additional data point (skin tone, fit/height) needed but not currently collected — if needed, logged as a follow-up ticket against the relevant onboarding/profile surface, not silently added to this ticket's scope
- Explicit decision recorded on the deferred "first outfit suggestion" onboarding hook (ship now as stub, or defer further)
- `routers/` has a stub endpoint depending on `IStylingProvider` via `Depends()`, exercising the port end-to-end with a mock adapter (proves the wiring, not real AI output)

## Technical Notes

- Follow CLAUDE.md's hexagonal pattern exactly: routers depend on the port, never on a concrete adapter
- No synchronous AI calls — background task pattern even for the stub, so the real adapter swap-in later doesn't change the calling convention
- Log all AI calls per CLAUDE.md: `user_id`, `tokens_used`, `latency_ms` (even if the stub logs zero/mock values, the logging call site should exist)

## Edge Cases & Failure Modes

- User has `style_preferences: null` (skipped all of onboarding) — suggestion engine must degrade gracefully (generic/popular suggestions), not error
- Partial preferences (e.g. onboarding was resumed and abandoned again at Step 2) — engine must handle missing `occasions_priority`/`favourite_colours` without crashing
