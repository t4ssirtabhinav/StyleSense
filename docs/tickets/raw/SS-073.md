## Description

Adds a landing screen that consumes the confirmation link from a signup email, establishes the session in the app itself, and hands off to SS-071's existing post-auth routing — so a user who clicks the link ends up **in the app, signed in**, instead of on an unowned browser page having to return and sign in manually (SS-072's revised flow, step 4).

**One new route, `app/(auth)/confirm.tsx`.** It reads the token from the URL, calls Supabase to exchange it for a session, and renders exactly three states: working, success (hand off to routing), and failed (a plain explanation plus a route back to `/login`). It performs no other function; in particular it is **not** a general-purpose auth callback and must not accept a caller-supplied redirect target.

**The mechanism is already decided — do not re-derive it.** See Technical Notes; the short version is `verifyOtp({ token_hash, type: 'email' })`, chosen over PKCE's `exchangeCodeForSession` because it is cross-device-safe.

**Two out-of-repo configuration changes ship with this ticket** and are as load-bearing as the code: the Supabase confirmation **email template** must emit a link pointing at this app's `/confirm` route carrying `{{ .TokenHash }}`, and every origin the app is served from must be in the Auth **Redirect URLs** allow-list. Neither is in this repo, neither can be tested from it, and the flow is inert without both.

## Acceptance Criteria

1. **A new route `app/(auth)/confirm.tsx` exists and is reachable while signed out.** Opening it with a valid token establishes a session in the app and hands off to SS-071's `useAuthRouting()` outcome (new user → `/onboarding`, completed user → `/`). It never renders a blank screen or an indefinite spinner: working / success / failed are all explicit.
2. **The guard interaction is decided deliberately and pinned by tests on both sides.** Whatever `app/(auth)/_layout.tsx`'s `GUARDED_ROUTES` does with `/confirm`, it must be: reachable unauthenticated (or the link is dead), non-looping (SS-071's "no route is both a redirect source and a target" property must survive), and covered by a test for the unauthenticated *and* already-authenticated entries.
3. **Token exchange uses `verifyOtp({ token_hash, type: 'email' })`.** `mobile/lib/supabase.ts` is **not** modified — `detectSessionInUrl` stays `false` (`BL-170`) and `flowType` stays the default `implicit`. Pinned by a test asserting the exact call shape.
4. **A web fragment fallback exists** so the screen still works under Supabase's *default* email template (which redirects with implicit tokens in the URL **fragment**): if no `token_hash` query param is present but `access_token`/`refresh_token` are in `window.location.hash`, adopt them via the public `setSession({ access_token, refresh_token })`. Web-only by construction; native must not crash on its absence.
5. **An expired, already-used, or malformed token produces a clear, non-technical failure state** with a route back to `/login` and an explanation that the account may already be confirmed and they can just sign in. No raw Supabase error string, no bare status code, and no dead end.
6. **No open redirect.** The screen never navigates to a destination read from the URL. Post-success routing comes exclusively from `useAuthRouting()`.
7. **The token is not left in the URL or in logs.** After a successful exchange the address bar must not retain the token (replace history state on web), and neither the token nor the resulting session is passed to `console.log` or an analytics event. `register`/`sign_in` analytics, if fired at all, carry no credential material.
8. **End-to-end verified live, once:** a real signup email is opened and the click lands the user in the app already signed in — on the same device *and* on a different device/browser than the one that signed up. Recorded in the worklog. **Gated on `BL-188`**; if outbound email still doesn't work, this AC is recorded as blocked, never as passed.
9. **The out-of-repo configuration is recorded, not just performed:** the exact email-template body used, and the exact Redirect-URL allow-list entries added, written into the worklog so they are reproducible against a second Supabase project later (`BL-003`).
10. **SS-072's flow keeps working unchanged** if this screen is never reached — "Check your email" → return → sign in stays a valid path. This ticket adds a fast path; it removes nothing. Pinned by SS-072's existing test suite staying green with no assertions weakened.
11. `tsc`, `biome` (this ticket's files) and the full jest suite clean.

## Technical Notes

- **The mechanism, settled — carry it forward, do not re-derive.** Use **`supabase.auth.verifyOtp({ token_hash, type: 'email' })`** (`VerifyTokenHashParams`, verified 2026-08-17 against installed `@supabase/auth-js@2.108.2` `types.d.ts:686-693`, `GoTrueClient.d.ts:1096-1102`). Use `type: 'email'`, **not** `'signup'` — the latter is marked deprecated in the SDK's own doc comment. Chosen over the two alternatives for three reasons: it needs **no** `lib/supabase.ts` change; it behaves identically on web and native; and it works **cross-device** — the user can sign up on a laptop and open the email on their phone — which PKCE's `exchangeCodeForSession` structurally cannot, because the code verifier lives in the originating browser's storage. Its cost is one email-template edit (`{{ .TokenHash }}` in place of `{{ .ConfirmationURL }}`).
- **Naming collision — check before writing.** `mobile/features/auth/auth.service.ts:106` **already exports a `verifyOtp(phoneDigits, token)`** for the phone/SMS path (`type: 'sms'`). The new function must take a distinct name (e.g. `confirmEmailToken(tokenHash)`); do not overload or rename the existing export, which SS-003's flow and its tests depend on.
- **`AuthErrorCode` gains only additive members.** It is currently `invalid_phone | network_error | rate_limited | invalid_or_expired_otp | unknown | email_already_registered | invalid_credentials | weak_password | email_confirmation_required` (`auth.types.ts:10-21`). `email_confirmation_required` is **already taken** by SS-072's sign-in-side mapping — do not reuse it for a bad link. Add something like `invalid_or_expired_confirmation_link`; leave every existing code and its copy untouched.
- **Guard facts, verified 2026-08-17.** `app/(auth)/_layout.tsx:28-33`'s `GUARDED_ROUTES` is exactly `{'/login', '/(auth)/login', '/verify-otp', '/(auth)/verify-otp'}`; anything not in that set falls straight through to the `Stack`. So a new `/confirm` route is unauthenticated-reachable **by default, with no edit** — which is the correct starting posture. The real decision is what should happen when it is opened *with* a live session (see Edge Cases); resolve it explicitly rather than by omission, per AC #2. `usePathname()` strips route-group segments (confirmed against `expo-router@56.2.11`), so match `/confirm` and `/(auth)/confirm` defensively if the route is added to the set, exactly as the existing entries do.
- **Why the fragment fallback (AC #4) is worth its lines.** The `token_hash` path only works *after* the email template is edited. Until then, and for any confirmation email already sent, GoTrue's default link 302s to the redirect target with implicit tokens in the URL **fragment** — which `useLocalSearchParams` does **not** read (it parses the query string). `[VERIFIED 2026-08-17]` the SDK's own fragment consumer `_getSessionFromURL` is **private** and throws `'No browser detected.'` outside a browser (`GoTrueClient.js:3164-3211`), so it cannot be called; `setSession({ access_token, refresh_token })` is the public, supported way to adopt those tokens. Read the hash directly from `window.location.hash` behind a `Platform.OS === 'web'` check.
- **Redirect-URL configuration is a real provisioning dependency, not a checkbox.** Supabase only redirects to origins on the Auth **Redirect URLs** allow-list, and there is **no hosted web origin for this app at all** (`BL-171` — it runs via `npx expo start --web` on the dev machine). In practice that means allow-listing `http://localhost:8081/confirm` (and the native `stylesense://confirm` scheme, already configured in `mobile/app.json:7,22-26`) to verify anything, and re-doing it against the real origin the moment one exists. Same class of external-provisioning gap as `BL-047`'s EAS build gap: the code can be complete and correct and still do nothing.
- **`SITE_URL` matters too.** It is the fallback target when no valid `emailRedirectTo` is supplied, and today it points at whatever the Supabase default is. Set it somewhere sane as part of this ticket and record the previous value.
- **No backend change, no migration, no schema change, no RLS change.** A session minted through `verifyOtp` is indistinguishable downstream from one minted by phone OTP or password — `hooks/useAuth.ts:42-87` adopts it purely via `getSession()`/`onAuthStateChange` and never inspects the provider. Do not open `backend/` in this ticket.
- **`emailRedirectTo` on the SS-072 side.** `signUp()` and `resend()` both forward `options.emailRedirectTo` to GoTrue (`GoTrueClient.js:696-708`). Setting it is how the link is pointed at `/confirm`. Touching those two call sites in `auth.service.ts` is in scope for this ticket; nothing else in SS-072's shipped flow is.
- **Scope fence.** Password reset (`BL-173`) uses a structurally identical landing/token-exchange flow and is **not** in this ticket. If the screen is built in a way that a future reset flow can reuse, good — but do not build the reset flow, and do not generalize the route into an all-purpose auth callback to anticipate it (that is what makes AC #6's open-redirect rule hard to hold).

## Edge Cases & Failure Modes

- **The link is opened on a device or browser with no existing app session (the cross-device case).** Signed up on a laptop, opens the email on a phone. This is the *normal* case, not an exotic one, and it is precisely why `verifyOtp({ token_hash })` was chosen over PKCE — `exchangeCodeForSession` would fail here because the code verifier is in the laptop browser's storage. The screen must work cold, with no prior state whatsoever.
- **An expired or already-used token.** GoTrue tokens are single-use and time-limited, and a user who clicks the link twice (or has a mail scanner pre-fetch it) hits this on a perfectly healthy account. The failure copy must say the account may already be confirmed and offer sign-in — treating this as a hard error would tell a successfully-confirmed user their signup failed.
- **The Redirect URL is not configured in the Supabase dashboard.** The click lands on `SITE_URL` (or an error page) instead of `/confirm`, and the app never sees the token. **The account is still confirmed** — GoTrue does that server-side before redirecting — so SS-072's manual path still saves the user. Failure must therefore be silent-and-recoverable, never a broken account. Provisioning dependency of the same kind as `BL-047`; see AC #9.
- **The link is opened while a *different* user's session is live in that browser.** Consuming the token would swap the active account underneath them; ignoring it leaves the clicker confused. Decide explicitly (a guard redirect away, or an explicit "you're signed in as X" state) and test it — this is half of AC #2.
- **The link is opened while the *same* user's session is already live.** Harmless, but must not loop or double-navigate.
- **A mail client pre-fetches the link** (corporate scanners, some webmail previews) and consumes the token before the human clicks. The human then hits the expired/used case above on an account that is genuinely confirmed. Same copy handles it; do not treat it as an attack.
- **Native deep link vs. web URL.** On native the link arrives through `expo-linking`/the `stylesense://` scheme; on web it is an ordinary navigation. `token_hash` as a query param works on both; the fragment fallback (AC #4) is web-only and must be inert, not crashing, on native.
- **Token left in the browser history or referrer.** After a successful exchange, replace the history entry so a back-navigation or a shared URL does not carry the token. Never log it.
- **No token at all** (someone opens `/confirm` directly, or a mail client strips the query string): render the failure state with a route to `/login`, not a crash and not an infinite spinner.
- **Network failure mid-exchange.** Reuse SS-003's existing `network_error` code and copy; the screen must offer a retry that does not lose the token from the URL before the retry runs.
- **`BL-188` blocks live verification entirely.** With no working outbound email, there is no link to click and AC #8 cannot pass. Build and unit-test against mocks; record AC #8 as blocked rather than inferred.
