# SS-021 — Style Score Calculation + Display

`[Feature]` `[P2]` `[Sprint 5]` `[1 pt]` Est: 3h
Depends on: SS-002, SS-015

## Description

Supabase Edge Function computes a style score (0–100) from: `wardrobe_variety` (items across categories), `occasion_coverage` (how many of the 8 occasions covered), `cost_efficiency` (avg cost per wear), `activity` (outfits saved this month). Circular progress widget on Home + Profile. Score breakdown in Profile (premium).

## Acceptance Criteria

- Score updates after each outfit saved or item added
- Free users see the total score only
- Premium: 4 sub-scores shown with improvement tips
- Score is shareable as a card image

## Technical Notes

- Pure DB computation (aggregates over `wardrobe_items`/`wardrobe_item_wears`/`outfits`) — no external API call, so this is a low-risk Edge Function unlike SS-010's `get-upload-url` (`BL-069`'s "deployed Edge Function env has gaps invisible to local checks" lesson applies less here, since there's no secret/credential dependency, but still worth a smoke check post-deploy)
- `cost_efficiency` should read `cost_per_wear` (the `GENERATED` column) directly rather than recomputing `wear_count`/`purchase_price` math itself — avoids a second implementation of logic SS-015's migration already owns

## Edge Cases & Failure Modes

- New user, empty wardrobe — score should render as a defined value (e.g. 0 or null-state), not divide-by-zero
- `activity` (outfits saved this month) has no data source yet — `outfits` table doesn't exist until SS-020 ships; this ticket can compute the other 3 sub-scores and stub `activity` at 0 until SS-020/outfit-save lands, or be sequenced after SS-020. Architect should decide and record which.
