## Source note (this repo)

Promoted from `docs/competitive/07-EPICS-AND-TICKETS.md`'s portfolio-scope rewrite (2026-08-20) — **the flagship UI piece of the whole portfolio-scope plan**. Per `docs/competitive/03-FITS-TEARDOWN.md` §Dressing Room mechanics: z-ordered transparent garment PNGs composited on a mannequin sprite, with per-item persisted transforms. Zero ML, zero network call at render time — the entire reason this is cheap to build and worth building is that it's pure client-side compositing, not a generative feature.

The user has explicitly named this the piece they want closest to Fits' UI/UX quality (see this session's earlier discussion) — this is the ticket to spend real design effort on, not the one to rush.

## Description

An on-body outfit builder: garments render as z-ordered transparent PNG layers over the `SS-056` mannequin, each with an independently draggable/scalable/rotatable transform that **persists per item** (`SS-040`'s `render_transform` column) — fiddle with a garment's fit once, and it looks right in every future outfit that reuses it. Tap-and-swipe to swap a slot's garment; per-slot and whole-outfit shuffle.

## Acceptance Criteria

- Garments composite in correct z-order on the `SS-056` mannequin: footwear → bottom → top → outerwear → accessories (layering order matches `garment_types.layer`/`assembly_slot`, already populated by `SS-044`'s registry work — reuse it, don't invent a second layering scheme)
- Each garment layer supports independent drag (x/y), pinch-scale, and rotation; the resulting `{x, y, scale, rotation, z}` persists to `wardrobe_items.render_transform` **per item**, not per outfit — the same kurta looks right whether it's in outfit A or outfit B
- Tap-and-swipe on any slot swaps that garment for another eligible item in the same slot, without disturbing the other slots' transforms
- Per-slot shuffle (randomise one slot) and whole-outfit shuffle (new candidate set from the engine, matching `EngineV2.generate_portfolio`'s existing output shape)
- **Zero network calls to render** — once the item images and their transforms are loaded, compositing/manipulation is 100% client-side; asserted by the design (no fetch in the render/manipulate path), not just claimed
- Swap interaction completes in <100ms perceived latency (client-side state update, no round trip)
- **Ethnic drape handling for saree/dupatta**: at minimum, a saree renders as a distinct composite (drape sprite + blouse beneath) rather than being treated as a single flat rectangle like a western top — verify this against a real saree photo before calling the AC met, per the original spec's own instruction (`06-UIUX-SPEC.md` §2.6: "verify the ethnic drape rendering with a real saree before calling this done — it is the part with no prior art to copy")
- Reachable from both `SS-049`'s home-suggestion flow (open a suggested outfit in the Dressing Room to adjust it) and a standalone "build an outfit" entry point

## Technical Notes

**This is the highest-craft UI ticket in the plan — budget real design iteration, not just implementation time.** Per this session's stated goal (a portfolio piece demonstrating both backend depth and frontend polish), this ticket is where the frontend-polish half of that goal is earned or lost.

**Gesture handling:** `react-native-gesture-handler` (v3) and `react-native-reanimated` (v4) are both already dependencies (confirmed via prior tickets' worklogs, e.g. `BL-142`) — this repo has no prior gesture-driven component to inherit a working web configuration from (`BL-142`'s own note: "the first drag-gesture interaction in the codebase"). Verify web behaviour early, not at the end, given this is a web-first app.

**`render_transform`'s shape is this ticket's decision** (`SS-040` deliberately left it an unshaped `JSONB` column for exactly this reason) — design and document the shape here (`{x, y, scale, rotation, z}` is the expected minimum per the AC, but confirm units, coordinate origin, and z-index range explicitly).

**Garment layering order should read `garment_types.layer`/`GARMENT_SLOT_TO_ASSEMBLY_SLOT`** (both populated by `SS-044`, in `backend/services/styling_rules_defaults.py`) rather than inventing a second z-order scheme — check whether that data needs to be exposed to the mobile client (a new lightweight endpoint, or bundled into the rail/suggestion payload) before assuming it's already reachable client-side.

**Ethnic drape rendering has no prior art anywhere in this codebase or in any competitor analysed** (`03-FITS-TEARDOWN.md`, `04-INDYX-TEARDOWN.md` — neither app represents a saree as anything but a flat item). Prototype this specifically before committing to the rest of the ticket's estimate; if it proves to need real per-garment authored drape sprites rather than a generic transform, that's a separate asset-production dependency worth surfacing early, not discovering at the end.

## Edge Cases & Failure Modes

- A slot with no eligible item in the wardrobe (e.g. no footwear at all) — must render a clear "add an item" affordance in that slot, not a broken/empty layer
- Swapping a garment that has never had a `render_transform` set — needs a sensible default transform (centred, slot-appropriate default scale) rather than a null-position crash
- A user resizes/rotates a garment to something absurd (0 scale, off-screen position) — client-side bounds clamping, not a server-side validation round trip (this stays a client-only interaction)
- Saree/dupatta drape sprite combined with a swapped blouse of a different colour — the composite must still read as coherent; if the drape sprite is colour-locked to a specific saree image, state that limitation explicitly rather than shipping a visibly broken combination
- Rotating device orientation or resizing the web viewport mid-manipulation — transforms are stored in a fixed coordinate space, not viewport-relative, so this shouldn't corrupt saved data (verify this assumption explicitly)
