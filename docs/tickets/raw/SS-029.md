# SS-029 — Cost & Capacity Ledger (Budget-Based Rate Limiting)

`[Infra]` `[P0]` `[Sprint 5]` `[4 pts]` Est: 19h
Depends on: SS-018, SS-026
Risk: high

## Description

Track what every AI request actually costs, per user, in paise — and enforce limits on **spend**, not on call count.

Call-count limiting systematically under-charges the users who cost the most: a 200-item wardrobe costs ~4× a 50-item wardrobe for the same three suggestions. Budget-based limiting is the only primitive that prices that correctly, and it is the backstop against a single heavy or abusive user breaking the unit economics.

## Acceptance Criteria

- Every AI call writes a ledger row: `user_id`, `provider`, `model`, `feature`, `tokens_in`, `tokens_out`, `cost_paise`, `latency_ms`, `cache_hit`, `created_at`
- Per-user daily and monthly spend counters in Redis, with the ledger table as the durable record
- Limits are expressed as **budgets** (paise), with per-tier ceilings read from config (SS-026) — not hardcoded, not per-endpoint call counts
- Enforcement is **fail-closed for free tier** (per SS-018's established pattern) and **fail-open with logging for paying tiers** — a paying user is never locked out of a feature they bought by an infra blip
- Cost-per-call is derived from a config-driven price table, so a vendor price change is a config update, not a code change
- Boundary sweep passes: empty / at-limit / over-limit / concurrent / stale-counter
- A per-user and per-feature cost breakdown is queryable — this is the data that tells us whether the business model works

## Technical Notes

**Reuse SS-018's Upstash fail-closed pattern; do not write a second rate limiter.** This ticket changes the *unit* being counted (paise, not calls) and the *tier semantics* (fail-open for paying users), not the mechanism.

**Extract `ICostLedger` and `IRateLimiter` as ports**, per `CLAUDE.md`'s Open/Closed rule applied one layer below AI. This is what keeps the future Upstash → Cloudflare Durable Objects migration (`BL-082`) a two-week adapter swap rather than a quarter — and DO's atomic per-key counters are the technically correct primitive for a revenue gate, where a distributed counter race means "free user got 4 calls instead of 3."

**The price table must carry an effective date.** Claude Sonnet 5's introductory pricing expires **2026-08-31** `[VERIFIED 2026-07-28]`; a ledger that hardcodes today's rate will silently under-report cost from September onward. Price rows are dated and the ledger records the rate it used.

**Resolves `BL-062`** (no per-user cost cap) and supersedes the per-vendor patching approach it describes.

## Edge Cases & Failure Modes

- Redis unavailable → free tier fails closed (denied, with a clear user-facing message), paid tiers fail open and log. Both paths must be explicitly tested, not inferred
- Ledger write fails but the AI call succeeded → **never fail the user's request because accounting failed.** Queue the ledger write and log; an unbilled call is better than a broken feature
- Concurrent requests racing the budget check → a user must not be able to burst past their ceiling via parallel requests. This is the boundary case most likely to be wrong; test it explicitly with real concurrency, not sequential calls
- Cache hits cost ~nothing but must still be *recorded* (with `cache_hit=true`, `cost_paise=0`) — otherwise cache effectiveness is invisible and we cannot tell an efficient user from an inactive one
- A user crosses their budget mid-multi-call request → complete the in-flight request, deny the next. Never leave a half-generated result
- Clock/timezone on daily reset → IST (`Asia/Kolkata`) per `CLAUDE.md`, not UTC. A day boundary that resets at 05:30 IST is a real and confusing bug
- Retries and failovers (SS-028) generate multiple provider calls for one user request → bill all of them, but attribute them to one `request_id` so per-request cost stays truthful
