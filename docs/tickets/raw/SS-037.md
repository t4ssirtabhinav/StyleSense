## Source note (this repo)

Created by `/new-feature` intake 2026-07-30, **Wave 1.5**. SS-027 shipped as an explicitly-labelled **v0** ([PR #31](https://github.com/t4ssirtabhinav/StyleSense/pull/31)) with three known limits named in its PR body. This ticket closes them.

The scope is deliberately **half** of what a full triage would cover. Stage 1 analysis established the dividing line: fix what changes **which outfits are expressible**; skip what only changes **how they are ranked**, because [Engine v2](../../proposals/STYLING-ENGINE-V2.md) §5 replaces the ranking stages wholesale and a v0 patch there would be discarded work. Engine v2 will not land before SS-020, so the expressibility half genuinely matters now.

SS-027's QA pass (PASS, 2026-07-30, 31 tests) did not catch any of these three — the acceptance criteria as written are satisfied by code that has these holes. That is worth noting for the QA phase here.

## Description

Three fixes to `backend/services/styling_rules_engine.py` and `styling_rules_defaults.py`. All pure Python, no schema, no network, fully reversible. The only consumer is SS-020, which does not exist yet.

## Acceptance Criteria

- **Named-colour white guard.** An item whose `color_primary` is an unparsable or *named* colour (e.g. the literal string `"white"`) is handled explicitly: named colours resolve to a colour family before the white test, **or** the guard fails closed. A `wedding_guest` request against a wardrobe of items tagged `color_primary: "white"` yields **zero** candidates
- **Outerwear assembly.** An occasion whose rules expect a layer surfaces candidates that include an `outerwear` item when the wardrobe has one; when it does not, an explicit gap flag is emitted rather than a silent omission
- **Dupatta attachability.** `ethnic_dupatta` is attachable for ethnic/ceremony/festival/religious occasions, and a candidate may carry more than one accessory
- Every existing SS-027 test still passes unchanged, **except** those whose assertions encoded one of the three fixed bugs — and each such change is justified in the diff
- The candidate-count bound and the determinism property both still hold (the two properties that make SS-027 worth keeping)
- The module docstring states which bugs are deliberately **not** fixed here, with a pointer to Engine v2

## Technical Notes

**Bug 1 — the white guard (do this one regardless of any other sequencing decision).** `_hex_to_hsv` (`styling_rules_engine.py:461-476`) returns `None` for any string that is not 3- or 6-hex-digits; `_is_near_white` (`:479-486`) then returns `False`; so `_item_is_hard_excluded_white` (`:489-492`) does **not** exclude an item whose colour is the literal string `"white"`. Meanwhile `001_initial.sql:52` documents the column as *"hex or named colour"*, and `BL-064` records that the vision adapter does not hard-reject out-of-vocabulary values.

Net effect: the AC *"`wedding_guest` never surfaces a white-dominant candidate — enforced in code, not in a prompt"* is true one layer down and **prompt-dependent one layer up**. This is a stated AC failing on the one styling rule CLAUDE.md names verbatim. The same hole makes `_hue_distance_score` return a flat `0.75` for named colours (`:506`), silently degrading all colour scoring for such items.

Prefer failing closed (exclude when the colour cannot be parsed *and* the occasion has a hard colour exclusion) over a partial named-colour map — a small map will not cover `"off white"`, `"ivory"`, `"cream"`, `"eggshell"`. If a map is used, say what it does not cover.

**Bug 2 — outerwear.** `:119` ranks all six slots including `outerwear`; `_build_base_combinations` (`:341-352`) uses only `one_piece`/`top`/`bottom`; the assembly loop (`:136-159`) appends only footwear and one accessory. `ranked_slots["outerwear"]` is computed and discarded. The raw SS-027 ticket's own Technical Notes name outerwear in category completeness, so this is a miss against spec, not new scope. Roughly 15 lines. Note `_category_completeness_score` (`:419-441`) also only scores footwear presence.

**Bug 3 — dupatta.** `styling_rules_defaults.py:47` maps `ethnic_dupatta` to slot `accessory`. Accessories attach only when `preferred_accessory_categories` is non-empty (`engine:149`) **and** the item's category is in that set (`:150-152`). The only kinds with a preferred accessory are ceremony/festival/religious, all set to `["accessory_jewellery"]` (`defaults:123,130,135`). No kind lists `ethnic_dupatta` — so a dupatta can never be attached to any candidate, for any occasion. For an anarkali or salwar kameez the dupatta is not optional, so this collides with CLAUDE.md's "ethnic wear is FIRST-CLASS." A data change plus allowing multiple accessories; roughly a 10-line diff.

## Out of scope — Engine v2 owns these

Recorded explicitly so no future Architect re-derives them as new findings:

- **Identical footwear/accessory on every candidate.** `footwear_key`/`accessory_key` (`:127-133`) are functions of the item alone, never of the base, so `sorted(...)[0]` returns the same shoe for all ~72 bases. Fixed by Engine v2 stage ② (wide search) + stage ④ (MMR portfolio diversity).
- **Colour absent from the per-slot capping formula.** `rank_key` (`:110-117`) has no colour term, and capping to `MAX_ITEMS_PER_SLOT = 8` happens at `:119` — before `_colour_harmony_score` is ever called (`:221`). So a colour-optimal combination can be pruned before colour is considered. Fixed by Engine v2 stage ②'s "nothing is pruned before it has been scored on the dimensions that matter."
- **Star-topology colour scoring.** `_colour_harmony_score` (`:444-450`) compares everything to `colored[0]`, whose identity depends on base ordering, so bottom-vs-footwear clashes are never evaluated. Fixed by Engine v2 stage ③'s pairwise scoring.

## Edge Cases & Failure Modes

- Wardrobe where every item has a named colour → engine must still return candidates for non-`wedding_guest` occasions (do not fail closed globally; only where a hard colour exclusion applies)
- Cream/ivory/beige at `wedding_guest` — **open product question, deliberately not decided here.** The current HSV test (`value >= 0.92 and saturation <= 0.12`) likely excludes gold-cream banarasi, which is appropriate Indian wedding-guest wear. Do not widen or narrow the threshold in this ticket without a decision; note it and leave it
- An occasion expecting a layer in a wardrobe with no outerwear → gap flag, not a dropped candidate
- Multiple accessories on one candidate must not break the candidate-count bound or the prompt-payload size budget (~800 tokens for 5 candidates)
- A dupatta as the *only* accessory vs. dupatta + jewellery → both valid; do not force jewellery
