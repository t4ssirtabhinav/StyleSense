# SS-056 — Body Type & Avatar

## Source note (this repo)

Promoted from `docs/competitive/07-EPICS-AND-TICKETS.md`'s portfolio-scope rewrite (2026-08-20). Per `docs/competitive/03-FITS-TEARDOWN.md` §5.8: a finite indexed sprite matrix, not ML, not measurements — the mechanism that makes "inclusive body types" cheap. This ticket exists to unblock `SS-055` (Dressing Room needs a mannequin to render garments on).

## Description

A body/avatar picker: gender presentation × size band × leg-proportion, mapped onto a small finite set of mannequin sprite assets, plus a hairstyle picker. No photo upload, no ML inference, no measurements collected. `users.body_type` already exists (`001_initial.sql:32`, currently unused by anything) as the natural storage column.

## Acceptance Criteria

- A picker UI (gender presentation, size band, leg-proportion — 3 independent axes) that resolves to one of a small, enumerated set of mannequin sprite ids
- Hairstyle + hair-colour picker, independent of body selection
- Selection persists to `users.body_type` (reuse the existing column — confirm its current type/shape before assuming it's free-form text) plus a new column or JSONB shape for hairstyle if `body_type` alone can't carry both — decide and record which
- Asset set is deliberately small for this ticket: enough sprite combinations to prove the mechanism (e.g. 2 gender presentations × 2 size bands × 2 leg-proportions = 8 base sprites, not the full ~24-sprite matrix `06-UIUX-SPEC.md` originally specified) — the full matrix is an asset-production task, not an engineering one, and can grow later without a code change
- No ML, no photo capture, no measurement input anywhere in this flow — if a design pass proposes any of these, it has drifted from this ticket's scope
- Selected avatar renders on a dedicated profile/avatar screen, independent of `SS-055` (this ticket doesn't depend on the Dressing Room existing yet, but is a prerequisite for it)

## Technical Notes

**This ticket ships assets, and asset production is real, non-trivial work** — budget time for actually producing (or sourcing, with a license check) 8 base sprites + a handful of hairstyle overlays, not just the picker UI. Don't let the Architect phase estimate this as pure code.

**Read `users.body_type`'s actual current shape** (`001_initial.sql:32`, `TEXT` — for avatar generation, per its comment, but never populated by any code path) before designing the storage shape.

**Sprite rendering approach:** decide whether sprites are separate PNG assets swapped by picker state, or a single composited image built from layers — this decision affects `SS-055` directly (which will composite garments on top of whatever this ticket produces), so get it right rather than fast.

## Edge Cases & Failure Modes

- A user who never opens this picker — `SS-055` needs a sensible default mannequin to fall back to, not a hard requirement that this screen be visited first
- Gender presentation is a sensitive, user-facing choice — don't default to a binary picker if a non-binary/neutral option is cheap to include at the sprite-asset level; if it's not cheap for this ticket's asset budget, say so explicitly rather than silently shipping a binary-only picker
- Hairstyle options should include options relevant to Indian users (braid, oiled centre-part, pagdi, hijab) per `06-UIUX-SPEC.md`'s asset scope — even in this ticket's trimmed 8-sprite version, don't ship a hairstyle set that's accidentally Western-only
