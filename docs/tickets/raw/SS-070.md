## Description

A single backend-only CLI script, `backend/scripts/ss070_test_users.py`, that manages throwaway test accounts against the live Supabase project through the Admin API. Subcommands:

- `create --label <slug>` — creates an `auth.users` row with a deterministic, prefix-namespaced email (`stylesense-test+<slug>@<test-domain>`) and a freshly generated strong password, printed **once** to stdout. Confirms the `public.users` row that `002_onboarding_completed.sql`'s `handle_new_auth_user` trigger is supposed to create actually exists (query it — do not assume the trigger fired).
- `seed --label <slug> [--items N]` — inserts N `wardrobe_items` rows owned by that user, and optionally flips `onboarding_completed`, so the account lands in a realistic state rather than an empty one.
- `session --label <slug>` — prints a redeemable session (access + refresh token JSON) plus the exact one-line browser-console snippet that installs it into `localStorage` for the running web build. This is the no-UI entry path.
- `list` — lists only accounts this script created (identified by the email prefix **and** an `app_metadata` marker written at create time), never any other user.
- `delete --label <slug>` — deletes the auth user and then **verifies** the cascade by querying `auth.users`, `public.users` and `wardrobe_items` for that id, printing the verification result.

The script is developer tooling. It ships no HTTP route, no mobile code, and nothing importable by the running backend.

## Acceptance Criteria

1. `create --label <slug>` produces a working test account: an `auth.users` row with the generated email and password, and a `public.users` row for the same id — the latter **confirmed by an actual query in the script's own output**, not inferred from the trigger's existence.
2. The generated password is printed exactly once at creation, is at least 16 characters from a CSPRNG, and is never written to any file the repo tracks.
3. `seed --label <slug> --items N` creates exactly N `wardrobe_items` rows owned by that user and no rows owned by anyone else; re-running it is additive and clearly reports the new total.
4. `session --label <slug>` outputs a session that successfully authenticates the running web build with **no login UI used** — verified by actually doing it once (install into `localStorage`, load the app, land on an authenticated screen), not by asserting the token looks right.
5. `list` shows every account created by this script and **zero** accounts it did not create — verified against a project that also contains the developer's own real account.
6. `delete --label <slug>` removes the account and prints a post-delete verification showing zero rows in `auth.users`, `public.users` and `wardrobe_items` for that user id.
7. **Guard rails, each independently tested:** the script refuses to run without an explicit opt-in env var set (e.g. `STYLESENSE_ALLOW_TEST_USER_ADMIN=1`); `delete` refuses any email that does not match the test prefix, with a clear refusal message; `create` refuses a label that already exists rather than producing a second account. No subcommand accepts a raw user id as a delete target.
8. The `service_role` key is read from the environment only. It never appears in source, in printed output, in a committed `.env.example` value, or in an error message.
9. Pytest coverage in `backend/tests/` for the guard rails specifically (delete refuses a non-test email; missing env var blocks every subcommand; duplicate label rejected), with the Supabase Admin client faked — **no live calls from CI**.

## Technical Notes

- Location `backend/scripts/`, matching the existing precedent (`ss015_verify_wear_history.py`, `ss026_verify_config_live_reload.py`, `ss033_verify_impression_logging.py`, …). Same shape: standalone, run by hand, not imported by `app.main`.
- **`[TRAINED KNOWLEDGE — verify before writing code]`** The intended mechanisms are `supabase-py`'s admin API (`auth.admin.create_user` with an `email_confirm` flag to skip confirmation, `auth.admin.delete_user`, `auth.admin.generate_link` for the magic-link → session redemption path). The exact method names, parameter names and return shapes **must be checked against the installed `supabase-py` version's source before any of them is written** — this repo has been bitten by exactly this class of assumption twice (`BL-051`: R2 presigned POST returned `501 NotImplemented` against a documented-in-memory API; SS-012: two dead SDK/model names shipped into a design doc). Per `docs/OPERATOR_RULEBOOK.md` §E, label what was verified and how.
- The `app_metadata` marker is what makes `list`/`delete` safe — an email-prefix check alone can be defeated by a real user who happens to sign up with a similar address once SS-072 ships. Use both.
- Deletion of `auth.users` cascades to `public.users` via the FK from `001_initial.sql`; `wardrobe_items` cascades from `public.users`. **Verify this is actually true against the live schema rather than trusting the cascade** — AC #6 exists because an uncascaded orphan is silent.
- The script is a **second reachable path into `BL-169`'s landmine**: creating a test account whose email already exists on a different `public.users` row aborts the auth insert inside a `SECURITY DEFINER` trigger with an opaque `500 Database error saving new user`. Until SS-072's migration `021` hardens that trigger, this script should pre-check `public.users` for the email and refuse with a clear message. Keep the pre-check after `021` lands — belt and braces, and it produces a better message than a raised exception.

## Edge Cases & Failure Modes

- **Wrong project.** The `service_role` key in `.env` points at whichever project is configured; there is only one live project today, but that will not always be true. The script should print the project ref it is about to act on and require confirmation (or an explicit `--project-ref` match) before any destructive subcommand.
- **R2 objects are not cleaned up.** Deleting a seeded user removes the DB rows but leaves any R2 objects behind — `BL-068`/SS-015 built R2 cleanup into the `DELETE /wardrobe/items/{id}` endpoint, which this script does not call. Either seed with placeholder image URLs that never touch R2 (preferred, simplest) or state the leak plainly in the script's own output.
- **Session artifact expiry.** The printed access token expires (~1h); the refresh token outlives it. A stale artifact should fail with "expired, re-run `session --label`", not with a confusing auth error inside the app.
- **Partial create.** If the `auth.users` insert succeeds but the trigger's `public.users` insert does not (the `BL-169` case, or any trigger failure), the account exists in a broken half-state. AC #1's query is what detects it; the script should say so loudly and offer `delete --label` as the remedy rather than leaving a half-user behind.
- **Concurrent runs.** Two `create` invocations with the same label racing each other: the second should lose on the email unique constraint and report it cleanly, not crash with a raw driver traceback.
- **`list` against a project with many real users.** Must page correctly rather than silently showing only the first page — a `list` that quietly truncates is what makes a later `delete` sweep miss accounts.
- **Someone runs `delete` against a real account by editing the prefix constant.** Not defensible in code; note in the script's docstring that the prefix constant is a safety device, not a configuration knob.
