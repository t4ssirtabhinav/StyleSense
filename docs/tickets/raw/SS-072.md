# SS-072 — Email/Password Sign-Up & Sign-In

## Source note (this repo)

Created by `/new-feature` intake Stage 2 (2026-08-15), continuing the Stage 1 impact analysis run 2026-08-14 on "additional sign-up/login methods (Google SSO + email/password)" — recorded in `docs/worklog/README.md`'s auth-intake paragraph and in `docs/BACKLOG.md` rows `BL-167`–`BL-172`. Not from `init documents/architecture-hld-lld.html`, which states the opposite (see below), and not from `init documents/epics-tickets.html`.

**Why this ticket exists.** Phone OTP is this product's correct India-first default, and it stays the default. But it cannot deliver a single real SMS today: TRAI DLT registration is unresolved (`BL-001`, re-verified 2026-08-14 — MSG91 still requires a custom Send-SMS-Hook Edge Function, and DLT applies to the destination number regardless of vendor). Email/password needs no vendor, no DLT, and no external provisioning, which is why Stage 1 recommended it over Google SSO for the 4-5 known beta users. **Google SSO was scoped in the same intake and deliberately deferred** by the user (external provisioning plus a blocked native path via `BL-047`, marginal value over this ticket at this user count); no SS-ID is reserved for it — whoever picks it up takes the next available ID then.

**This ticket contradicts the original architecture doc, and that is recorded.** `init documents/architecture-hld-lld.html`'s Security Architecture section (line 865) states "India users prefer phone-first auth… No password storage needed." Password storage (Supabase-managed) now exists. Logged as `AMEND-005` in `docs/ARCHITECTURE_AMENDMENTS.md`.

**Risk: high — justified against `docs/OPERATOR_RULEBOOK.md` §C2.** Three separate one-way doors in one ticket: it is an authentication method (credential handling, account enumeration surface); it stores passwords; and it ships **migration `021`**, which rewrites a `SECURITY DEFINER` trigger firing on `auth.users` inserts — i.e. a function that can abort the signup transaction of *every* auth method, phone included, if it is wrong. Full lane, every gate.

**Settled decisions this ticket must implement as written (from the 2026-08-14 sign-off — do not re-litigate):**
- **Email confirmation is OFF.** Signup completes and returns a live session with no verification step.
- **Duplicate email is rejected outright, never merged** — at both the client and the database.
- **Account linking is out of scope** but must not be precluded (`BL-172`).

## Description

Adds email/password as the second method in SS-071's login method registry, plus a database-side hardening of the auto-provisioning trigger.

**Screen.** One route, `app/(auth)/email-auth.tsx`, with sign-in and create-account modes sharing an email field, a password field and validation. Reached from the method chooser SS-071 built; phone OTP remains the primary/default method on that screen. Follows SS-003's established patterns rather than inventing new ones — typed `AuthErrorCode` values, `Input` error states, `useMutation`-backed queries in `auth.queries.ts` over service functions in `auth.service.ts`.

**Email confirmation off — a deliberate, stated tradeoff, not a discovery.** With Supabase's "Confirm email" setting disabled, `signUp` returns a live session immediately and no verification email is ever sent. The cost, stated plainly here so nobody has to rediscover it: **an unverified email is accepted at signup**, so a user who mistypes their address gets a working account tied to an address they do not control, and there is no email-based recovery path for it. Accepted for a 4-5 person beta where the operator knows every user; it is not an acceptable posture for public signup, and turning confirmation on later is a real, separate piece of work (it changes `signUp`'s return shape to a session-less "check your email" state, which this ticket's flow does not handle). Recorded as `BL-174`.

**Duplicate email — rejected at two layers.** The client maps Supabase's own already-registered error to specific, actionable copy. Independently, migration `021` hardens `handle_new_auth_user` (from `002_onboarding_completed.sql`), which today does `INSERT INTO public.users (id, phone, email) VALUES (NEW.id, NEW.phone, NEW.email) ON CONFLICT (id) DO NOTHING` — a guard on `id` only, with **no guard on `public.users.email UNIQUE`** (`001_initial.sql:26`). A second auth user carrying an already-present email therefore raises a unique violation *inside* the trigger and aborts the auth signup with an opaque `500 Database error saving new user` (`BL-169`). The client-side check alone is not sufficient defence — it does not cover races, and it does not cover future entry points (SS-070's admin script reaches the same trigger today).

## Acceptance Criteria

1. The login method chooser offers an email method alongside phone OTP; phone remains the visually primary/default path. Selecting email reaches a screen supporting both **Create account** and **Sign in**, switchable without losing the typed email.
2. **Sign-up succeeds with no verification step.** A new email plus a valid password creates an account and lands the user in the app with a live session, routed by SS-071's shared post-auth mechanism (new user → `/onboarding`). No "check your email" state is ever shown, because none exists.
3. **Duplicate email is rejected with specific, actionable copy.** Attempting to sign up with an email already registered by *any* provider fails with a message of the form "This email is already registered — sign in instead", together with a control that switches to sign-in mode with the email prefilled. The raw string `Database error saving new user`, a bare `500`, and any unhandled error shape must never reach the user.
4. **Migration `021` hardens `handle_new_auth_user`.** A duplicate-email insert into `auth.users` is rejected by the trigger with an identifiable, deterministic error and the **entire transaction rolls back** — no orphaned `auth.users` row, no partial or merged `public.users` row, no silent overwrite of the existing owner's email. Verified **live against the project by actually attempting a duplicate**, not asserted from the SQL.
5. **The phone OTP path is provably unaffected by migration `021`.** A phone-only signup (NULL email) still auto-provisions its `public.users` row exactly as before — verified live, and pinned by a test. This AC exists because `021` touches the trigger that every auth method's signup transaction runs through.
6. **Sign-in works and persists.** Correct email + password creates a session persisted by the same mechanism phone OTP uses, and SS-071's shared routing sends a completed user to `/` and an incomplete one to `/onboarding`.
7. **No account enumeration on sign-in.** A wrong password and an unknown email produce the *same* generic message ("Incorrect email or password"), with no timing or copy difference between them. The signup duplicate case (AC #3) is deliberately specific — that asymmetry is intentional and stated, since a signup form necessarily reveals whether an address is taken.
8. Client-side validation before any network call: email shape and trimming, password minimum length, both surfaced as inline `Input` error states in SS-003's established style. `AuthErrorCode` gains only additive members (e.g. `email_already_registered`, `invalid_credentials`, `weak_password`); existing codes and copy are untouched.
9. `register` fires through the existing analytics hook with `method: 'email_password'`, matching the existing `method: 'phone_otp'` call in `verify-otp.tsx`.
10. **No dead ends.** There is no "Forgot password?" affordance that leads nowhere. Password reset is explicitly out of scope for this ticket (it would be this app's first outbound-email dependency) and is logged as `BL-173`; the ticket ships without it knowingly rather than shipping a link to a screen that does not exist.
11. `tsc`, `biome` and the full jest suite clean; migration `021` applied and verified live per this repo's convention (`BL-110`'s serialization rule — `021` is this ticket's reserved slot, nothing else may take it).

## Technical Notes

- **Migration `021` shape.** The trigger should explicitly check for an existing `public.users` row owned by a *different* id whose email matches case-insensitively, and `RAISE EXCEPTION` with a recognizable message/SQLSTATE so the client can map it deterministically — rather than letting the unique constraint fire from inside the `SECURITY DEFINER` body. Aborting the transaction *is* the correct outcome here: "rejected outright, never merged" means no account is created at all. Keep the existing `ON CONFLICT (id) DO NOTHING` behaviour for the id case (re-entrancy) unchanged.
- **Do not add `NOT NULL` to `public.users.email` or `phone`, and do not merge rows.** `phone` is already nullable and Postgres permits multiple NULLs under `UNIQUE`, so an email-only identity is representable today with no column change. Preserving this is what keeps a future authenticated `linkIdentity()`-style flow buildable (`BL-172`): the trigger fires `AFTER INSERT` only, so an explicit, authenticated "add an email to my account" `UPDATE` later is unobstructed by it.
- **A case-insensitive functional unique index on `email` is optional and conditional.** The trigger's `lower()` comparison covers the semantics. If an index is added, the migration must first verify zero pre-existing case-variant duplicates in live data and abort loudly if any exist — do not add an index that can fail mid-migration on real rows.
- **`[TRAINED KNOWLEDGE — verify before writing code]`** The intended client calls are `supabase.auth.signUp({ email, password })` and `supabase.auth.signInWithPassword({ email, password })`, with `signUp` returning a live session only when Confirm-email is disabled, and a duplicate producing an already-registered error. **Every one of those claims must be checked against the installed `@supabase/supabase-js` source and the live project's actual settings before the flow is built** (`docs/OPERATOR_RULEBOOK.md` §E). Supabase has also, at times, obscured duplicate-signup responses as an anti-enumeration measure — if that is what the live project actually does, AC #3's copy must be reconciled with observed behaviour rather than assumed.
- **Confirm-email is a live dashboard setting, not code.** The Developer must check the live project's current value and turn confirmation **off**, and record what it was before. If it is on when the flow runs, `signUp` returns `session: null` and the screen would otherwise hang or blank — the code must handle `session === null` with an explicit error regardless, as a defence against the setting being flipped later.
- **No backend change.** `backend/dependencies/auth.py::get_current_user_id` verifies JWTs through `supabase-py` and is provider-agnostic; all RLS policies key on `auth.uid()`. An email/password session authenticates through the existing dependency and every existing policy with zero changes. Do not open the backend surface in this ticket (`BL-052`'s `/generate` stub stays as-is and out of scope).
- **Password rules.** Supabase enforces its own project-level minimum. State the client-side rule explicitly, keep it at or above the project setting, and map Supabase's own weak-password rejection to a clear message rather than a generic failure.
- Regenerate `types/supabase.ts` only if `021` changes a type surface (it should not — it rewrites a function, not a table). `BL-143` already tracks that file being stale; do not fold that cleanup into this ticket.

## Edge Cases & Failure Modes

- **Email differing only in case or surrounding whitespace** (`User@x.com` vs `user@x.com`, trailing space from autofill): trim and normalise client-side; the trigger's check is case-insensitive. Both must land on AC #3's message, not on a second account.
- **A phone-first user signs up with an email.** Per `BL-172` this creates a **second, separate account** with its own empty wardrobe — accepted, not fought, and not silently merged. Do not build linking UI; do not warn speculatively about an account the app cannot prove exists.
- **Confirm-email is ON in the live project.** `signUp` resolves with `session: null` and no error. Must produce an explicit, honest message, never a blank screen or an infinite spinner.
- **Signup rate limiting.** Supabase throttles repeated signup/sign-in attempts; map to the existing `rate_limited` code and copy from SS-003 rather than a new string.
- **Offline / network failure** at either call: existing `network_error` mapping and copy, no crash, no partially-navigated state.
- **A duplicate that races the client check.** Two signups for the same email in flight simultaneously: one wins, the other must surface AC #3's message via the *server* error path — this is precisely the case the client check cannot cover and migration `021` exists for.
- **Web password-manager autofill** filling both fields (or filling the sign-in form while in sign-up mode): mode switching must not strand stale credentials, and the submit handler must read current values rather than cached state.
- **A user who forgets their password** has no recovery path at all in this ticket (AC #10, `BL-173`). For the beta this is recoverable operationally — SS-070's admin script can reset or recreate the account — and that is the stated mitigation, not a claim that the gap does not exist.
- **`BL-169`'s landmine is reachable from SS-070's seed script too.** Once `021` lands, the script's failure mode there becomes a clean identifiable error instead of an opaque `500`; SS-070's own pre-check stays as the better-message layer.
- **Migration rollback story.** `021` replaces a function; the previous definition is recoverable from `002_onboarding_completed.sql` verbatim. Note it in the design doc so a rollback is a copy-paste rather than a reconstruction.
