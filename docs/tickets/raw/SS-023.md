# SS-023 — Outfit Suggestion UI (Occasion Flow)

`[Feature]` `[P1]` `[Sprint 5]` `[2 pts]` Est: 6h
Depends on: SS-020

## Description

Style tab: occasion selector (icon grid), optional weather context (auto-detected via city, from SS-022 if ready), "Get suggestions" CTA. Loading state with animated skeleton cards. Result: swipeable outfit cards (Tinder-style accept/reject). Each card shows stacked item thumbnails, occasion score badge, AI reasoning snippet. Accept saves to a new `outfits` table.

## Acceptance Criteria

- Occasion selection to results in max 2 taps
- Swipe right saves outfit; swipe left dismisses
- AI reasoning is expandable in the card
- Share button on an accepted outfit (PNG export)
- "Not quite right — regenerate" refreshes suggestions

## Technical Notes

- This is the ticket that creates the `outfits` table (first writer to it) — SS-014/SS-015's Architect passes both flagged their own "item in a saved outfit" edge cases as forward-looking-only because this table didn't exist yet. Revisit those two tickets' deferred edge cases (item removed/deleted while referenced in a saved outfit) as part of this ticket's own schema design, not as new scope invented here.
- PNG export: check whether an existing repo pattern exists (none does yet) before picking a library — first ticket needing client-side image composition/export
- New `components/ui/` primitives only if the swipe-card interaction genuinely needs one not already in the design system — check SS-008's kit first

## Edge Cases & Failure Modes

- User has zero wardrobe items — CTA should route to upload flow (SS-013) rather than call the suggestion endpoint at all
- All 3 suggestions rejected (swiped left) — "regenerate" should not return the exact same 3 outfits from cache; needs either a cache-bypass flag or a larger candidate pool to draw a fresh 3 from
