## Description

`app/(auth)/onboarding.tsx`'s `showResumePrompt` condition currently is:

```ts
const showResumePrompt =
  progressQuery.isSuccess &&
  Boolean(progressQuery.data?.fullName) &&
  !hasDismissedResumePrompt;
```

The comment above it claims "routing to this screen at all already implies `onboarding_completed: false`" — true for the normal entry path (`verify-otp.tsx` only routes here for an incomplete user), but **not** true for direct-URL entry or a deep link straight to `/onboarding`, which SS-007's Architect confirmed is no longer even reachable from Profile (that button now goes to `/edit-preferences`) but is still reachable by typing the URL directly or via an old deep link. A fully-onboarded user landing here this way sees "Welcome back!" framing instead of something that makes sense for someone who already finished.

`OnboardingProgress` already has an `onboardingCompleted` field (added in SS-007) that isn't being read here — the fix is to gate `showResumePrompt` on it also being `false`.

## Acceptance Criteria

- `showResumePrompt` is `false` whenever `progressQuery.data?.onboardingCompleted` is `true`, regardless of `fullName`
- Existing resume-prompt behavior for a genuinely incomplete user (started but didn't finish) is unchanged
- A completed user who reaches `/onboarding` via direct URL/deep link sees the wizard pre-filled with their saved answers (existing hydrate behavior) without the "Welcome back!" interstitial
- Existing onboarding tests continue to pass; add a test case for a completed user hitting this route directly

## Technical Notes

- One-line condition change: add `!progressQuery.data?.onboardingCompleted &&` to `showResumePrompt`'s definition (`app/(auth)/onboarding.tsx`, ~line 100)
- Remove or correct the now-inaccurate comment claiming this routing precondition always holds

## Edge Cases & Failure Modes

- `progressQuery` still loading (`isSuccess` false) when the screen first mounts: unchanged existing behavior (prompt doesn't show until the query resolves)
- User completed onboarding, then an admin/support flow resets `onboarding_completed` to `false` for a re-onboard: resume prompt correctly reappears (condition re-evaluates from live data, not cached)
