# SS-028 — Multi-Provider AI Router & Gemini Styling Adapters

`[Feature]` `[P0]` `[Sprint 5]` `[5 pts]` Est: 27h
Depends on: SS-006, SS-026
Risk: high

## Description

A routing layer in front of `IStylingProvider` that picks a provider+model per request based on **three** inputs: task complexity (cost/quality), provider health and remaining quota (capacity), and user tier (product). Adds `GeminiStylingAdapter` alongside the existing port so Gemini and Anthropic both serve styling traffic.

Per `CLAUDE.md`'s Open/Closed rule, **`IStylingProvider` is not modified** — SS-006 already defined it, and this ticket is exactly the swap-in case that abstraction exists for. It is the first real proof the ports architecture pays for itself.

## Acceptance Criteria

- `GeminiStylingAdapter` implements the existing `IStylingProvider` unchanged, **parameterised by model ID** — "use Flash-Lite" vs "use Sonnet" is a config value, not a class
- Router selects provider+model from the `app_config` routing table (SS-026); changing the table changes routing **without a redeploy**
- Provider failure or quota exhaustion fails over to the alternate provider and returns a real answer. **This satisfies SS-020's existing AC — "graceful fallback if the AI provider is down, never a hard error to the user" — better than the rule-based degradation that AC was written for**
- Per-provider quota tracking (RPM/TPM) with ceilings read from config, not hardcoded
- Every call logs `user_id`, `provider`, `model`, `tokens_used`, `latency_ms`, `routing_reason` per `CLAUDE.md`
- Routing decisions are observable — a dashboard-able log line, so silent drift to an expensive model is caught within a day, not on a bill
- Both adapters pass an identical contract test suite against the port

## Edge Cases & Failure Modes

- Both providers down → degrade to SS-027's deterministic candidates with rule-based reasoning. **The pre-filter is the last line of defence, and it always works** — no network, no quota
- Provider returns malformed/unparseable JSON → retry once on the same provider, then fail over, then degrade. Never surface a parse error to the user
- Quota exhausted mid-request-burst → route new requests to the alternate provider; do not queue behind an exhausted pool
- Config routing table is malformed → coded default routing (SS-026's guarantee). A bad config row must never take the feature offline
- Failover masks a persistent outage — if provider A has been failing for hours, that must alert, not silently cost 3× on provider B forever
- Latency differs by provider; SS-020's `<4s` cold-call AC must hold on the **slowest** path in the routing table, not the fastest
