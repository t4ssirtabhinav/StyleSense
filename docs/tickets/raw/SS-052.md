## Description

A wardrobe insights screen with three sections — Composition (what's in the wardrobe, by category/colour/fabric), Usage (worn vs. never-worn, versatility), Value (cost-per-wear distribution, already-computed `wardrobe_items.cost_per_wear` aggregated) — built entirely from existing and `SS-040`-added columns, no new AI calls.

## Acceptance Criteria

- **Composition**: category breakdown (using `SS-044`'s now-resolving `garment_types` registry for grouping, not the raw 21-value enum, so ethnic vs. western vs. accessories groups sensibly), colour distribution, fabric distribution
- **Usage**: worn vs. never-worn split, `not_yet_worn` count (reuses `SS-048`'s rail definition — one query, not two), and **versatility**: `COUNT(DISTINCT outfit_id) GROUP BY item_id` over `outfits.item_ids` — the single highest-value metric in the whole screen per the competitive analysis, and cheap
- **Value**: cost-per-wear distribution using the existing `GENERATED` `wardrobe_items.cost_per_wear` column — no reimplementation of that formula
- Every metric card states its formula and its exclusions in a `?` tooltip (e.g. "excludes archived and do-not-style items, excludes wishlist-status outfits") — per `04-INDYX-TEARDOWN.md` §10.3's finding that this is what makes Indyx's analytics trustworthy where competitors' aren't
- `SS-057`'s `status='wishlist'` outfits excluded from every usage/versatility metric
- `SS-040`'s `is_archived`/`do_not_style` items excluded from composition/value metrics (an archived item shouldn't count toward "your wardrobe is 40% kurtas")
- Currency formatted `₹1,23,456` per `.claude/CLAUDE.md`'s India-specific rule — `Intl.NumberFormat('en-IN', {...})`, matching the pattern `SS-014`/`SS-015` already established
- "Undefined"/unknown is always a visible slice in any breakdown chart (e.g. items with no `fabric` set) rather than silently dropped — per `04-INDYX-TEARDOWN.md`'s own finding on this exact failure mode

## Technical Notes

**Load `dataviz` before writing chart code — this is stated twice for emphasis because it's a repo-level requirement, not a suggestion.**

**Versatility's query is genuinely one line** (`SELECT unnest(item_ids) AS item_id, COUNT(DISTINCT id) FROM outfits WHERE status != 'wishlist' GROUP BY item_id`) — don't over-engineer this into a service class; it's the highest-value-per-line-of-code metric in the ticket.

**Composition grouping should use the registry, not the raw enum** — `SS-044` made `garment_types` resolve for every live category; reuse that resolution rather than grouping on the 21 raw enum strings, which would put `ethnic_saree` and `ethnic_lehenga` in unrelated buckets instead of both reading as "ethnic."

**Check `docs/BACKLOG.md`'s tokens-tagged rows before designing charts** — `BL-153`/`BL-154`/`BL-155` (dataviz palette reconciliation, dark-mode tokens, marigold contrast) were logged specifically against this ticket's original draft; verify current status rather than assuming resolved.

## Edge Cases & Failure Modes

- A brand-new wardrobe with too few items for a meaningful chart (e.g. 3 items) — degrade to a simple list/count rather than rendering a chart with 3 data points that looks broken
- An item with `wear_count = 0` that's also `do_not_style = true` — excluded from composition/value (per the AC above) but should it still count in "never worn"? Decide and record — likely still excluded, since a do-not-style item was never eligible to be worn via the app's suggestions in the first place
- Cost-per-wear on an item with `purchase_price = NULL` (price not recorded) — must not silently coerce to 0 or crash the aggregate; exclude from the value metric and reflect the exclusion count in the tooltip
- Versatility metric on an item that only appears in `wishlist`-status outfits — `COUNT(DISTINCT outfit_id)` should read as 0 for real usage purposes once wishlist outfits are filtered out, not accidentally count them
