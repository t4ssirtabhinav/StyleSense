Depends on: SS-015, SS-025

## Source note (this repo)

Created by `/new-feature` intake 2026-07-30 from [`docs/proposals/STYLING-ENGINE-V2.md`](../../proposals/STYLING-ENGINE-V2.md) §5 stage ③ (commit `a95059f`), **Wave 1.5**. Originated as a user observation: *"when an item was worn, was it recently worn for this same occasion or has time passed and it can now be re-suggested."* That is a genuinely better novelty signal than the global recency the engine uses today, and it is unimplementable on the current schema — `wardrobe_item_wears` (migration `006`) records only `item_id`, `user_id`, `worn_on`, `created_at`.

**Stage 1 analysis flagged this as the ticket most under-estimated by its own description.** It reads as two additive columns. It is a product decision on a shipped table with an idempotency constraint, a stats trigger, and a downstream generated money column.

## Description

Record *which occasion* an item was worn for, and *which outfit* it was part of, so wear-recency becomes occasion-scoped: "you wore this kurta to `office` on Tuesday, but it is fresh for `festival`."

This is also what lets a deterministic engine stop repeating itself without abandoning determinism — recent-wear-per-occasion becomes part of the engine's **input**, so same-input-same-output still holds while the output naturally rotates.

## Acceptance Criteria

- A wear row can record which occasion the item was worn for, normalised against the `occasions` registry **at the DB boundary** (aliases mapped, unknowns kept and captured — never dropped, never a failed write)
- A wear row can reference the outfit it was part of; **deleting that outfit does not delete or alter the wear row**
- **The same item can be logged as worn for two different occasions on the same date** (product decision, confirmed by the user 2026-07-30 — e.g. `office` in the morning, `puja` in the evening)
- Repeat "Mark Worn" taps for the *same* item + date + occasion still cannot inflate `wear_count` — `BL-071`'s idempotency guarantee must not regress, and a test must prove it under the widened constraint
- `wear_count`, `last_worn_at` and `cost_per_wear` are **unchanged for every pre-existing row** after the migration — asserted against a captured before/after fixture (the SS-025 §7.4 pattern)
- The engine can answer "days since this item was worn *for this occasion*" distinctly from "days since worn at all"
- Existing wear rows backfill to `occasion_key = NULL`, and every consumer treats `NULL` as "unknown occasion" — never as a match for any occasion

## Technical Notes

**Migration `014_wear_occasion_awareness.sql`** — assigned up front. `011` SS-029, `012` SS-033, `013` SS-034, `015` SS-036.

**⚠️ The uniqueness constraint is the whole risk of this ticket.** `006_wardrobe_item_wears.sql:28` is `CONSTRAINT wardrobe_item_wears_one_per_day UNIQUE (item_id, worn_on)`, and its in-file comment states its purpose: *"At most one wear per item per day: makes the 'Mark Worn' tap idempotent and stops repeat taps inflating the count (BL-071's primary complaint)."*

Given the confirmed product decision (multi-occasion same-day wears ARE allowed), the constraint must widen to include `occasion_key` — and **a naive widening re-opens `BL-071`**, because Postgres treats every `NULL` as distinct in a unique index, permitting unlimited duplicate `NULL`-occasion rows per item per day.

- **Preferred:** `UNIQUE (item_id, worn_on, occasion_key) NULLS NOT DISTINCT` (PG15+).
- **Version status:** `supabase/config.toml:42` declares `major_version = 17` `[VERIFIED 2026-07-30 — local stack config only]`. The **live remote project's** version is **UNVERIFIED** — an MCP query against `mefpfykuinasgkpfhmzk` was permission-denied. **Developer precondition: confirm the live project's `server_version_num` before writing this DDL.**
- **Fallback if remote is <15:** a `COALESCE`-expression unique index (e.g. on `COALESCE(occasion_key, '')`). Document whichever is used and why.

**Why a wrong call here is expensive and silent:** the constraint sits upstream of the `AFTER INSERT/UPDATE/DELETE` trigger (`006:78-80`) that recomputes `wear_count`, which is the input to the **`cost_per_wear` GENERATED column** (`001_initial.sql:63-68`). A double-counted wear silently *halves* a money figure — the same silent-failure class `BL-075` already flags for money units.

**`occasion_key` is a NEW occasion write boundary** — exactly the standing obligation `BL-078` logs. `008_occasion_columns_to_text.sql:60-70`'s `occasion_scalar_normalize_trigger` is **hardcoded to a column named `occasion`**, so this needs a new or parameterised `SECURITY DEFINER` function (with `SET search_path = public, pg_temp`), not a reuse.

**`outfit_id` must follow this repo's established composite-FK convention.** `006:22-24` used `FOREIGN KEY (item_id, user_id) REFERENCES wardrobe_items(id, user_id)` for defence-in-depth, which required adding `UNIQUE (id, user_id)` to `wardrobe_items` (`006:13-14`). Matching that for `outfits` (`001:80-94`) needs the same additive unique constraint. Silently dropping the pattern would regress a convention this repo adopted deliberately.

**`ON DELETE SET NULL` for `outfit_id`, never `CASCADE`.** The wear happened even if the outfit is later deleted; cascading would corrupt `wear_count` and `cost_per_wear`.

**Frontend:** Mark Worn / wear-history UI gains an occasion picker (`mobile/features/wardrobe/`). Occasion selection must be optional — a user who just taps "worn" gets `NULL`, which is a valid state, not a validation error.

**Parallel `db push` hazard:** serialize the push; expect sibling tickets' objects as `db diff --linked` drift; report the exact diff, never loosen the CI filter (`BL-060`).

## Edge Cases & Failure Modes

- Same item, same day, two different occasions → both rows accepted (the confirmed decision)
- Same item, same day, same occasion, repeat taps → idempotent, count not inflated
- Same item, same day, one row with `occasion_key = NULL` and one with `'office'` → must not permit unlimited NULL duplicates
- An occasion that is later deactivated or deleted from the registry → historical wear rows must survive with their recorded key (history is not re-writable); `ON DELETE RESTRICT` on the registry side, consistent with `occasions.parent_key`
- An unknown/unmapped occasion slug on write → stored + captured, never dropped, never a failed write (`BL-078`'s write-boundary matrix)
- Backfilled `NULL` occasion rows must not be counted as a match when the engine asks "worn for this occasion recently?" — `NULL` means unknown, not "no"
- Deleting an outfit → wear rows survive with `outfit_id = NULL`; `wear_count` and `cost_per_wear` unchanged
- A wear logged for an item the user has since deleted → existing `ON DELETE CASCADE` from `wardrobe_items` still applies; do not change it in this ticket
