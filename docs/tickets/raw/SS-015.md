# SS-015 — Wardrobe Item Edit, Delete & Mark Worn

`[Feature]` `[P1]` `[Sprint 4]` `[1 pt]` Est: 4h
Depends on: SS-014

## Description

CRUD on wardrobe items via the detail BottomSheet. **Edit:** the same tag chips as the upload review screen (category dropdown, occasion multi-select, colour picker, fabric, pattern) + brand input, `purchase_price` (₹ formatting), `purchase_date`, `user_notes` (max 500 chars). Save via `PATCH /wardrobe/items/:id`.

**Delete:** confirmation dialog. Cascades removal from outfit references. R2 cleanup async. **Mark Worn:** single tap increments `wear_count` + sets `last_worn_at`. Shows a toast: "Outfit logged! Cost per wear: ₹X". Favourite toggle with a heart animation.

## Acceptance Criteria

- Edit mode switches to editable tag fields in the BottomSheet
- Category changeable via dropdown; saves to the DB immediately on confirm
- Purchase price in Indian rupee format (₹1,23,456 via `Intl.NumberFormat('en-IN')`)
- Delete shows a confirmation; confirmed delete removes the item from the grid immediately (optimistic UI)
- "Mark Worn" increments `wear_count`, shows a toast with the updated cost per wear
- Favourite toggle is instant with a heart animation (optimistic)
- User notes max 500 characters with a character count indicator

## Technical Notes

- `PATCH` via the Supabase client (RLS ensures the user owns the item)
- Optimistic updates: Zustand + React Query cache update immediately, revert on error
- R2 cleanup on delete: Supabase Database Webhook or Edge Function (async)

## Edge Cases & Failure Modes

- Item in a saved outfit: changes propagate to the outfit display
- Deleting an item that's in an outfit: outfit marks the item "removed", suggests a replacement
- Purchase price of 0: valid (gifted); `cost_per_wear` handles it gracefully

## Status note (this repo)

Straightforward CRUD extension of SS-014's detail sheet — no new schema, no new routes. The "item in a saved outfit" edge cases are forward-looking only: `outfits`/`suggestion_sessions` (Epic 3) don't exist yet at this point in the sprint, so those specific edge cases have nothing to actually exercise them yet. Note this explicitly in the design doc rather than building dead code against tables no writer populates yet — implement the item-level CRUD now, defer the outfit-cascade behavior's actual wiring to whichever Epic 3 ticket first writes to `outfits`.
