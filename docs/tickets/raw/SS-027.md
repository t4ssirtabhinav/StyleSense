# SS-027 — Styling Rules Engine & Deterministic Pre-Filter

`[Feature]` `[P0]` `[Sprint 5]` `[4 pts]` Est: 22h
Depends on: SS-025
Risk: med

## Description

A pure, deterministic module that generates and scores candidate outfit combinations from a wardrobe **before** any LLM is involved. The AI's job changes from *"search a 200-item wardrobe for valid combinations and reason about them"* to *"rank 5 pre-scored candidates and write a sentence about each."*

This is the highest-value, lowest-risk ticket in the Epic 3 foundation: no external dependencies, no network, fully unit-testable, and it delivers ~6× token reduction on **any** provider — a saving that survives every future vendor change, price rise and model deprecation.

## Acceptance Criteria

- Given a wardrobe and an occasion, returns a ranked list of candidate outfits with scores and per-rule explanations — **with zero network calls**
- Every candidate references only real `wardrobe_item.id` values from the input set. **This makes SS-020's "item IDs must not be hallucinated" AC structurally impossible to fail** rather than prompt-dependent
- Occasion rules are read from `occasions.styling_rules` (SS-025), not hardcoded
- `wedding_guest` never surfaces a white-dominant candidate — enforced in code, not in a prompt
- Handles wardrobes of 1 to 500+ items within a bounded time budget; candidate generation does not combinatorially explode
- Fewer than 3 valid candidates → returns what exists with an honest `limited_options` flag. Never pads, never invents
- Deterministic: same input, same output, every time. Property-tested

## Technical Notes

**One rules module, consumed twice — non-negotiable.** Colour theory, formality matching and occasion constraints live in a single `styling_rules` module used by *both* the scorer and the prompt template. Two copies will drift, and drifted style rules are invisible until a user is shown white for a wedding. This is the most likely long-term maintenance failure in the whole design; the Architect pass must make it structurally impossible, not merely discouraged.

**Scoring inputs:** occasion formality vs item formality (`occasions.formality`), colour harmony, category completeness (top/bottom/footwear/outerwear per occasion `kind`), season/weather fit, wear recency (favour under-worn items — this is also the `cost_per_wear` hook shipped in SS-015), and user `style_preferences`.

**Bound the combinatorics.** Generate candidates via constrained selection per slot, not a full cross-product. A 200-item wardrobe must not produce a 10⁶-candidate pool. Cap per-slot options by score before combining.

**`pattern`/`fabric` are free-text with no canonical vocabulary (`BL-064`, open).** Treat them as advisory scoring hints, never hard filters — an unexpected string must not silently exclude an item.

**Output shape is the LLM's input contract.** ~5 candidates × compact item descriptors ≈ 800 tokens `[ESTIMATE]`. Keep it tight; this number is the entire cost case.

## Edge Cases & Failure Modes

- Wardrobe smaller than the occasion's required slots (e.g. no footwear at all) → partial candidates + explicit gap flags, which SS-024's "missing footwear" alert and future gap-analysis features consume
- All items tagged for one occasion only, request is for another → fall back to formality-adjacent items with a lowered score rather than returning nothing
- `style_preferences: null` (user skipped onboarding) → generic scoring weights, per SS-006's spec. Not an error
- An occasion with empty `styling_rules` (newly inserted via SS-025) → sane defaults from `kind` + `formality`. **A new occasion must work the moment it is inserted, before anyone authors rules for it** — otherwise the extensibility promise is hollow
- Items with `NULL` colour or category (tagging failed / in progress, per SS-005's processing status) → excluded from candidates but counted in the gap report
