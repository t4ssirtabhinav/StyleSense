# SS-071 — Auth Foundation: Multi-Provider Entry Points, Sign-Out, Onboarding-Routing Hoist

`[Feature]` `[P0]` `[Sprint 7]` `[2 pts]` Est: 6h
Depends on: SS-003, SS-004, SS-005

## Source note (this repo)

Created by `/new-feature` intake Stage 2 (2026-08-15), continuing the Stage 1 impact analysis run 2026-08-14 on "additional sign-up/login methods (Google SSO + email/password)" — recorded in `docs/worklog/README.md`'s auth-intake paragraph and in `docs/BACKLOG.md` rows `BL-167`–`BL-172`. Not from `init documents/architecture-hld-lld.html` (which specifies phone-first auth and nothing else) and not from `init documents/epics-tickets.html`.

**What gap this closes.** Stage 1 went looking for what it would take to add a second sign-in method and found that the *first* one was never finished. Two defects, both verified against the repo on 2026-08-14, both pre-existing and independent of any new auth method:

1. **There is no sign-out anywhere in the app** (`BL-167`) — zero `signOut` call sites in `mobile/`; `app/(tabs)/profile.tsx` has exactly one action, "Edit Preferences". A user cannot end a session or switch accounts on a device. This is also why SS-070's test accounts are only half-useful without it.
2. **Post-auth onboarding routing lives inside one screen** (`BL-168`) — `app/(auth)/verify-otp.tsx:55-65` is the only place that reads `useOnboardingCompletedQuery` and chooses `/onboarding` vs `/`. The `(tabs)` guard checks session presence only. So any second entry point that does not copy that exact block silently skips onboarding, and — independently of any new scope — a returning phone user with a valid session and incomplete onboarding is never re-prompted.

This ticket fixes both and restructures the login screen so a second method is an addition rather than a rewrite. It deliberately ships **no second method itself** — that is SS-072.

**Risk: high — justified against `docs/OPERATOR_RULEBOOK.md` §C2.** This ticket rewires session lifecycle and the routing guard that stands in front of every authenticated screen. The two failure modes it can introduce are (a) leaking one user's cached wardrobe/profile/suggestion data into another user's session after a switch, and (b) locking a user out of, or into, a screen they cannot leave. Both are external-facing auth surface. No schema change and no migration, but §C2's "on the fence → classify up" applies with room to spare.

**Scope boundary — account linking.** Per the settled policy in `BL-172` (`[VERIFIED 2026-08-14 via WebSearch: supabase.com/docs/guides/auth/auth-identity-linking, ory.com, supertokens.com]`), linking is always user-initiated *while already authenticated*, mirroring Supabase's own `linkIdentity()` shape, and is never automatic on a matching value. **This ticket builds no linking UI** — that belongs to whoever eventually picks up Google SSO (deferred, no ID reserved). What this ticket owes the future is only that its structural choices do not preclude such a flow; AC #8 is the concrete expression of that.

## Description

Three changes to `mobile/`, no backend and no schema.

**1. Login screen becomes a method host.** `app/(auth)/login.tsx` today is phone-only: a heading "Enter your mobile number", one phone `Input` with a country-code picker, one "Send OTP" button. Extract that form wholesale into `features/auth/components/PhoneLoginForm.tsx` and have `login.tsx` render it from a typed method registry that currently contains exactly one entry. **With one registered method the screen must look and behave exactly as it does today** — no chooser chrome, no dead "more options" affordance, no placeholder for a method that does not exist. Adding a second registry entry is what makes the chooser appear.

**2. Sign-out.** `signOut()` in `features/auth/auth.service.ts`, a `useSignOutMutation` in `auth.queries.ts`, and a Sign Out action on `app/(tabs)/profile.tsx` behind a confirmation. Ending a session must clear *all four* places user state lives: the Supabase session (and its SecureStore/web-storage persistence), the React Query cache, every user-scoped Zustand store (wardrobe, onboarding, outfit-ai, style-score, and anything else holding fetched user data), and the Sentry/PostHog user context set at sign-in (`hooks/useAuth.ts`'s `setSentryUserContext`). Then route to `/(auth)/login` with no back-navigation into authenticated screens.

**3. Onboarding routing hoisted out of `verify-otp.tsx`.** One shared mechanism decides, for *any* authenticated session regardless of how it was minted, whether the user goes to `/onboarding` or into the tabs. `verify-otp.tsx`'s inline `useEffect` block is deleted and replaced by it. The existing fail-safe semantics of `checkOnboardingCompleted` (a failed lookup returns `false`, routing to `/onboarding`) are preserved — never trap a user in the tabs on a failed check.

## Acceptance Criteria

1. `app/(auth)/login.tsx` renders the phone form via an extracted `PhoneLoginForm` component, and with a single registered method the screen is behaviourally identical to today — same heading, same country-code picker, same 10-digit validation and error copy, same "Send OTP" CTA. **Proven by SS-003's existing login tests passing unmodified**, not by inspection.
2. Registering a second method in the registry surfaces a method chooser without editing `login.tsx` — proven by a test that registers a fake second method and asserts both entry points are reachable and labelled.
3. A single shared post-auth routing mechanism is the only place in the codebase that decides `/onboarding` vs `/`; `app/(auth)/verify-otp.tsx` no longer contains that decision. Phone OTP sign-in end-to-end behaviour is unchanged (first-ever verify → `/onboarding`; completed user → `/`).
4. A returning user with a valid session and `onboarding_completed = false` who opens the app cold — never passing through an auth screen — is routed to `/onboarding`, not dropped into the tabs. (This is `BL-168`'s second, pre-existing consequence; it is a real behaviour change, and it is the intended one.)
5. `app/(tabs)/profile.tsx` has a Sign Out action; confirming it ends the session and lands on `/(auth)/login`, and no back/history navigation returns to an authenticated screen afterwards.
6. **No cross-user bleed.** After sign-out, the React Query cache and every user-scoped Zustand store are empty: an integration test that seeds cache + store state, signs out, and then mounts an authenticated screen as a *different* user asserts zero rows/values from the first user are present. This AC is the one that makes SS-070's "switch between test users" actually safe.
7. **Sign-out never traps the user.** With the network `signOut` call mocked to fail, local session state and persisted storage are still cleared and the user still lands on login — asserted, not reasoned about.
8. **Forward-compatibility with a phone-less identity, and with future linking.** No screen or hook assumes `session.user.phone` is non-null: a test using a phone-less session fixture (email-only, or neither) mounts profile and the tab layout without crashing, and any identity display falls back email → neutral label. Nothing in this ticket writes to `public.users.phone`/`email` or adds a constraint that would prevent a future authenticated `linkIdentity()`-style flow from attaching a second identifier.
9. `AuthErrorCode` and the auth domain's types are extended **additively only** — existing codes, copy and `AuthError` shape unchanged, so SS-003's flow and tests are untouched.
10. A sign-out analytics event fires through the existing `useAnalytics()` hook using a typed constant in `constants/analyticsEvents.ts` (add one if none fits — see `BL-049`); no `console.log`.
11. `tsc`, `biome` and the full jest suite are clean, with the pre-existing suite green (no test weakened or deleted to accommodate the routing hoist).

## Technical Notes

- **Where the routing decision should live.** The two candidates are (a) a shared hook called by each auth entry point, and (b) a guard in the route layouts (`app/(tabs)/_layout.tsx`, which today checks session presence only). AC #4 — the cold-open case, where no auth screen is involved — can only be satisfied by (b) or by (b)+(a). The design doc must pick one explicitly and say why; do not ship both mechanisms racing each other.
- **Redirect-loop hazard.** A `(tabs)` guard that redirects to `/onboarding` interacts with: `app/(auth)/onboarding.tsx`'s own mount behaviour, SS-016's "Welcome back!" resume prompt (which exists precisely because completed users were being re-prompted — do not regress it), and the `onboardingCompletedQueryKey` invalidation that `onboarding.queries.ts`'s `useCompleteOnboardingMutation` performs on completion. There must be a test that completes onboarding and asserts the user lands in the tabs and *stays* there.
- **Loading state, not a flash.** The onboarding-completed query is asynchronous. The guard must render a loading state while it settles rather than briefly showing tabs and then redirecting (or vice versa). `useOnboardingCompletedQuery` already exposes `isSuccess`; the current `verify-otp.tsx` block gates on it — preserve that discipline.
- **Store clearing must be exhaustive, and provably so.** Enumerate the Zustand stores in the design doc rather than clearing the ones that come to mind. A store added later that holds user data and is not cleared is a silent cross-user leak — consider a single `resetAllUserState()` in `features/auth/` that every store registers with, so the failure mode is "a new store forgot to register" rather than "someone forgot to edit sign-out".
- **`[TRAINED KNOWLEDGE — verify against the installed SDK]`** `supabase.auth.signOut()` accepts a scope (`global` / `local` / `others`); AC #7's failure path likely wants a local clear as the fallback. Check the installed `@supabase/supabase-js` version's actual signature and behaviour before relying on it (`docs/OPERATOR_RULEBOOK.md` §E; `BL-001`'s history is the cautionary example).
- **Do not touch `mobile/lib/supabase.ts`'s `detectSessionInUrl: false`** (`BL-170`). It is set deliberately for native, changing it is a shared-client change across every platform's session bootstrap, and nothing in this ticket needs it — only OAuth/magic-link callbacks do, and Google SSO is deferred. Note that SS-070's `localStorage`-injection path also does not need it.
- `hooks/useAuth.ts` and `features/auth/auth.store.ts` are already provider-neutral (session-truthiness based) — expect small additions, not a rewrite.

## Edge Cases & Failure Modes

- **Sign-out with a mutation in flight** (an upload, a preference save): the mutation resolves against a dead session. Cancel/settle in-flight React Query work before clearing, and ensure a late rejection cannot navigate the now-signed-out user or surface an error toast on the login screen.
- **Double-tap sign-out**, or sign-out fired twice from a confirmation dialog: idempotent, no double navigation, no crash.
- **Sign-out mid-onboarding** (partial `users` row written, `onboarding_completed = false`): allowed; signing back in returns the user to `/onboarding` with whatever was saved. Must not leave a half-cleared store that the next sign-in inherits.
- **Web vs native persistence.** Web uses browser storage, native uses `expo-secure-store`. Both must be cleared. **Native cannot be verified end-to-end** — no EAS build exists (`BL-047`) and no hosted build exists (`BL-171`); say so plainly in QA rather than claiming a native check that did not happen.
- **Deep link to an authenticated route while signed out** (`/wardrobe`, `/outfit/[id]`): guard redirects to login, and — ideally — does not lose the intended destination. If the destination is dropped, say so; do not silently pretend it round-trips.
- **Onboarding-completed check fails** (network blip, RLS edge): the existing service fails safe to `false` → `/onboarding`. Preserve exactly this; a completed user briefly seeing onboarding is recoverable, a user trapped outside the app is not.
- **Session expiry while the app is open.** The existing auth listener handles the session going away; confirm the new guard reacts to that transition the same way it reacts to sign-out, and does not require an app restart.
- **A phone-less session today.** No such session can be minted before SS-072 lands — but SS-070's admin-created accounts are exactly that (email, no phone), so AC #8's fixture is not hypothetical: it is what SS-070 produces.
