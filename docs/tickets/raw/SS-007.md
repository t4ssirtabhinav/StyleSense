# SS-007 — Granular Preferences Editor (Profile → Edit Preferences)

`[Feature]` `[P1]` `[Sprint 2]` `[2 pts]` Est: 6h
Depends on: SS-004, SS-005

## Source note (this repo)

Surfaced during SS-004's Architect design review (2026-07-13): SS-004's only path to change any onboarding answer post-signup is re-running the full 4-step wizard from Profile → Edit Preferences (itself blocked on SS-005's Profile tab shipping — see BL-023). There is no way to make a single targeted change (e.g. "I want to add a 4th occasion I now care about" when the cap was 3, or "swap one favourite colour for another") without replaying every step. This ticket builds that targeted editor.

## Description

A dedicated Preferences screen (reached from Profile → Edit Preferences) that lets a user view and edit each `style_preferences` field independently — not a re-run of the onboarding wizard. Each section (style keywords, wardrobe type, occasion priorities, budget range, favourite colours) is its own editable block with its own save action, using the same option taxonomies SS-004 (and SS-006, if it ships DB-backed reference tables first) defines.

- View current values for every field, pre-filled from `users`/`style_preferences`
- Edit any single section without touching the others; each section saves independently (partial update, not a full-object overwrite)
- Occasion priorities and favourite colours keep their existing caps (3 and 5 respectively) but allow swapping — deselect one, select a replacement — without going through Steps 1-3 again
- Uses the same components as onboarding (`Badge` chips, colour swatches) — no new design-system components needed, only a new screen composing them differently

## Acceptance Criteria

- Profile → Edit Preferences opens this screen, not the onboarding wizard
- Each of the 5 preference sections (style keywords, wardrobe type, occasion priorities, budget range, colours) can be edited and saved independently of the others
- Occasion priority and colour caps (3 / 5) are enforced the same way they are in onboarding, with the same "you can select up to N" inline hint
- Saving one section does not overwrite or clear any other section's data
- Screen reflects the currently saved values on load (no stale/empty state even if the user has never touched a given section since onboarding)

## Technical Notes

- Reuses `features/onboarding/onboarding.constants.ts` (or SS-006's DB-backed reference tables, if that ships first) for option lists — do not fork a second copy of these taxonomies
- New `features/onboarding/onboarding.service.ts` methods for per-section partial updates (e.g. `updateOccasionPriorities(userId, occasions)`), separate from `completeOnboarding`'s full-object write
- Lives under `app/(tabs)/profile/edit-preferences.tsx` (exact route depends on SS-005's Profile tab structure)

## Edge Cases & Failure Modes

- User has never completed onboarding (`onboarding_completed: false`) and reaches this screen some other way — decide whether to block entry (redirect to the wizard) or allow partial editing of whatever they've saved so far
- Network failure mid-save on one section must not roll back or affect other already-saved sections
