# SS-057 — Save Outfit, Occasions, Visibility & Collections

`[Feature]` `[P1]` `[3 pts]` Est: 10h
Depends on: none (works standalone; pairs naturally with SS-055)
Risk: low

## Source note (this repo)

Promoted from `docs/competitive/07-EPICS-AND-TICKETS.md`'s portfolio-scope rewrite (2026-08-20). The one schema decision in the whole plan worth shipping ahead of its consumer: `docs/competitive/04-INDYX-TEARDOWN.md` §7.6 notes `source`/`status` on outfits is the one Indyx schema decision that's genuinely painful to retrofit after real data exists. Two columns now, versus a migration on a grown table plus permanently unattributable history later.

## Description

A real save-outfit flow: `source` (who/what created this outfit — `self | ai | expert | social`) and `status` (`owned | recommendation | wishlist`) added to `outfits`, plus a save sheet UI that lets a user name an outfit, tag its occasion (already supported — `outfits.occasion` exists), and assign it to a typed collection.

## Acceptance Criteria

- `outfits` gains `source TEXT` (`self|ai|expert|social`, CHECK-constrained) and `status TEXT` (`owned|recommendation|wishlist`, CHECK-constrained) — additive, nullable or defaulted, following `020_outfits_first_writer.sql`'s established pattern for widening this same table
- Every write path that creates an outfit (the existing `SS-023` swipe-accept flow, and any new explicit "save from Dressing Room" path from `SS-055`) sets `source`/`status` correctly — `source='ai', status='owned'` for an accepted suggestion; a `SS-055`-built-from-scratch outfit is `source='self', status='owned'`
- A collections concept: at minimum a `collection` type/label on outfits (`wishlist | packing | capsule | custom`) — decide whether this needs its own table or fits as another typed column/tag on `outfits`, and record the choice
- **`wishlist`-status outfits are excluded from wardrobe stats** (`SS-052`'s eventual consumer) — an outfit someone's dreaming about shouldn't count toward "how often do you re-wear outfits"
- Save sheet UI: name (optional), occasion picker (reuse existing occasion registry/picker from `SS-023`'s suggestion flow — don't build a second one), collection assignment
- Nothing existing breaks — `outfits`' current sole real writer (`SS-023`'s outcome endpoint) keeps working with the new columns defaulting sensibly for its existing call sites

## Technical Notes

**Add the columns even though `SS-052` (the only near-term reader) isn't built yet** — this is explicitly the point of doing it now, per the source note above. Don't wait for a consumer to justify the migration.

**Follow `020_outfits_first_writer.sql`'s exact pattern** — it's the precedent for widening this specific table, including its RLS-unchanged reasoning and its rollback-block convention. Read it before writing the new migration.

**`outfit_fingerprint`/`items_snapshot` already exist** (`020`) — this ticket doesn't touch outfit identity or the denormalised item snapshot, only adds provenance/status/collection metadata alongside them.

## Edge Cases & Failure Modes

- An outfit accepted via `SS-023`'s existing flow before this ticket ships — backfill or leave `source`/`status` NULL for pre-existing rows? State the choice (likely: leave NULL, treat NULL as "unknown provenance" rather than backfilling a guess)
- A `status='wishlist'` outfit that a user later actually wears — does status need to transition to `owned`, and if so, is that automatic (on a "wore this today" action) or manual? Decide and record; don't leave it undefined
- Collection assignment on an outfit with no items yet (a wishlist entry built from items the user doesn't own) — confirm `outfits.item_ids`' existing `NOT NULL`/non-empty CHECK (`020_outfits_first_writer.sql:21-22`) doesn't block this use case; if it does, that's a real conflict to surface, not silently work around
