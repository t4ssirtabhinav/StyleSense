# SS-038 — Engine v2 Core: Wide Search, Attribute Scoring & MMR Portfolio — Design

## Scope restatement

Replace the deterministic styling pre-filter's stage-②/③ (candidate generation + scoring) with a four-stage pipeline — eligibility, wide candidate search, pairwise attribute scoring (including occasion-aware novelty), MMR portfolio selection — that explores far more of a wardrobe than today's flat ~72-candidate cap, scores colour/formality/register pairwise instead of star-topology, and returns a diverse 5–8-outfit portfolio plus up to 2 explicitly-labelled exploration candidates, all above a hard score floor. Garment identity (slot/layer/register/formality/pairs_with) is read through a new cached adapter over the `garment_types` registry (SS-034) with an explicit, tested fallback to the legacy 21-value `WardrobeCategory` enum dicts — since no live `wardrobe_items.category` value currently resolves through `garment_types` (SS-034 seeded new-vocabulary keys, not the enum), every real wardrobe exercises the fallback path today, by design, until a future taxonomy migration. The near-white cream/ivory threshold moves from a Python literal into an `app_config` row (identical coded default) with a per-occasion override path via `occasions.styling_rules`, resolving `BL-111`. This ticket is a pure-Python callable pipeline (`EngineV2.generate_portfolio(...)`) plus one data-only migration seeding the new config row — no new HTTP route, no router wiring, no schema DDL. It is the first real caller of `wear_recency()`/`IWearHistoryRepository` (SS-035) and writes real `suggestion_impressions` rows (SS-033), bumping `engine_version` to `"engine-v2"`.

## Files to create/modify

### New files

**`backend/services/engine_v2.py`** — orchestrator. `EngineV2` class, constructor-injected with `GarmentRegistryAdapter`, `IFabricRegistryRepository`, `IWearHistoryRepository`, `ISuggestionLogRepository`, `AppConfigService`. Public method:

```python
async def generate_portfolio(
    self,
    wardrobe: list[WardrobeItemInput],
    occasion: OccasionStylingInput,
    *,
    jwt: str,
    user_id: str,
    as_of: date,
    season: SeasonTag | None = None,
    style_preferences: StylePreferencesInput | None = None,
    portfolio_size_range: tuple[int, int] = (5, 8),
    max_exploration: int = 2,
) -> EngineV2Result
```

This is the **only** async/I/O boundary in the whole pipeline. Sequence:
1. `await self._garment_registry.refresh()` — TTL-cached, safe to call every request.
2. `fabric_attrs = await self._fabric_repo.fetch_all()` (a small dict snapshot, re-fetched per call — see "Concrete values" for why this doesn't need `garment_registry`'s TTL machinery).
3. `rules = engine_v2_eligibility.resolve_styling_rules(occasion)` — pure.
4. `app_config_snapshot = await self._app_config.snapshot()`.
5. `near_white = engine_v2_eligibility.resolve_near_white_thresholds(app_config_snapshot, rules)` — pure given the snapshot.
6. `eligibility = engine_v2_eligibility.filter_eligible(wardrobe, occasion, rules, near_white_thresholds=near_white)` — pure.
7. `novelty_inputs = await engine_v2_novelty.fetch_novelty_inputs(self._wear_history_repo, self._suggestion_log_repo, jwt=jwt, user_id=user_id, occasion_key=occasion.key, as_of=as_of)` — the one other I/O call, contractually never-raising per both ports.
8. `search_result = engine_v2_candidate_search.search_candidates(eligibility.eligible_items, garment_lookup=self._garment_registry.get_garment_attributes, rules=rules, as_of=as_of, season=season, style_preferences=style_preferences)` — pure.
9. `scored = [engine_v2_attribute_scoring.score_assembled_candidate(c, occasion, rules, garment_lookup=..., fabric_attrs=fabric_attrs, novelty_inputs=novelty_inputs, as_of=as_of, season=season, style_preferences=style_preferences) for c in search_result.candidates]` — pure.
10. `portfolio_result = engine_v2_portfolio.select_portfolio(scored, score_floor=DEFAULT_SCORE_FLOOR, lambda_=DEFAULT_MMR_LAMBDA, portfolio_size_range=portfolio_size_range, max_exploration=max_exploration)` — pure.
11. Best-effort log: build one `SuggestionSessionLog(engine_version="engine-v2", ...)` + a `SuggestionImpressionLog` per portfolio item (rank, item_ids, `outfit_fingerprint`, `total_score`, `rule_scores`, `gap_flags`, `is_exploration`) and call `await self._suggestion_log_repo.log_session(...)` — never raises by the port's own contract; `session_id` may be `None`, never blocks the return.
12. Return `EngineV2Result(portfolio=..., limited_options=..., gap_report=..., session_id=..., engine_version="engine-v2")`.

Module docstring is this ticket's AC-required "successor docstring" — see "Concrete values" for its required content (which SS-027/037-era gaps are fixed, by stage, and which named `BL-XXX` rows remain open).

**`backend/services/engine_v2_colour.py`** — the one colour-primitives module both eligibility (near-white guard) and attribute-scoring (pairwise harmony) depend on, so there is exactly one implementation, never two:
- `hex_to_hsv(hex_color: str) -> tuple[float, float, float] | None` — moved verbatim from `styling_rules_engine._hex_to_hsv`.
- `hue_distance_score(hex_a: str, hex_b: str) -> float` — moved verbatim from `styling_rules_engine._hue_distance_score`, **including its flat `0.75` fallback for unparsable input, deliberately unchanged** — see "Concrete values" for why (BL-128's fallback half stays open).
- `is_near_white(hex_color: str, *, value_threshold: float, saturation_threshold: float) -> bool` — same predicate as `styling_rules_engine._is_near_white`, now parameterized on thresholds instead of importing module constants (so the eligibility stage can pass the app_config/occasion-resolved values through).
- `item_is_hard_excluded_white(item: WardrobeItemInput, *, value_threshold: float, saturation_threshold: float) -> bool` — same fail-closed semantics as `styling_rules_engine._item_is_hard_excluded_white`, parameterized.
- `pairwise_colour_harmony(items: list[WardrobeItemInput]) -> float` — **new**, replaces `_colour_harmony_score`'s star-topology. Computes `hue_distance_score` over every `itertools.combinations(colored, 2)` pair (not just `colored[1:]` vs `colored[0]`), returns the mean (same `<2 colours → 1.0` "nothing to clash with" base case as today).

**`backend/services/engine_v2_eligibility.py`** — stage ①, pure:
- `resolve_styling_rules(occasion: OccasionStylingInput) -> StylingRulesOverride` — moved verbatim from `styling_rules_engine._resolve_styling_rules`.
- `resolve_near_white_thresholds(snapshot: AppConfigSnapshot, resolved_rules: StylingRulesOverride) -> NearWhiteThresholdConfig` — **new**. `app_config_value = app_config_service.read(snapshot, NEAR_WHITE_THRESHOLD_SPEC)`; per-field, occasion override wins if `resolved_rules.near_white_value_threshold`/`near_white_saturation_threshold` is non-`None`, else the app_config value. **`backend/services/engine_v2_candidate_search.py`** — stage ②, pure:
- Per-item scoring primitives moved verbatim from `styling_rules_engine.py` (unchanged formulas — `_formality_item_score`, `_recency_item_score`, `_season_item_score`, `_occasion_tag_item_score`, `_style_preference_item_bonus`), so stage② and stage③ share **one** implementation of each, same "no drift" contract v0 already established.
- `assembly_slot_for(item: WardrobeItemInput, garment_lookup) -> str` — resolves via `garment_lookup(item.category)` → `GarmentAttributes.assembly_slot` when a row exists, else `CATEGORY_SLOT[item.category]` (the existing 21-value dict). This is the fallback boundary the AC's regression test targets.
- `search_candidates(eligible_items, *, garment_lookup, rules, as_of, season, style_preferences, top_k_bases=CANDIDATE_SEARCH_TOP_K_BASES, top_n_per_remaining_slot=CANDIDATE_SEARCH_TOP_N_PER_REMAINING_SLOT) -> CandidateSearchResult`:
  1. Group eligible items by `assembly_slot_for(...)` (replaces `_group_by_slot`; same six buckets: top/bottom/one_piece/outerwear/footwear/accessory).
  2. Build **every** top×bottom pair and every one_piece base (no per-slot pre-cap) — this is `total_base_pairs_considered`.
  3. Rank each base by a combined key: `0.35*mean(formality) + 0.25*mean(recency) + 0.15*mean(season) + 0.15*mean(occasion_tag) + 0.10*mean(style_pref) + colour_weight*pairwise_colour_harmony(base_items)` (colour folded into the ranking key itself — this is the literal fix for "colour absent from the per-slot capping formula"; `colour_weight` is an Architect-assigned constant, see "Concrete values"). Keep the top `top_k_bases` (default 200).
  4. For the top 50 of those (or fewer if `top_k_bases` capped lower), expand each with the top `top_n_per_remaining_slot` (default 5, not the single best) options per remaining slot (footwear if `rules.footwear_required` or available; outerwear if available, attached opportunistically exactly as SS-037 did — BL-129's ranking half, not attachment-gating, is this ticket's job; one item per `rules.preferred_accessory_categories` category, top-N per category), producing multiple distinct `AssembledCandidate`s per base rather than one. Each combination is scored for slot-fit using the same per-item primitives (plus a category preference bonus, unchanged from v0's `footwear_key`/`accessory_key`).
  5. `missing_slots` computed the same way `generate_candidates` did (any of the six slots with zero eligible items).

**`backend/services/engine_v2_attribute_scoring.py`** — stage ③, pure:
- `category_completeness_score(items, rules) -> float` — moved verbatim from `styling_rules_engine._category_completeness_score`.
- `volume_balance_score(items, garment_lookup) -> float` — **new**. For every pair where BOTH items resolve via `garment_lookup` and both have a non-`None` `volume_class`: penalize (`0.6`) when both are `"voluminous"`/`"oversized"`-class **and** neither item's `register` includes `"streetwear"`; else `1.0`. Any item unresolved (fallback path) or missing `volume_class` contributes **no signal** for that pair (excluded from the mean, not scored as `0`) — mean over scored pairs, `1.0` if no pair had a signal at all (matches the Technical Notes' "neither bonus nor penalty" instruction literally).
- `register_coherence_score(items, garment_lookup) -> float` — **new**. For every pair where both resolve via `garment_lookup`: `1.0` if `set(a.register) & set(b.register)` is non-empty or `b.key in a.pairs_with` or `a.key in b.pairs_with`; else `0.5`. Same "unresolved pair contributes no signal, mean over scored pairs, `1.0` default" degrade as `volume_balance_score`.
- `fabric_weather_score(items, fabric_attrs: dict[str, FabricAttributes], *, season) -> float` — **new**, gated per BL-125 (see "Concrete values"). Per item: look up `fabric_attrs.get(item.fabric)`; if `season is None` or no fabric row → `1.0` (no opinion). Else combine, where populated: (a) `season_affinity` match (`1.0` if `season in row.season_affinity`, `0.4` if populated-but-no-match, **skipped** if `row.season_affinity is None`); (b) breathability-vs-season heuristic (`summer` prefers high breathability, `winter` prefers low/heavy, `monsoon` prefers light+moderate-high breathability; skipped if `row.breathability is None`). Mean of whichever sub-signals are actually populated; `1.0` if none are.
- `score_assembled_candidate(candidate: AssembledCandidate, occasion, rules, *, garment_lookup, fabric_attrs, novelty_inputs, as_of, season, style_preferences) -> ScoredCandidate` — orchestrates all terms into one `RuleScore` list + weighted `total_score`, mirrors `styling_rules_engine.score_candidate`'s shape exactly (same `ScoredCandidate`/`RuleScore` types, so `render_candidate_for_prompt` needs zero changes). Uses `ENGINE_V2_RULE_WEIGHTS` (see "Concrete values").

**`backend/services/engine_v2_novelty.py`** — stage ③'s novelty sub-term, split impure/pure:
- `async def fetch_novelty_inputs(wear_history_repo: IWearHistoryRepository, suggestion_log_repo: ISuggestionLogRepository, *, jwt, user_id, occasion_key, as_of) -> NoveltyInputs` — calls `wear_history_repo.fetch_wear_recency(jwt=jwt, user_id=user_id, occasion_key=occasion_key)` and `suggestion_log_repo.recent_impressions(user_id=user_id, since=<as_of - 30 days>)`, both **already contractually never-raise** (returning `[]` on failure per their own port docstrings) — this function does not need its own try/except to satisfy "DB error degrades to neutral," it only needs to correctly build a neutral `NoveltyInputs` from empty inputs, which the pure scorer below already does.
- `compute_novelty_score(item_ids: list[str], occasion_key: str | None, inputs: NoveltyInputs, *, as_of: date) -> float` — pure. Per item: `days_since_occasion` from `last_worn_on_for_occasion` (`None` → maximal novelty, `1.0`); `days_since_any` from `last_worn_on` similarly; `times_shown = inputs.recent_impression_item_counts.get(item_id, 0)`. `item_novelty = 0.5*saturate(days_since_occasion, 90) + 0.3*saturate(days_since_any, 90) + 0.2*(1 - min(1.0, times_shown/5))`, where `saturate(days, cap)` mirrors `_recency_item_score`'s existing `min(1.0, days/cap)` convention (`None` days → `1.0`). When `occasion_key is None` (BL-121's Mark Worn case), the `days_since_occasion` term degrades to `days_since_any`'s value instead of always being `1.0`-by-absence — i.e. novelty degrades to "global novelty," not "everything maximally novel." Candidate-level score is the mean over `item_ids`.

**`backend/services/engine_v2_portfolio.py`** — stage ④, pure:
- `compute_outfit_fingerprint(item_ids: list[str]) -> str` — `hashlib.sha256(",".join(sorted(item_ids)).encode()).hexdigest()`, order-independent, matches `suggestion_impressions.outfit_fingerprint`'s `^[0-9a-f]{64}$` CHECK.
- `jaccard_similarity(a: ScoredCandidate, b: ScoredCandidate) -> float` — `|set(a.item_ids) ∩ set(b.item_ids)| / |set(a.item_ids) ∪ set(b.item_ids)|`. Architect-chosen concrete metric for the proposal's abstract "similarity" term — flagged as unvalidated, same class as `RULE_WEIGHTS` (folds into `BL-077`).
- `select_portfolio(scored: list[ScoredCandidate], *, score_floor, lambda_, portfolio_size_range=(5,8), max_exploration=2) -> PortfolioResult` (`PortfolioResult(portfolio: list[PortfolioCandidate], limited_options: bool, gap_report: GapReport)`):
  1. `eligible = [c for c in scored if c.total_score >= score_floor]`, sorted `(-total_score, tuple(item_ids))` for determinism.
  2. `limited_options = len(eligible) < 3` (same threshold semantics as v0's `len(scored) < 3`).
  3. Greedy MMR: seed with the top-scored candidate; repeatedly pick `argmax(lambda_*score - (1-lambda_)*max(jaccard_similarity(c, s) for s in selected))` over remaining eligible candidates, deterministic tiebreak `(-mmr_score, item_ids tuple)`, until `portfolio_size_range[1]` (8) is reached or `eligible` is exhausted.
  4. If `len(portfolio) < portfolio_size_range[0]` (5), that's honest — return what's available, do not fabricate.
  5. Exploration: continue the **same** MMR process (same eligible pool minus already-selected) for up to `max_exploration` (2) more picks, each marked `is_exploration=True`. Since step 1 already filtered to `>= score_floor` before *any* selection happens, an exploration pick can never be below-floor by construction (satisfies the edge case literally).

**`backend/services/garment_registry_adapter.py`** — the cached lookup:
```python
class GarmentRegistryAdapter:
    def __init__(self, repository: IGarmentRegistryRepository, *, ttl_seconds: float = 60.0) -> None: ...
    async def refresh(self) -> None: ...  # never raises; stale-or-empty-serving, mirrors OccasionNormalizer.get_registry
    def get_garment_attributes(self, category: str) -> GarmentAttributes | None: ...  # pure, sync, given whatever is cached
```
`get_garment_attributes` normalizes `category.strip().lower()`, checks `snapshot.rows` (exact key) first, then `snapshot.aliases` (alias → key → row) — mirrors `garment_normalize_one`'s step-2-before-step-3 resolution order, **without** writing to `garment_unknown_types` (this is a read-only hot-path consumer; logging every fallback category — 100% of them today — would spam that table for no review value). Module-scope singleton `garment_registry_adapter = GarmentRegistryAdapter(SupabaseGarmentRegistryRepository())`, constructed with zero I/O, mirrors `app_config_service`'s precedent exactly.

**`backend/adapters/garment_registry_repository.py`** — `SupabaseGarmentRegistryRepository(IGarmentRegistryRepository)`. `fetch_registry() -> GarmentRegistrySnapshot`: `SELECT key, slot, layer, register, base_formality, pairs_with, requires_with, excludes_with, styling_rules FROM garment_types WHERE is_active` + `SELECT alias, garment_key FROM garment_type_aliases`. **Uses `service_role`, not caller-JWT** — deliberate, explicit deviation, same justification as `IAppConfigRepository`'s own documented precedent (`app_config_repository.py`'s module docstring): `garment_types` is non-user-owned reference data, its RLS policy (`authenticated_read_garment_types`) requires only `auth.role() = 'authenticated'` (no per-user ownership), and the hot scoring loop needs `get_garment_attributes` callable with **no jwt in hand** (per the ticket's own literal signature). Documented here rather than silently introduced, per `app_config_repository.py`'s own stated norm.

**`backend/adapters/fabric_registry_repository.py`** — `SupabaseFabricRegistryRepository(IFabricRegistryRepository)`. `fetch_all() -> dict[str, FabricAttributes]`: `SELECT key, weight, breathability, season_affinity FROM fabrics WHERE is_active`. Same `service_role` justification as above (reference data). No TTL-cache class needed — `fabrics` has 11 seeded rows, near-zero write frequency, and `engine_v2.py` fetches it once per `generate_portfolio()` call (not per-item inside the hot loop) — a plain per-request fetch is cheap and needs none of `garment_registry_adapter`'s cross-request caching sophistication, which exists specifically because `get_garment_attributes` is called once per item **inside** the O(pairs) scoring loop.

## Concrete values to use, not invent

- **Near-white thresholds** — coded default `value_threshold=0.92`, `saturation_threshold=0.12` (transcribed verbatim from `NEAR_WHITE_VALUE_THRESHOLD`/`NEAR_WHITE_SATURATION_THRESHOLD`), unchanged by this ticket per the user's explicit sign-off. `app_config` key name: `near_white_threshold`. `occasions.styling_rules` override field names: `near_white_value_threshold`/`near_white_saturation_threshold` (must match `StylingRulesOverride`'s new field names exactly, snake_case, mirroring existing fields like `formality_tolerance`).

## Edge cases

Carried forward verbatim from the raw ticket (all nine — see raw ticket's own "Edge Cases & Failure Modes"), plus these newly observed during design:

- `garment_registry_adapter.refresh()` is never awaited before the first `get_garment_attributes()` call (a caller bug) — `_snapshot` starts `None`, treated as empty, every lookup returns `None` (full fallback) — safe, not a crash.
- A wardrobe item's `fabric` column holds a slug that shape-normalizes but isn't a real `fabrics.key` (an unknown fabric captured in `attribute_unknown_tags` per SS-036) — `fabric_attrs.get(item.fabric)` returns `None`, `fabric_weather_score` degrades to `1.0` for that item, same posture as an unresolved `garment_lookup`.
- `season` is provided but a candidate has zero items with a populated `fabric` — `fabric_weather_score` returns `1.0` (no signal anywhere), not an error or a `0`.
- Stage②'s base-pair ranking key uses `pairwise_colour_harmony`, which needs `>=2` coloured items — a `one_piece` base has exactly one item, so the colour term there is always `1.0` ("nothing to clash with"), consistent with v0.
- A candidate ties exactly on MMR score during portfolio selection (possible with small wardrobes / few distinct items) — deterministic tiebreak `(-mmr_score, item_ids tuple)`, same convention as every other sort in this codebase.
- `recent_impressions()` returns impressions from **other occasions** too (it is not occasion-filtered by the port) — `NoveltyInputs.recent_impression_item_counts` should count **all** recent impressions regardless of occasion (an item shown often anywhere is less novel to show again anywhere), while `wear_recency_by_item`'s occasion-scoped fields stay occasion-specific — these are two different axes of "novelty" and must not be conflated into one filter.
- `garment_types.styling_rules.volume_class` is absent (`{}`  or key missing) for a `garment_lookup`-resolved item — `volume_balance_score` treats this identically to an unresolved item for that pair (no signal), not as `volume_class=None` being itself informative.
